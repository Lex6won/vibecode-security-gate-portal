# L1 Thin Mode Policy

L1 시제품은 1시간 내 첫 결과물을 목표로 한다. 운영·보안 기준을 버리는 것이 아니라, 기록과 에이전트 홉을 최소화한다.

Codex 하네스는 내부적으로 표준 운영 하네스지만, L1 사용자 경험은 Claude식 현장 실행처럼 가볍게 보여야 한다. 사용자에게는 “구상 → 만들기 → 확인” 정도로 보이고, 기관 담당자에게 필요한 증거는 `_workspace/`와 manifest에 얇게 남긴다.

## L1 필수 산출물

- `_workspace/00_feature_brief.md`: 만들 것, 사용자, 화면/입력/출력, 위험 플래그
- `_workspace/00_작업현황.md`: 현재 단계와 핵심 결정 3~5줄
- `_workspace/source/`: 실행 가능한 시제품 코드
- `_workspace/vibecode-manifest.json`: 최소 필드만

## L1 선택 산출물

다음은 조건부로만 만든다.

- PRD: 사용자가 요청하거나 L2로 올릴 때
- DB정의서: 지속 저장이 있을 때
- 보안점검보고서: quick 검사 결과 요약 또는 위험 플래그가 있을 때
- 핸드오프 파일: `block`, `warn`, `needs-user`일 때. `pass` 흐름은 작업현황에 한 줄 기록으로 대체 가능
- 배포가이드/신청서: L3로 올린 뒤에도 기관 양식 또는 운영팀 설치 인계가 필요할 때만

## L1 축약 흐름

사용자에게 보이는 흐름:

`구상 정리 → 표준 템플릿으로 만들기 → 필요한 점검만 하기`

내부 기본 흐름(6홉):

`intake-guide(성숙도 L1 직접 설정) → feature-discovery → template-engineer → gg-platform-coder → security-checker(quick) → qa-operator`

- **stage-advisor는 L1 기본에서 생략한다.** intake-guide가 승격 신호 없는 L1을 직접 설정하므로 별도 홉이 불필요하다.
- stage-advisor는 승격 신호가 있거나 사용자가 L2/L3을 목표할 때만 호출한다(성숙도 최종 판정 권한은 유지).
- security-checker quick은 위험 변경, 새 패키지, 개인정보/파일업로드/외부통신, 또는 사용자의 “중간 점검” 요청이 있을 때만 호출한다. 단순 문구·색상·레이아웃 수정에는 자동 점검을 강요하지 않는다.
- L1에서 모든 에이전트 이름을 사용자에게 나열하지 않는다. 필요한 경우 “표준 템플릿으로 만들고, 위험한 부분만 빠르게 확인하겠습니다”라고 말한다.

다음 조건이면 상세 흐름(+stage-advisor)으로 승격한다.

- 시민/도민 접근
- 개인정보/민감정보
- 파일업로드
- 지속 저장 DB
- 외부 API/CDN/LLM/MCP
- 담당자가 L2/L3 목표를 명시

## 원칙

- L1에서 문서 완성도를 이유로 첫 실행을 늦추지 않는다.
- 단, 위험 플래그는 생략하지 않는다.
- L1 결과물에는 “내부 시제품이며 정식 서비스가 아님”을 표시한다.
- 차단이 발생하면 예외신청보다 먼저 대체 구현, 승인 템플릿 안의 기능 축소, 승인 패키지 대체안을 제시한다.
