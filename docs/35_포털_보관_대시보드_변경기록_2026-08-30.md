# 35. 포털 보관·대시보드 변경 기록 (2026-08-30)

## 목적

점검 결과를 사용자가 먼저 확인·저장한 뒤 보안성검토 요청으로 제출하고, 원본 보고서 보관 기간이 끝난 뒤에도 기관의 점검 추세와 사용 패키지 현황을 관리한다.

## 확정 보관 정책

| 데이터 | 생성 시점 | 보관 내용 | 보관 정책 |
| --- | --- | --- | --- |
| 임시 산출물 | 점검 완료 | HTML, JSON, Markdown, CycloneDX SBOM(지원되는 의존성 파일이 있을 때) | 보안성검토 요청 전 최대 24시간 |
| 제출 보고서 원본 | 보안성검토 자료 제출 | HTML, JSON, Markdown, SBOM, 생성 요청서, 제출자료 ZIP | 기본 90일 후 자동 삭제 |
| 점검 이력 | 점검 상태 변경 | 일시, 상태, 판정, 건수, 개발언어, 점검 시점의 이메일·기관·부서 스냅샷 | 유지. 시계열 및 사용자·기관·부서 통계 기준 데이터 |
| 패키지 관측·통계 | 보안성검토 요청 제출 | 생태계, 패키지명, 정확 버전 여부와 버전, 취약 신호 | 유지. 대시보드·화이트리스트 기준 데이터 |
| 화이트리스트 | 관리자 변경 | 포함·제외 상태와 감사 이력 | 기존 정책에 따라 유지 |

원본 소스는 점검 직후 삭제한다. 90일 정리 작업은 제출 보고서 파일만 대상으로 하며, 점검 이력·패키지 통계·화이트리스트를 삭제해서는 안 된다.

## 이번 구현 내용

- 점검 완료 시 JSON, HTML, Markdown을 임시 산출물로 생성한다. CycloneDX 1.6 SBOM은 체커가 지원하는 의존성 파일(`package.json`, `requirements*.txt`)을 찾은 경우에만 생성하며, 빈 SBOM은 만들지 않는다.
- 산출물 파일명은 `<점검대상>_<한국시간 점검일시>_<점검방식>`으로 생성한다. 폴더·압축 파일은 선택한 이름을 사용하고, GitHub·GitLab은 URL의 마지막 저장소 이름을 사용한다.
- 체커가 HTML·Markdown 파일명에 내부 프로젝트명을 쓰는 경우에도 포털이 최종 파일명으로 정규화한다. 결과 화면은 사람이 읽는 산출물 이름만 눌러 볼 수 있게 제공한다.
- 결과 화면에서 각 산출물을 바로 보기 또는 내려받기 할 수 있다. SBOM의 PC 저장은 선택 사항이다.
- `보안성검토 자료 제출` 버튼 한 번으로 산출물을 제출 보고서 영역으로 승격하고, 패키지·버전 관측값을 적재한다.
- 제출 시 보안성검토 요청서(HTML)와 모든 점검 산출물을 담은 제출자료 ZIP을 생성한다. ZIP에는 `01_보안성검토요청서.html`, `02_점검리포트/결과 리포트·패키지 목록·소프트웨어 명세서(SBOM)`가 들어간다.
- 선택한 저장 폴더가 있으면 제출자료 ZIP을 그 폴더에 자동 저장한다. 제출 완료 뒤 `저장 폴더 열기`는 해당 폴더를 시작 위치로 하는 브라우저의 Windows 폴더 확인 창을 연다. `확인하고 마치기`는 포털 홈으로 돌아간다. 폴더 선택을 지원하지 않는 브라우저에서는 기본 다운로드 위치로 저장을 요청한다.
- 관리자 대시보드에서 기간, 상태, 검색어(이메일·기관·부서 포함), 생태계, 개발언어, 화이트리스트 상태로 필터링한다.
- 월별 점검 건수는 꺾은선 그래프, 개발언어·패키지 분포는 원그래프, 화이트리스트는 목록으로 제공한다.
- 이메일별·기관별·부서별로 점검 건수와 최근 점검일을 제공한다. 이 값은 보고서 원본 파일의 90일 보관 정책과 독립적으로 유지한다.
- SBOM은 잠금 파일 또는 정확 버전 선언이 있으면 `components[].name`, `components[].version`, `purl`에 정확 버전을 기록한다. 버전 범위만 있거나 잠금 파일이 없으면 정확 버전은 보장하지 않는다.

## 하네스 설치 화면 정리 (2026-08-30)

- 하네스 화면은 `1 내려받기 → 2 설치 → 3 설정`으로 고정한다. 1단계는 큰 설치 파일 내려받기 버튼과 함께 Harness Manager·AI 도구 지침·gg 명령이 왜 필요한지 짧게 설명한다.
- 설치 파일 내려받기 버튼을 누르면 2단계 설치 안내로 자동 이동한다. 브라우저는 외부 설치 파일의 디스크 저장 완료나 Windows 설치 프로그램 종료를 감지할 수 없으므로, 2단계에서 사용자가 설치를 마친 뒤 `설치 완료 · 설정하기`를 눌러 3단계로 이동한다.
- 2단계에는 다운로드 완료 확인, 설치 파일 실행, Windows 설치, 시작 메뉴의 `VibeCode Harness Manager` 실행 순서만 표시한다.
- 체험판처럼 서명되지 않은 배포일 때에만 2단계에 `알 수 없는 게시자 → 추가 정보 → 실행` 안내를 표시한다. 이 문구는 포털에서 직접 내려받은 설치 파일에만 적용한다.

## 내 점검 이력 진입 경로 정리 (2026-08-30)

- 홈의 `내 점검 이력`은 `/my`로 직접 이동한다. `/my`도 `/scan`과 동일하게 Cloudflare Access 세션 또는 개발용 루프백 세션을 자동 생성해야 하며, 점검 화면을 먼저 방문해야만 이력이 보이는 흐름을 금지한다.
- `/my`의 첫 화면은 `점검 이력`이다. 소속 정보는 헤더의 `소속 수정`을 눌렀을 때만 이력 아래에서 열고, 기관명·부서명 라벨을 분명히 표시한다.
- 개발 서버 기본 계정의 `개발 검증`·`보안점검`은 기관·부서 예시값일 뿐 기능명이나 이력 분류가 아니다. 이 값이 이력 첫 화면에 독립 카드로 노출되지 않게 한다.
- `scripts/portal-button-contract-test.mjs`에 `/my`의 Access 자동 로그인, 이력 우선 배치, 선택형 소속 수정 계약을 추가한다.

## 도움말 정리 및 관리자 인증 동기화 (2026-08-30)

- 별도 도움말 화면과 홈의 `도움말·FAQ / 도구 설치 / GitHub` 중복 바로가기 묶음을 제거한다. 기존 `/help`, `/help.html` 주소는 홈으로 되돌린다.
- 관리자 로그인 화면의 도움말 버튼도 제거한다.
- 관리자 비밀번호는 최초 기동 후 `ADMIN_AUTH_FILE`의 해시가 우선하므로 `.env`의 `ADMIN_INITIAL_PASSWORD`만 바꾸면 기존 개발·운영 환경의 로그인이 바뀌지 않는다.
- 개발·운영에서 같은 관리자 계정을 유지하려면 두 환경의 `.env`에 같은 `ADMIN_ID`, `ADMIN_INITIAL_PASSWORD`와 `ADMIN_CREDENTIALS_SYNC=true`를 설정하고 각 서버를 재시작한다. 이때 각 환경의 인증 파일 해시만 동기화하며, 점검 데이터 경로는 계속 분리한다.
- 운영 서버 설정 변경은 개발 클론에서 수행하지 않는다. 운영 배포 절차에서 운영 `.env`를 같은 값으로 설정한 뒤 서비스 재시작과 로그인 검증을 수행한다.

## 관리자 이력·대시보드 필터 보정 (2026-08-30)

- 관리자 요약 카드의 상태 조건은 다른 필터를 남기지 않고 즉시 조회한다. `초기화`는 검색어·기간·결과·생태계·개발언어·화이트리스트 조건을 한 번에 해제한다.
- 필터 영역은 라벨과 값이 분명히 보이는 세로 입력형으로 정리하고, 현재 적용 조건과 표시 건수를 함께 보여 준다.
- 날짜 필터와 `오늘 점검` 집계는 서버·브라우저 모두 `Asia/Seoul` 기준으로 계산한다. UTC 자정 경계 때문에 한국 시간의 오늘 이력이 누락되는 것을 금지한다.
- 월별 점검 그래프는 전체 너비를 사용하고, 개발언어·패키지 분포는 그 아래 큰 두 영역에 표시한다. 0건 조건에서는 평평한 0선 대신 빈 상태를 명확히 표시한다.
- `확인 필요` 집계와 필터는 `needs_review`뿐 아니라 점검 실패·미완료의 `incomplete`도 함께 표시한다. 미완료 이력을 `사람 검토 0건` 뒤에 숨기지 않는다.

## 확인 계약

- `PORTAL_REPORT_RETENTION_DAYS`의 기본값은 90일이며, 만료 보고서는 기동 시와 6시간 주기로 삭제한다.
- `scripts/portal-scenario-test.mjs`의 보존 시나리오는 만료 보고서 삭제, 유효 보고서 유지, 점검 이력 유지, 패키지·정확 버전 통계 유지를 함께 확인한다.
- 보존 정책을 수정할 때는 `PORTAL_REPORT_DIR` 정리 코드가 `PORTAL_SCAN_HISTORY_FILE`, `PORTAL_OBSERVATION_DIR`, 화이트리스트 저장소를 건드리지 않는지 반드시 검토한다.

## Codex·Claude Code 교차 검증 절차

1. 개발 클론 `C:\coding\vibecode-security-gate-portal`에서만 작업하고, 시작 전에 `git pull --ff-only`를 실행한다.
2. [23_서버_API_계약.md](23_서버_API_계약.md)와 이 문서를 읽고 보관 경계를 유지한다.
3. 변경 후 `npm run check`, `npm run scenario:test`, `npm run button:test`, `npm run security:scan`을 실행한다.
4. 화면 변경은 `npm start` 후 개발 주소에서 점검 결과, 제출, 관리자 필터와 그래프를 확인한다.
5. 커밋 전 `git diff --check`와 `git status --short`로 의도하지 않은 변경을 분리한다.

## Git 및 배포 경계

- 커밋은 개발 클론의 로컬 Git 이력에 남긴다.
- 푸시는 `origin` 원격 저장소인 `https://github.com/Lex6won/vibecode-security-gate-portal.git`의 `main` 브랜치로 보낸다.
- 푸시는 운영 배포가 아니다. 배포는 별도 절차인 pull, 검증, 태그, 운영 서버 반영으로 진행한다.

## 관리자 실데이터 대시보드 정리 (2026-08-30)

- 일반 사용자 홈에서는 `관리자` 진입 버튼과 관리자 기능 카드를 제거한다. 관리자 URL과 인증 기능은 유지하되, 일반 사용자 화면에서 관리자 기능을 노출하지 않는다.
- 관리자 화면의 초기 예시 수치·가상 이력·가상 대상명은 제거한다. API 응답 전에는 `불러오는 중`, 응답 실패 시에는 오류 상태만 표시하며, 실제처럼 보이는 임시 데이터를 표시하지 않는다.
- 개발언어 원그래프는 각 점검 이력의 `summary.language_counts`를 합산한다. 값은 체커가 실제 분석한 **소스 파일 수**이며, GitHub 언어 막대의 바이트 비율과 같은 지표라고 표현하지 않는다.
- 언어별 API 항목에는 `file_count`와 `target_count`를 함께 제공한다. 관리자는 차트 조각·범례·월별 그래프의 점을 클릭하거나 키보드로 선택해 해당 실제 수치를 확인할 수 있다.
- 패키지 원그래프는 보안성검토 자료 제출 시 축적되는 패키지 관측값과 버전 목록만 사용한다. 이 데이터는 `observations/package-observations.jsonl`, `observations/package-usage-stats.json`에 별도로 보관된다.
- 점검 이력·개발언어 통계는 별도 관계형 통계 테이블이 아니라 `scan-history.jsonl`의 점검별 요약값으로 계산한다. 제출 보고서 원본이 90일 뒤 삭제되어도 이력 요약과 패키지 관측 통계는 유지된다.
- 기존 개발 데이터에 포함된 수동 검증·테스트 점검 이력은 감사 이력이므로 자동 삭제하지 않는다. 운영 통계와 분리해야 할 경우 점검을 생성할 때부터 개발·운영 구분값을 저장하는 별도 정책을 추가한다.
- 차트 캔버스·상세값·범례를 각각 독립된 그리드 행으로 배치하고, 카드·이력·상세 대상명은 줄바꿈할 수 있게 해 긴 저장소명이나 버전 정보가 다음 영역을 덮지 않게 한다.

## 저장 위치·내 점검 이력·개발 기본 소속 보정 (2026-08-30)

- 브라우저의 `showDirectoryPicker()`는 Windows 탐색기를 여는 API가 아니라 저장할 폴더를 고르는 API다. 이를 `저장 폴더 열기`로 표기해 빈 폴더 선택 창이 다시 뜨던 버튼을 제거했다. 제출 완료 후에는 `확인하고 마치기`만 제공하고, 제출자료는 처음 선택한 폴더에 저장한 뒤 내 점검 이력에서 다시 확인한다.
- 폴더 저장은 HTML, JSON, Markdown, 제출자료와 함께 생성된 SBOM까지 모두 저장한다. 브라우저 보안 정책상 웹페이지가 임의의 Windows 폴더를 직접 열 수는 없다.
- 내 점검 이력은 Git 저장소·폴더·압축파일의 대상명을 우선 표시하고, 산출물은 `결과 리포트`, `패키지 목록·점검 데이터`, `소프트웨어 명세서`, `보안성검토 요청서`, `보안성검토 제출자료 ZIP`으로 표시한다. 보안성검토 요청 전 임시 산출물도 이력에서 바로 볼 수 있다.
- 새 Git 점검은 `호스트/그룹/저장소` 형식의 읽기 쉬운 대상을 저장하며, 로컬 경로는 이력에 보관하지 않는다.
- 개발 자동 로그인은 더 이상 `개발 검증 / 보안점검`을 실제 소속처럼 채우지 않는다. 기존 개발 자동 계정에 정확히 이 임시값만 저장된 경우 빈 값으로 1회 정리하고, 다음 점검 전 실제 기관명·부서명을 입력받는다. 이미 생성된 점검 이력의 소속 스냅샷은 변경하지 않는다.
