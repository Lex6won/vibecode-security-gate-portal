체커는 두 곳에서 돕니다 — 같은 체커, 같은 규칙

① 공무원 PC 안에서 — 만드는 중에

  • 하네스가 AI 도구에 체커를 붙여 둡니다(MCP)
  • AI가 패키지를 깔려 하면 하네스가 체커에게 물어봅니다
  • 체커가 답하면 하네스가 막거나·경고하거나·통과시킵니다
  • 포털은 이 경로에 없습니다 — PC 안에서 끝납니다

② 포털 서버에서 — 다 만든 뒤에

  • 공무원이 폴더를 웹으로 올립니다
  • 포털이 서버의 체커를 실행합니다
  • 체커가 검사하고 보고서를 만듭니다
  • 포털은 그 보고서 위치를 알려 줄 뿐입니다

그래서 결과가 어긋나지 않습니다

두 경로가 같은 체커·같은 규칙을 씁니다. "만들 때는 괜찮다더니 올리니까 걸린다"가 생기지 않습니다. 체커 버전이 벌어지면 그 약속이 깨지므로, 포털이 최신 버전을 알려 주고 관리자 화면에 서버 체커 버전을 띄웁니다.

화이트리스트가 쌓이면 무엇이 달라지는가

하네스가 묻는 곳은 바뀌지 않습니다. 언제나 체커에게 묻습니다. 달라지는 것은 체커가 주는 답입니다 — 화이트리스트를 조회해 자기 검사 결과와 합쳐서 주기 때문입니다.

지금 — 화이트리스트가 아직 없을 때

  • 하네스가 체커에게 묻는다
  • 체커가 답한다 — checked_clean · vulnerable · unknown
  • 기관이 정한 것이 없으니 판단 근거가 검사 결과뿐
  • 공무원 체감 — "이거 써도 되나요?"를 자주 묻게 됨

나중 — 화이트리스트가 쓸 만해진 뒤

  • 하네스가 여전히 체커에게 묻는다 (안 바뀜)
  • 체커가 화이트리스트까지 조회해 합친 답을 준다 — registry_approved · registry_rejected가 붙는다
  • 기관이 정한 것이 있으니 대부분 즉시 통과
  • 공무원 체감 — 막히는 일이 줄고 물어볼 일도 줄어듦

화이트리스트에 있다고 검사를 건너뛰지는 않습니다

하네스가 화이트리스트만 보고 통과시키면 두 가지를 놓칩니다. ① 목록에 올린 뒤 새로 뜬 취약점(어제 긴급 취약점이 등재됐어도 목록은 그대로입니다). ② 로컬에서만 보이는 악성 신호(이름을 흉내 낸 가짜, 내 PC에서 변조된 것 — 목록으로는 알 수 없습니다).

그래서 체커의 판정 순서에서 악성 탐지가 기관 승인보다 위에 있습니다. 승인된 패키지라도 악성 신호가 뜨면 그것이 이깁니다.

행정망에서도 같습니다

행정망은 실시간 조회가 안 되므로 화이트리스트를 파일로 반입해 체커가 로컬에서 참조합니다. 그래도 하네스 → 체커 경로는 그대로입니다. 반입본이 낡으면 체커가 "낡은 근거"라고 밝히고, 오래되면 신규 배포가 자동으로 멈춥니다.

구현할 때 어기기 쉬운 경계 다섯

1 · 포털이 판정을 관대한 쪽으로 바꾸는 것

포털은 체커 판정을 더 안전한 쪽으로만 덮어쓸 수 있습니다. 검사가 잘렸을 때 "통과"를 "여기까지만 봄"으로 낮추는 것은 됩니다. 반대로 체커가 "확인 필요"라 한 것을 포털이 "통과"로 올리는 것은 절대 안 됩니다. 강화는 자동, 완화는 사람입니다.

2 · 하네스가 체커를 건너뛰는 것

하네스가 승인 목록만 보고 통과시키면 로컬 악성 탐지와 긴급 취약점 대조가 빠집니다. 하네스는 반드시 체커에게 물어보고 그 답으로 집행합니다.

3 · "확인 못 함"을 "안전"으로 바꾸는 것

조회 실패·검사 미완·대조 불가는 전부 "모른다"입니다. 어느 화면에서도 초록불로 바꾸지 않습니다. 특히 기관이 승인한 패키지라도 로컬에서 악성 신호가 뜨면 그것을 가리지 않습니다.

4 · 포털이 보고서를 다시 만드는 것

보고서는 체커가 만든 파일 그대로 전달합니다. 포털이 예쁘게 다시 그리면 결재 문서와 검사 증거가 갈라집니다.

5 · 감지·설정 변경 로직을 두 곳에 두는 것

도구 감지와 설정 파일 수정은 하네스에만 둡니다. 도구 관리자에 또 만들면 규칙이 갈라져 어느 쪽이 맞는지 알 수 없게 됩니다.

핵심 — 탐색기는 누가 띄우는가

탐색기는 브라우저가 사용자 PC에서 띄웁니다. 서버는 관여하지 않습니다. 그래서 서버에 올려도 공무원이 보는 화면은 지금과 똑같습니다. 서버가 직접 탐색기를 띄우는 것은 불가능하고, 시도하면 서버 콘솔에 대화상자가 떠서 아무도 누를 수 없게 됩니다 — 현재 코드의 PowerShell 방식이 정확히 그 문제라 걷어냅니다.

달라지는 것 하나

브라우저는 전체 경로(C:\Users\…)를 알려주지 않습니다. 폴더 안 상대 경로만 줍니다. 이건 제약이 아니라 이점입니다 — 어차피 전체 경로는 저장하지 않는다는 원칙이 있어서, 브라우저가 알아서 지켜 주는 셈입니다.

그래서 버전 확인·업데이트·설정 변경은 PC에 설치된 프로그램이 합니다 — 다음 화면.

"고르기"가 아니라 "안내"입니다

누가 실제로 PC를 바꾸는가 — 세 층

감지와 설정 변경 로직을 도구 관리자에 또 만들지 않습니다. 두 곳에 두면 규칙이 갈라집니다. 하네스팀 소관으로 둡니다.

설치 결과를 서버에 알려 줍니다

왜 부서 수로 줄 세우는가

같은 라이브러리라도 한 부서가 20번 쓴 것보다 일곱 부서가 한 번씩 쓴 것이 먼저입니다. 후자를 승인하면 더 많은 사람의 대기가 풀립니다.

개정(08-24) — 화이트리스트를 포털에서 관리합니다

이전에는 "내보내기까지만"이었으나, 관리자(보안담당)가 이 화면에서 화이트리스트에 담고·빼고·저장하는 것까지로 범위를 넓혔습니다. 저장된 파일이 기본 이미지에 반영됩니다.

경계는 유지됩니다 — 관리자는 보안담당의 별도 계정이므로 "검사한 쪽이 스스로 승인"하는 구조가 아니고, 일반 공무원 화면에는 어떤 판정 버튼도 없으며, 모든 담기·제외는 누가 언제 왜가 감사 기록에 남습니다.

"딸려 옴"

직접 고른 것이 아니라 다른 라이브러리가 끌고 들어온 것입니다(전이 의존성). 실측하면 검사 1회 188개 중 148개가 딸려 온 것이고, 실제 위험도 대부분 여기서 나옵니다. 그래서 기록은 전부 남기되, 사람이 볼 심사 대기열에는 직접 선언한 것만 올립니다. 다 올리면 담당자가 감당하지 못합니다.

탐색기는 어떻게 뜨는가

서버로 옮기면 파일 선택이 안 되는 것 아니냐는 질문에 대한 답입니다. 결론부터: 화면은 똑같고, 뒤에서 오가는 것만 달라집니다.

지금 (로컬 방식)

  • 서버(내 PC)가 PowerShell로 탐색기를 띄움
  • 돌려받는 것: 전체 경로 C:\작업\민원도우미
  • 그 경로를 그 자리에서 검사 — 전송 없음
  • 서버에 올리면 망가짐 — 대화상자가 서버 콘솔에 떠서 아무도 못 누름

앞으로 (서버 방식)

  • 브라우저가 사용자 PC에서 탐색기를 띄움
  • 돌려받는 것: 파일 내용과 상대 경로 민원도우미/app.py
  • 서버로 올려서 검사하고 즉시 삭제
  • 공무원이 보는 화면은 지금과 같음 — 올리는 시간만 추가
세 가지 방식 직접 확인실제 동작

브라우저가 실제로 무엇을 주는지 보십시오. 아무것도 전송하지 않습니다.

위 버튼을 누르면 윈도우 탐색기가 열립니다.

폴더 선택

<input type="file" webkitdirectory> — 윈도우 탐색기의 폴더 선택 창이 뜹니다. 하위 폴더까지 전부 딸려 옵니다. 크롬·엣지·파이어폭스 모두 됩니다.

압축파일 선택

<input type="file" accept=".zip"> — 일반 파일 선택 창이 뜨고 ZIP만 보입니다. 서버가 풀기 전에 크기·압축비·경로를 먼저 검사해서 압축폭탄과 경로 탈출을 막습니다.

GitHub 주소

사용자 PC는 관여하지 않습니다. 서버가 직접 내려받아 검사합니다. 포털 서버가 인터넷망에 있어서 가능합니다. 주소는 https://github.com/… 형식만 받습니다.

끌어다 놓기도 됩니다

탐색기에서 폴더를 끌어다 놓는 방식이 실제로는 더 많이 쓰입니다. 버튼과 함께 넣습니다.

이 문서는 설계 확정용입니다. 화면은 확정 전 시안이며, 문구·배치는 검토 의견에 따라 바뀝니다. 데이터는 실제 체커 산출물 구조(gvskb-registry-bundle/1)와 실측값에 맞췄습니다.

2026-08-13 확정 — ① 도구 설치는 도구 관리자(PC 프로그램) 방식으로 간다. 웹은 안내·지원 범위 표시·설치 파일 배포·상태 표시까지, 버전 비교와 업데이트는 도구 관리자가, 실제 도구 감지와 설정 변경은 하네스가 한다(하네스팀 협의 반영, 3층 분리). 기존 로컬 포털 코드를 옮겨 재활용한다. ② 관리자 화면에 승인·차단 버튼은 만들지 않는다. 보안담당자가 화이트리스트를 만들고 기본 이미지를 굽도록 지원하는 데까지가 범위다.

2026-08-24 확정 — ① 일반 공무원은 기관 메일 가입 + 기관·부서 선택으로 이용(통합인증 확정 전 임시 경로, 도메인 제한). 관리자는 별도 계정으로 /admin 로그인. ② 점검 후 결과 제출은 opt-in 버튼 — 라이브러리 메타값만 제출되어 화이트리스트 후보가 된다. ③ 보안성 검토 요청 신설 — 요청은 관리자 대기열로, 진행 상태는 내 이력에 표시. ④ 08-13의 "승인 버튼 없음"을 갱신 — 관리자(보안담당)가 포털에서 화이트리스트를 담고·빼고·저장한다(감사 기록 필수). 저장 파일이 기본 이미지에 반영된다.
