## 1. 서비스명

공공 코드 보안검사 게이트

가칭: `VibeCode Security Gate`

## 2. 목적

공무원이 AI 코딩 도구로 만든 소스코드나 GitHub 저장소를 제출하기 전에, 보안 위험과 의존성 위험을 스스로 확인하고 제출 가능한 점검 증거물을 만들 수 있게 한다.

이 서비스의 목적은 “개발자를 벌주는 검사기”가 아니라, 공무원이 무엇을 고쳐야 하는지 이해하고 보안팀 또는 AX 담당자에게 설명 가능한 자료를 준비하도록 돕는 것이다.

## 2-1. 1차 범위 결정

1차 제품은 웹 UI 기반 로컬 웹앱과 Python 기반 체커 엔진으로 한정한다. 필요하면 같은 구조를 데스크톱 앱으로 포장한다.

1차 포함:

- 웹 UI 기반 로컬 웹앱
- 선택적 데스크톱 앱 포장
- Python 기반 `vibecode-checker/gvskb` 엔진 호출
- 공공 하네스 감지, 설치, 검증
- 로컬 폴더 검사
- 압축파일 검사
- 공개 GitHub URL 검사
- 개발 중 간편 점검, 개발 완료 표준 점검 선택
- 체커 원본 HTML, JSON, Markdown 리포트 다운로드
- 체커 엔진, 룰셋, 인텔 데이터 상태 표시
- GitHub, OSV, PyPI, npm 연결 진단
- Codex, Claude Code용 체커 MCP 기본 등록과 연결 검증
- 하네스와 체커 설치 상태 확인, 업데이트 미리보기

1차 제외:

- LLM API 기반 설명 생성
- MCP 고급 자동복구와 기관 일괄 배포
- 중앙 기관 웹 포털
- 관리자 승인 워크플로
- 보안팀 검토 큐
- 자동 수정
- 공식 보안 승인 처리

LLM API는 필수 구성요소가 아니다. 1차 제품은 LLM 없이 동작해야 하며, 보안 판정과 제출 evidence는 체커 원본 결과만 기준으로 한다.

Node.js는 체커 실행을 위한 필수 조건이 아니다. Node 프로젝트를 검사할 수는 있어야 하지만, 검사 도구 자체는 Python 엔진만으로 실행 가능해야 한다.

하네스 자동 설치는 선택 기능이다. 보안검사를 실행하기 위한 필수 조건으로 만들지 않는다. 다만 개발 중 점검을 돕기 위해 하네스 설치, 체커 MCP 등록, 연결 검증을 한 화면에서 제공한다.

## 6. 입력 데이터

- (필수) 로컬 소스 폴더 / `.zip` 등 압축 소스 /  GitHub 저장소 URL (중 선택)
- (선택) 브랜치, 커밋 SHA, 토큰이 필요 없는 공개 저장소 우선
- (필수) 프로젝트 이름
- (선택) 하네스 설치 위치
- (필수) 사용 목적: 내부도구, 대민서비스, MCP, 자동화, 데이터 처리
- 운영 예정 위치: 개인 PC, 내부망, DMZ, 공개 인터넷 시제품
- 개인정보 포함 가능성
- 제출 목적 여부

민감정보 입력은 최소화한다. GitHub 개인 토큰, 업무망 계정, 비밀번호는 검사 설정에 직접 저장하지 않는다.

## 7. 출력 결과

출력 결과는 체커 원본 산출물과 서비스 보조 산출물로 분리한다. 보안 판정의 원천은 반드시 `vibecode-checker/gvskb`가 만든 원본 리포트와 JSON evidence여야 한다.

### 7-1. 체커가 현재 제공하는 원본 산출물

CLI 기준:

- `markdown`
- `html`
- `json`
- `sarif`

MCP `render_report/save_report` 기준:

- `markdown`: 텍스트 검토, 협업, 이력 관리용
- `html`: 사람이 열람하고 인쇄/PDF 제출하기 쉬운 보고서
- `json`: 자동화와 재검증을 위한 원본 증거 데이터

MCP 저장 규약:

- 기본 저장 위치: `<검사한 프로젝트>/.check-reports/`
- 기본 저장 파일: `YYYY-MM-DD_HHMM_보안점검.{md,html,json}`
- 서비스는 체커가 반환한 `saved.markdown`, `saved.html`, `saved.json` 경로를 그대로 사용한다.
- 서비스나 AI 에이전트가 원본 리포트를 임의 위치와 임의 이름으로 다시 저장하지 않는다.

### 7-2. 서비스 화면에서 보여줄 결과

서비스 화면은 체커 원본 데이터를 보기 쉽게 요약한다. 이 요약은 원본 리포트를 대체하지 않는다.

- 검사 상태: 제출 가능, 수정 필요, 사람 검토 필요, 검사 미완료
- 검사 범위: 소스, 의존성, 설치 패키지, vendor bundle 검사 여부
- 수정 필요 항목 목록
- 사람 검토 필요 항목 목록
- 오탐 후보 목록
- 의존성 취약점 및 공급망 위험 목록
- 검사 미완료 사유
- 다운로드 가능한 체커 원본 리포트 경로

### 7-3. 서비스가 제공하는 보조 산출물

추가 제공물은 제출 편의와 업무 흐름을 위한 보조 산출물로 한정한다. 체커 원본 판정을 새로 해석하거나 대체하지 않는다.

- 검사 manifest: 검사 대상, 실행 모드, 체커 버전, 리포트 경로, 파일 hash를 담은 서비스 관리용 파일
- 재검사 체크리스트: 수정 후 다시 확인해야 할 항목 목록
- 선택 출력: SARIF 파일. CI 또는 GitHub code scanning 연동이 필요한 경우에만 제공한다.

기본 제출 산출물:

1. 체커가 저장한 HTML 보고서
2. 체커가 저장한 JSON evidence

선택 산출물:

- Markdown 보고서
- SARIF

이 산출물들은 공식 승인서가 아니라 보안팀 또는 AX 담당자가 검토하기 위한 증거물이다.

## 8. 개인정보 여부

- [ ] 없음
- [x] 가능성 있음
- [ ] 있음

사용자가 검사하는 소스에는 샘플 주민등록번호, 전화번호, API 키, 내부 IP, 운영 DB 접속 문자열이 포함될 수 있다. 기본 설계는 로컬 검사 우선이며, 웹 포털형으로 확장하더라도 원본 소스 저장은 기본 비활성화한다.

필수 원칙:

- 원본 소스는 기본적으로 사용자 PC에서 검사
- 서버 업로드 검사는 기관 정책 승인 후 제공
- 보고서에는 실제 비밀값을 마스킹
- 결과 보고서에는 원본 소스를 포함하지 않음

## 9. 외부통신 여부

필요 가능성이 있는 외부통신:

- GitHub 저장소 clone 또는 release 다운로드
- OSV, EPSS, PyPI, npm 취약점 및 패키지 정보 조회
- 체커 엔진, 룰셋, 인텔 데이터 업데이트
- 하네스 공식 저장소 또는 검증된 릴리스 다운로드

LLM API 외부통신은 1차 범위에 포함하지 않는다. 향후 도입하더라도 기관 승인 경로에서 결과 설명 보조 기능으로만 사용하고, 보안 판정에는 사용하지 않는다.

권장 방식:

- 개발 PC 또는 내부망에서 허용 도메인 기반 방화벽 정책 적용
- 운영 중 자동 업데이트는 서명된 안정 릴리스 또는 승인된 업데이트 매니페스트만 반영
- `main` 브랜치 직접 추적 금지
- 네트워크 실패 시 검사 미완료 또는 제한 검사로 명확히 표시

## 10. 성공 기준

- 개발 경험이 적은 공무원이 첫 화면에서 1분 안에 검사 대상을 넣고 검사를 시작할 수 있다.
- 처음 들어온 사용자가 별도 매뉴얼 없이 대시보드 안에서 서비스 목적, 입력 방법, 결과 확인 방법을 이해할 수 있다.
- 검사 결과가 “무엇을 고쳐야 하는지”, “무엇은 사람 검토가 필요한지”, “무엇은 오탐 가능성이 있는지”로 분리된다.
- 표준 점검은 소스와 의존성 검사 범위 누락 여부를 스스로 검증한다.
- 발견 0건이어도 검사 범위가 불완전하면 제출 가능으로 표시하지 않는다.
- 보고서에는 체커 버전, 룰셋 버전, 인텔 기준시각, 검사 대상 commit 또는 해시가 남는다.
- 체커 업데이트는 재설치를 전제로 하지 않고 앱 내부 업데이트 또는 MCP 재시작으로 반영된다.
- 하네스 설치와 업데이트는 공식 저장소 또는 검증된 릴리스를 기준으로 하며, 설치 후 검증 스크립트를 통과해야 한다.
- 위험한 변경은 적대적 회귀 검증과 최종 재점검 없이는 안정 채널에 배포되지 않는다.

## 보강: 제품 관점과 UX 핵심

하네스는 설계, 구현, 테스트, 검증, 배포지원을 포괄한다. 따라서 이 서비스는 단순 보안검사 게이트가 아니라 공무원이 하네스를 쉽게 시작하도록 돕는 진입점이어야 한다.

1차 대시보드는 다음 세 가지 작업을 쉽게 구분해서 보여준다.

1. 보안검사만 하기
2. 하네스로 개발 시작
3. 기존 프로젝트 이어가기

사용자는 첫 화면에서 이 서비스가 무엇을 해주는지, 하네스로 무엇을 할 수 있는지, 내가 지금 무엇을 눌러야 하는지를 바로 이해해야 한다. 기능 신뢰성은 기본이고, 사용자 이해 가능성이 핵심 UX 기준이다.
