## 1. 포털 — 배포 판정을 체커 `gate.verdict` 기준으로 (①)

### 무엇이 문제였나

포털은 존재하지 않는 `report.decision` 을 읽고, 없으면 `summary.blocked` 로
폴백했다. `summary.blocked` 는 **소스 발견만** 보는 옛 필드다(체커
`gate.py` 가 "이 값을 판정으로 쓰지 말라"고 명시). 결과가 양방향으로 뒤집혔다.

수정 전 로직을 그대로 재현해 같은 입력을 넣어본 결과:

```
시나리오                              체커 gate      수정 전 포털   기대값
------------------------------------------------------------------------
코드 정상 + 패키지 CRITICAL           blocked        allow          blocked
소스 block 발견 + 패키지 정상         conditional    blocked        needs_review
gate 없는 구버전 결과                 (없음)         allow          incomplete
```

### 어떻게 고쳤나

판정 로직을 [src/scan-summary.mjs](../src/scan-summary.mjs)의 순수 함수
`scanDecision(report, {mode, timedOut})` 으로 분리하고, 서버는 그 결과를 옮겨
적기만 한다. 매핑은 한 표에만 있다.

| 체커 `gate.verdict` | 포털 decision |
|---|---|
| `blocked` | `blocked` |
| `conditional` | `needs_review` (화면 표기: 조건부 승인) |
| `undetermined` | `incomplete` |
| `approved` | `allow` (간편점검이면 `quick_complete`) |
| 없음 · 모르는 값 | **`incomplete`** (fail-safe) |

검사가 온전하지 않으면(시간초과 · 프로파일 폴백 · 범위 절단 · 의존성 미완)
`gate` 보다 먼저 `incomplete` 로 간다. 판정 불가는 안전이 아니다.

### 과거 기록은 건드리지 않는다

새 판정에는 `decision_source: "gate_v1"` 을 찍고, 이력 파일에서 불러온 기록에
그 값이 없으면 메모리에서만 `"legacy"` 를 붙인다. **저장된 `decision` 은 재계산
하지 않는다** — 이미 결재가 끝난 점검을 소급해 뒤집지 않기 위해서다.
`loadScanHistory` 는 원래도 `decision` 을 재계산하지 않았고(의존성 요약만
보정), 그 성질을 그대로 유지했다.

### 회귀 테스트

[scripts/checker-contract-test.mjs](../scripts/checker-contract-test.mjs) 신설,
`npm run check` 에 포함. 24개 단언으로 위 표 전체 + fail-safe + 범위 절단
구조화/문장 폴백 + 면제·엔진 상태 파싱을 고정한다.

## 2. 포털 — E3 자동 판정 거부 (②)

### 무엇이 문제였나

체커는 E3 를 **의도적으로 지원하지 않는다** — MCP 도구 정의에 "E3(대민·개인
정보)는 바이브코딩 대상이 아니므로 받지 않음"이라고 적혀 있고, CLI `--env` 도
E0~E2 로 제한한다. 그런데 포털 패키지 게이트는 CLI·MCP 가 아니라
`from gvskb.tools.check_package import audit_manifest` 로 **함수를 직접
호출**해 두 경계를 모두 지나쳤다. 그 결과:

- 체커는 모르는 등급을 조용히 기본값(E1, 개인 PC)으로 바꿔 쿨다운을 적용하고
- 결과 최상위에는 전달받은 `"E3"` 를 그대로 적었다

→ 한 문서 안에서 **"E3 로 점검함"과 "E1 쿨다운 적용"이 공존**했다. 대민 서비스를
개인 PC 기준으로 검사해 놓고 기록만 대민으로 남는 상태다.

또한 이 저장소의 정책 문서에는 이미 규칙이 있었으나 집행부에 구현이 없었다:

> [shared/institution-profile.yaml:46](../shared/institution-profile.yaml)
> `"E2/E3 package auto-approval is not allowed; human/platform review is required."`

### 어떻게 고쳤나

[shared/enforcement/gvskb_gate.py](../shared/enforcement/gvskb_gate.py)에
`env_grade_block()` 을 두고 `check` · `install` · `verify-manifest` 세 명령
**전부**에서 체커 호출 **전에** 검사한다. E3 및 미상 등급이면 체커에 묻지 않고
`action: "block"`, `checker_verdict: "unsupported_env_grade"`,
`requires_human_review: true` 로 돌려주며, 사유에 다음 행동(패키지검토요청서 →
보안담당자 심사)을 함께 적는다.

`resolve_env_grade()` 로 대소문자·공백을 정규화한다 — `"e2"` 가 목록에 없는
값으로 취급돼 조용히 E1 이 되던 구멍을 막는다.

JS 래퍼([gvskb_gate.js](../shared/enforcement/gvskb_gate.js))는 `--env-grade`
값을 대문자로 정규화만 하고 **판단은 하지 않는다**. 정책을 두 언어에 복제하면
갈라지기 때문이다(이 프로젝트가 institution-profile 이중화로 이미 겪은 문제).

### ⚠ 검토자에게 묻는 결정 사항

`gvskb_gate.py` 는 Python 이라 **실행 검증을 하지 못했다.** 아래 두 가지를
검토해 달라.

1. **E2 는 손대지 않았다.** 정책 문서는 "E2/E3 자동승인 금지"라고 하지만,
   `default_env_grade()` 는 CI 환경에서 E2 를 기본값으로 돌려준다. E2 를
   자동 통과 불가로 만들면 **현재 CI 가 전부 막힌다.** 정책 문장의 "package
   auto-approval" 이 *패키지 예외 승인*을 뜻하는지 *모든 패키지 통과*를 뜻하는지
   확정이 필요하다. 확정 전까지는 E3 만 막는 것이 안전하다고 판단했다.
2. `GVSKB_GATE_ENV_GRADE` 환경변수로 E3 를 넣는 경로도 같은 가드를 지나간다
   (`default_env_grade` → `resolve_env_grade` → `env_grade_block`). 의도한 대로인지 확인 바람.

| 행 | 내용 | 왜 |
|---|---|---|
| 판정 근거 | 체커 원본 판정 · 재점검 사유 · 엔진/룰셋 버전 · 소스 커밋 | 무엇을 근거로 한 결론인지 |
| 검사 범위 | 파일 수 · 절단/판정불가/프로파일 미적용 경고 | "이상 없음"의 범위가 어디까지인지 |
| 면제 처리 | 승인된 예외 N건 · **주석 무시 N건** · 만료/무효 | 지적을 끄고 통과한 흔적이 보이게 |
| 검사 엔진 | 수행 · 미수행 · 실패 | 판정의 깊이. 목록 없으면 '미상' |

면제에서 **승인된 예외와 인라인 주석을 나눠 적는다.** 전자는 승인자·사유·만료가

구분이 사라진다.

체커가 아직 집계를 주지 않는 항목은 `0` 이 아니라 **'미상'** 으로 적는다 —
"없음"과 "모름"은 다르다.

### 7.1 JS 인라인 무시 우회 (Critical) — 1차 수정이 만든 퇴행

코덱스가 실행해 재현한 사례:

```js
eval(user); const s = 'http://example/gvskb: ignore'   // → 탐지 0건
eval(user);                                             // → 탐지됨
```

1차 수정의 `_comment_start` 가 `line.find("//")` 로 주석 시작을 찾아, **문자열
안의 `http://`** 를 주석으로 오인했다. 검사 대상 코드가 자기 검사를 끌 수 있는
상태였고, 이 도구가 검사하는 것이 대개 남이 쓴 코드라는 점에서 게이트로서
성립하지 않는다.

**1차 인계서에서 이 위험을 적어 두고도 "무시를 놓치는 쪽보다 낫다"고 판단했는데,
그 판단이 틀렸다.** 보안 도구에서 할 저울질이 아니었다.

수정: 따옴표와 이스케이프를 추적하는 문자열 인식 스캐너로 교체했다. 그리고
**세 엔진의 중복 구현을 한 곳으로 모았다** — `js_taint` 와 `ast_scanner` 는 각자
`_IGNORE_RE.search(line)` 를 써서 주석 여부를 **전혀** 보지 않았고(이건 1차 수정
이전부터의 결함), 그래서 코덱스가 지적한 regex 엔진만 고쳤다면 우회가 그대로
남았을 것이다. 이제 `regex_scanner.line_ignores_rule()` 한 곳에서만 판정한다.

회귀 테스트 7건 추가 — 코덱스의 재현 사례 그대로 + 큰따옴표·템플릿 리터럴·
이스케이프 변형 + **반대 방향**(URL 이 있어도 진짜 주석은 계속 동작) + 세 엔진 각각.

남은 한계(주석에 명시): 정규식 리터럴(`/\/\//`)은 추적하지 않는다. 공격자가 코드
위치에 정규식을 두어야 해서 실익이 없고, 완전한 JS 렉서 비용이 더 크다고 보았다.

### 7.2 E2 자동승인 금지 (Critical) — A안 채택

사업 담당자 결정: **정책대로 막는다.**

E2 는 E3 와 다르게 처리한다 — E3 는 체커가 판정 자체를 못 하므로 검사 없이
거부하지만, **E2 는 검사를 정상 수행하고 결과가 깨끗하더라도 자동 설치만 막는다.**
"위험해서 차단"이 아니라 "절차상 사람 확인"이므로 안내 문구도 분리했다
(`requires_human_review` 필드 + 전용 안내문).

`install` 경로는 `action == "block"` **또는** `requires_human_review` 중 하나만
걸려도 설치하지 않는다(이중 잠금 — 판정 매핑이 바뀌어도 절차 요건이 조용히
통과되지 않게).

**예외 — 이미 사람 검토를 거친 경우**: 기관 승인 목록(`local_approved`)에 있거나
체커가 `registry_approved` 를 돌려주면 통과시킨다. 그 승인이 곧 사람 검토
결과이고, 여기서 또 막으면 승인 목록이 무의미해져 게이트가 우회된다. 이는 같은
정책 문서의 다른 규칙과 앞뒤를 맞추기 위한 해석이다:

> `harness-enforcement-contract.yaml` (local_catalog_and_registry_priority)
> "If local allow and checker returns registry_approved/checked_clean, pass."

**이 해석이 맞는지 검토해 달라.** 틀렸다면 `PRIOR_REVIEW_CATALOG_STATUSES` 를
비우면 된다.

### 7.3 npm 게이트 래퍼 (Important)

`gvskb_gate.js` 가 `"type": "module"` 인 저장소에서 `require()` 를 써서 **실행 즉시
죽고 있었다.** AGENTS.md 는 npm 패키지 추가 시 이 스크립트를 거치라고 안내하므로,
**npm 쪽 패키지 게이트가 한 번도 동작한 적이 없다.** 1차 수정과 무관한 기존
결함이지만, 그 파일을 건드리면서 실행해 보지 않은 것은 이쪽 책임이다.

ESM 으로 전환(`import` + `fileURLToPath(import.meta.url)`)했고,
[scripts/package-gate-smoke-test.mjs](../scripts/package-gate-smoke-test.mjs) 를
`npm run check` 에 넣었다. `node --check` 는 이 결함을 못 잡는다 — 모듈 로딩은
런타임 실패라, 실제로 프로세스를 띄워야 한다.

### 7.4 체커 E3 즉시 거부 (Important)

1차 수정은 E1 로 계산한 뒤 "검토 필요"를 붙였다. 코덱스 지적대로 방어가 약하다 —
그 수치가 이 업무의 기준인 것처럼 읽힌다. 이제 `check_package_impl` 과
`audit_manifest` **둘 다 진입부에서** `unsupported_env_grade` 로 즉시 끝낸다.
네트워크도 쓰지 않고 패키지도 파싱하지 않는다. `env_grade` 는 `None`(적용된 등급
없음)이고 `requested_env_grade` 에 요청값이 남는다.

이에 따라 1차에서 넣었던 `requires_review` 승격 조건 2곳은 도달 불가가 되어
제거했다.

## 6. 검토 요청 형식

"괜찮아 보인다"가 아니라 **주장을 검증하는 형태**로 부탁한다. 예:

- 코드는 깨끗하고 패키지에 CRITICAL 취약점만 있는 체커 JSON 을 넣었을 때
  포털이 `blocked` 를 내는가? 픽스처를 만들어 실제로 돌려서 답할 것.
- 체커 저장소에서 `pytest -q` 가 통과하는가? 실패하면 어느 테스트인가?
- `gvskb_gate.py` 에 `--env-grade E3` 를 넣으면 체커를 호출하지 **않고**
  exit 2 로 끝나는가?
