# 설치 상태 점검·업데이트 기능 설계

## 결론

설치 상태 점검과 업데이트는 포털 서비스 기능으로 제공한다. 하네스 저장소에는 공통 정책, 템플릿, 검증 스크립트만 유지한다.

하네스는 검증 기준과 스크립트를 제공할 수 있지만, 사용자가 누르는 버튼, 상태 표시, 업데이트 승인 흐름은 이 포털이 담당한다.

## 하네스와 MCP를 구분하는 기준

- 하네스는 프로젝트에 한 번 적용하는 공통 개발 기준이다. Codex와 Claude Code에 각각 다른 하네스를 설치하지 않는다.
- 도구마다 달라지는 것은 체커 MCP의 설정 위치와 자동 등록 가능 여부다.
- ChatGPT 데스크톱·Codex는 `.codex/config.toml` 설정 계층을 공유한다.
- Claude Code는 프로젝트 루트 `.mcp.json`을 사용한다.
- Claude Desktop은 Claude Code 설정을 자동으로 공유하지 않으며 Desktop Extension 또는 `.mcpb`가 필요하다.
- Lovable은 현재 자동 MCP 등록 대상이 아니다. 하네스 지침을 적용하고 포털에서 제출 전 점검한다.

## 버전 확인 UX

버전 확인은 무거운 전체 상태 점검과 분리한다. (2026-08-12 정정) 최신 여부 판정 기준은 `origin/main` commit 비교가 아니라 **서명된 릴리스/승인 매니페스트**여야 한다 — `origin/main` 비교를 기준으로 삼으면 01 §9의 "`main` 직접 추적 금지" 원칙과 자기모순이 된다. 릴리스 채널이 마련되기 전까지의 임시 구현만 `origin/main` 비교를 사용하며, 이 임시 상태를 화면에 명시한다.

1. 확인 전에는 `버전 확인` 버튼을 누를 수 있다.
2. 확인 중에는 버튼에 `확인 중`을 표시한다.
3. 최신이면 버튼을 `최신 버전`으로 바꾸고 비활성화한다. 업데이트 버튼도 `업데이트 불필요`로 비활성화한다.
4. 구버전이면 버튼을 `업데이트 필요`로 바꾸고 비활성화한다. 업데이트 버튼만 활성화한다.
5. GitHub에 연결할 수 없거나 Git 복사본이 아니면 `확인할 수 없음`을 알리고 다시 확인할 수 있게 둔다.

사용자에게는 `최신 버전입니다.` 또는 `업데이트가 필요합니다.`만 레이어 팝업으로 안내한다. commit, doctor, 실행 게이트, 훅 상태는 전체 진단 화면에서만 제공한다.

## 실행 형태별 가능 범위

| 형태 | 사용자 PC 하네스 확인 | 사용자 PC 체커 확인 | 로컬 폴더 검사 | 중앙 통계 |
|---|---:|---:|---:|---:|
| 순수 웹 포털 | 불가 | 불가 | 불가 | 가능 |
| 로컬 웹앱 | 가능 | 가능 | 가능 | 선택 |
| 데스크톱 앱 | 가능 | 가능 | 가능 | 선택 |
| 기관 관리 에이전트 + 웹 | 가능 | 가능 | 가능 | 가능 |

1차 제품이 로컬 폴더 검사와 사용자 PC 설치 상태 확인을 포함하려면 데스크톱 앱 또는 로컬 웹앱이어야 한다.

## 상태 점검 항목

상태 점검은 읽기 전용으로 동작한다.

- 하네스 설치 경로
- 하네스 Git remote가 공식 저장소인지 여부
- 하네스 로컬 commit
- 하네스 GitHub `origin/main` commit
- 로컬 변경 여부
- 프로젝트 실행 게이트 명령 존재 여부: `npm run guard`
- 커밋 전 훅 활성화 여부: `git config core.hooksPath`
- 패키지 설치 게이트 존재 여부: `shared/enforcement/gvskb_gate.js`, `shared/enforcement/gvskb_gate.py`
- 체커 CLI 설치 여부
- 체커 MCP 서버 실행 파일 여부
- 체커 버전
- 체커 doctor 요약
- 체커 룰셋, 인텔 데이터 상태
- Codex 전역 MCP 설정 여부
- 프로젝트 MCP 설정 여부
- Claude Code / Claude Desktop 연결 설정 여부
- GitHub 접근 가능 여부
- OSV, PyPI, npm 접근 가능 여부

## 업데이트 원칙

업데이트는 바로 실행하지 않는다.

1. 상태 점검을 먼저 실행한다.
2. 업데이트가 필요한 항목만 보여준다.
3. 업데이트 출처와 변경 내용을 보여준다.
4. 사용자가 승인한다.
5. 업데이트를 실행한다.
6. 하네스 검증과 체커 doctor를 다시 실행한다.
7. 실패하면 원복 또는 수동 조치 안내를 제공한다.

## 금지

- `main` 브랜치 실시간 자동 반영
- 사용자 승인 없는 GitHub pull
- 사용자 승인 없는 Python 패키지 설치
- 사용자 승인 없는 MCP 설정 변경
- 체커 결과가 없는데 최신 또는 정상으로 표시
- 로컬 전체 경로, 계정명, 토큰을 중앙 서버에 저장

## UI 배치

첫 화면:

- 상단 상태 배지: `상태 점검`
- 누르면 하네스 및 MCP 등록 화면의 `내 PC 설치 상태` 섹션으로 이동

하네스 및 MCP 등록 화면:

- `내 PC 설치 상태를 확인하세요`
- 상태 카드 4개: 하네스 파일, 실행 게이트, 체커·MCP, 네트워크
- `상태 점검 시작`
- `업데이트 확인`

업데이트 확인 결과:

- 최신: 조치 없음
- 업데이트 가능: 변경 내용 보기 후 업데이트
- 검증 필요: 업데이트 또는 재검증 필요
- 연결 실패: 방화벽, GitHub 접근, 프록시 확인

구버전 감지 시 화면:

- `체커 업데이트 권장`: 현재 버전, 최신 안정 버전, 룰셋 변경 요약 표시
- `하네스 업데이트 가능`: 현재 commit, 승인된 릴리스 또는 검증된 commit 표시
- `MCP 재등록 필요`: 기존 설정 백업 여부와 재검증 항목 표시
- `변경 내용 보기`: 설치 없이 변경 요약과 검증 상태만 표시
- `업데이트 적용 준비`: 사용자 승인 확인 화면으로 이동

업데이트 확인 화면은 다음 절차를 한 줄 흐름으로 보여준다.

```text
상태 확인 -> 변경 내용 보기 -> 사용자 승인 -> 업데이트 적용 -> 재검증
```

업데이트 적용 전 확인해야 할 항목:

- 출처가 공식 릴리스 또는 승인된 manifest인지
- 룰 변경이 적대적 검증을 통과했는지
- 기존 설정 파일 백업 위치가 표시되는지
- 업데이트 후 `gg-validate.ps1`, `gvskb doctor`, MCP 연결 테스트가 실행되는지
- 실패 시 이전 버전 유지 또는 수동 조치 안내가 제공되는지

## 로컬 실행 계약

현재 설계용 로컬 점검 스크립트:

```powershell
.\tools\pc-status.ps1 -Root <harness-path> -Json
```

이 스크립트는 포털 백엔드가 호출할 수 있는 계약 예시다. 최종 구현에서는 Python 백엔드 또는 데스크톱 앱 런타임에서 동일한 결과 구조를 반환하는 API로 감싸는 것을 권장한다.

예상 API:

```text
GET  /api/local/status
POST /api/local/update/preview
POST /api/local/update/apply
POST /api/local/mcp/register
POST /api/local/validate
```

`/api/local/update/apply`는 반드시 사용자 승인 토큰 또는 확인 플래그를 요구한다.
