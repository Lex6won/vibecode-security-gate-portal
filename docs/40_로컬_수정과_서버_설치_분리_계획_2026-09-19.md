# 40. 로컬 수정과 서버 설치 분리 계획 (2026-09-19)

## 1. 목적과 적용 원칙

포털은 중앙 서버에 설치하고, 사용자는 웹브라우저로 접속해 소스 폴더·ZIP 또는 허용된 Git 저장소를 제출한다. 서버는 제출물을 임시 저장하고 `gvskb`를 실행해 보고서와 SBOM을 만든다.

이 문서는 다음 두 작업을 분리한다.

- **로컬 보완**: 서버에 배포되기 전에 저장소 코드와 자동 테스트로 끝내야 하는 작업
- **서버 보완**: 배포할 서버가 준비된 뒤 운영자 권한으로 설정·검증해야 하는 작업

서버 설정으로 코드 결함을 가리지 않는다. 반대로 서버 주소, 인증서, 서비스 계정, 방화벽과 백업처럼 환경에서만 정할 수 있는 값은 소스에 하드코딩하지 않는다.

## 4. 로컬에서 먼저 보완할 코드

### L-01. 운영 인증을 fail-closed로 변경 — P0 · 완료(2026-09-19)

기존에는 `PORTAL_AUTH_MODE`가 `smtp`가 아니면 개발 로그인 URL이 노출될 수 있었다. 현재는 아래 배포·인증 조합을 서버 시작 시 검증한다.

구현:

- `PORTAL_DEPLOYMENT_MODE=local|pilot|production`, `PORTAL_AUTH_PROVIDER=local-dev|cloudflare-access|smtp`를 명시한다.
- `pilot`·`production`에서는 인증 제공자, 허용 호스트, 40자리 체커 커밋 고정값이 없으면 서버 시작을 거부한다.
- Access/기관 SSO를 쓰면 검증된 상위 인증 신원만 세션으로 교환한다.
- SMTP를 쓰면 실제 발송 성공 전에는 로그인 토큰을 사용자 응답에 넣지 않는다.
- 개발 로그인은 loopback 바인드와 `local` 모드가 동시에 성립할 때만 허용한다.

자동 검증:

- 운영 모드에서 `dev_login_url`이 절대 반환되지 않는다.
- 인증 헤더 위조, 다른 이메일 요청, 만료·재사용 토큰을 거부한다.
- 인증 설정이 비어 있으면 운영 프로세스가 시작되지 않는다.

### L-02. 업로드 총량 제한과 실패 정리 — P0

현재 JSON 요청 본문은 상한 없이 메모리에 모이고, multipart 제한은 파일별 제한과 사후 총량 판정 중심이다.

구현:

- JSON 본문에 작은 명시적 상한을 둔다.
- `Content-Length` 선검사와 스트리밍 누적 총량 제한을 함께 적용한다.
- 총량 초과 시 입력 스트림과 파일 쓰기를 즉시 중단한다.
- busboy 오류, 연결 중단, pipeline 실패, timeout 모두에서 업로드 임시 디렉터리를 삭제한다.
- 중복 경로, 대소문자 충돌, 심볼릭 링크성 항목, 빈 파일 과다 제출을 검증한다.

자동 검증:

- 500MB 초과, 파일 수 초과, 선언 크기와 실제 크기 불일치
- 전송 중 연결 종료와 느린 전송
- ZIP 경로 탈출, 고압축률, 과다 엔트리, 중복 파일명
- 모든 실패 후 임시 디렉터리가 남지 않음

### L-03. 생성 보고서의 브라우저 실행 격리 — P0

현재 HTML 보고서를 `?view=1`로 같은 origin에서 inline 제공할 수 있다. 보고서 내용에 공격 문자열이 들어가면 포털 세션과 같은 출처에서 실행될 가능성이 있다.

구현 우선순위:

1. 기본은 HTML도 `attachment` 다운로드로 제공한다.
2. 브라우저 열람이 필요하면 별도 무쿠키 origin에서 제공한다.
3. 별도 origin이 어렵다면 sandbox iframe과 강한 CSP를 적용하고 포털 쿠키를 전달하지 않는다.
4. 사용자 입력이 들어가는 파일명, 표, 요약문을 HTML 문맥에 맞게 이스케이프한다.

자동 검증:

- `<script>`, 이벤트 속성, `javascript:` URL, HTML 종료문자 삽입
- 다른 사용자의 보고서 URL 직접 접근은 404
- inline 보고서에서 포털 세션 쿠키와 로컬 API 토큰에 접근할 수 없음

### L-04. TLS 프록시 인식과 쿠키·보안 헤더 — P0

구현:

- 운영 세션 쿠키에 `Secure`, `HttpOnly`, 적절한 `SameSite`를 적용한다.
- 신뢰할 프록시 범위를 명시하고 임의의 `X-Forwarded-*` 헤더를 신뢰하지 않는다.
- 정적 화면과 API에 CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`를 일관되게 적용한다.
- HSTS는 TLS 종단과 도메인이 확정된 운영 환경에서만 활성화한다.
- 운영 모드 HTTP 직접 접속은 거부하거나 HTTPS로 리다이렉트한다.

### L-05. 체커 실행 경계 — P0

코드에서 할 일:

- 작업별 고유 임시 디렉터리와 최소 환경변수만 체커에 전달한다.
- timeout·취소 시 자식 프로세스 트리와 임시파일을 정리한다.
- 실행 대상 경로가 해당 작업 디렉터리 밖으로 벗어나지 못하게 한다.
- 동시실행·대기열·디스크 부족을 fail-closed로 처리한다.
- 체커 커밋과 룰셋 신원 불일치 시 점검을 거부한다.

서버의 저권한 계정·컨테이너 설정은 S-03에서 별도로 수행한다.

### L-06. 목표 OS에 맞는 ZIP 처리 — P0 또는 조건부

- 기관 서버가 `shared/institution-profile.yaml`대로 Rocky Linux 9이면 현재 PowerShell `Expand-Archive` 의존을 배포 전에 제거한다.
- 기관 서버가 Windows로 확정되면 현재 경로를 유지할 수 있지만 기관 프로파일 변경과 운영 승인이 필요하다.
- 새 압축 라이브러리가 필요하면 패키지 게이트를 먼저 통과시킨다. 표준 도구만으로 구현할 수 있으면 새 의존성을 추가하지 않는다.

### L-07. 배포 게이트 강화 — P0

현재 `deploy-server.ps1`은 `node --check`와 버튼 계약 테스트까지만 실행한다.

구현:

- 배포 전 `npm ci` 후 `npm run guard`를 실행한다.
- `db:check`, 체커 신원, fixture 커밋, 시나리오 테스트를 포함한다.
- 운영 프로파일 설정 검사를 추가하고 개발 인증·미고정 체커·HTTP 공개 상태를 차단한다.
- 검증이 끝난 뒤에만 서비스를 재시작한다.
- 재시작 후 `/health`의 `identity_state=ok`까지 확인하고 아니면 자동 롤백 또는 이전 서비스 유지로 처리한다.

### L-08. 중앙 운영 데이터 모델 — 관리자 기능 착수 전 P1

현재 파일 기반 저장과 메모리 세션은 단일 프로세스 시범운영 범위다. 여러 사용자의 서비스·SBOM·패키지 현황을 관리하려면 다음을 코드로 구현한다.

- PostgreSQL 16 마이그레이션과 트랜잭션
- 안정적인 `service_id`, 점검 snapshot, SBOM 원본·정규화 inventory
- 최신 완료 점검과 과거 이력의 분리
- 사용자·부서·관리자 권한과 감사로그
- 재시작·중복 제출·동시 점검의 멱등성

## 6. 서버에서 수행할 세부 작업

### S-01. 설치 전 운영 조건 확정

담당 부서와 다음 값을 문서로 확정한다.

- 서버 OS와 컨테이너 방식: 기본안은 Rocky Linux 9 + rootless Podman
- 이용 범위: 내부 직원, 타 기관, 인터넷 사용자 중 어디까지인지
- 예상 사용자 수, 동시 점검 수, 최대 업로드 크기, 일 점검 건수
- 처리 가능한 데이터 등급과 개인정보 포함 가능 여부
- 보고서·SBOM·점검 이력 보존기간과 파기 책임자
- 인증 방식: 기관 SSO, Access, SMTP 중 하나
- 외부 통신: GitHub, 정부 깃랩, PyPI/npm, 인텔 번들 반입 경로
- 장애·보안사고·패키지 오탐의 운영 연락체계

완료 증거: 확정값, 담당자 역할, 승인 문서 번호. 개인 이름이나 전화번호는 저장소에 기록하지 않는다.

### S-02. 네트워크·DNS·TLS

- Node 포트를 인터넷에 직접 공개하지 않는다.
- 방화벽은 reverse proxy/load balancer 또는 내부 허용망에서 오는 연결만 허용한다.
- DNS 이름과 기관 인증서를 적용하고 TLS 1.2 이상을 사용한다.
- 외부 인증 관문을 쓰면 origin 직접 접속을 방화벽에서 막는다.
- 관리 경로는 일반 사용자 경로보다 좁은 네트워크 또는 별도 접근정책을 적용한다.
- outbound는 필요한 목적지만 허용한다. 망분리이면 서명·해시 검증된 번들 반입 절차를 사용한다.
- 프록시의 본문 크기 제한과 timeout을 포털 제한보다 같거나 작게 설정한다.

완료 검증:

- HTTP 직접 접속 차단 또는 HTTPS 전환
- 인증 없는 `/`, `/api/*`, `/reports/*`, `/admin` 접근 차단
- Host 헤더 위조 거부
- origin IP로 우회 접속 불가
- 인증서 만료 감시 등록

### S-03. 서비스 계정과 실행 격리

기본안:

- root 로그인과 LocalSystem 실행을 금지한다.
- 포털용 비로그인 서비스 계정과 체커 작업 권한을 최소화한다.
- rootless Podman 컨테이너는 읽기 전용 애플리케이션 이미지로 실행한다.
- 작업 임시영역만 쓰기 허용하고 호스트의 사용자 홈, 시스템 디렉터리, 소켓을 마운트하지 않는다.
- CPU, 메모리, 프로세스 수, 열린 파일 수, 실행시간과 디스크 quota를 둔다.
- 컨테이너 권한 상승, privileged, host network, Docker/Podman socket 마운트를 금지한다.
- 가능하면 seccomp/SELinux enforcing과 `no-new-privileges`를 적용한다.

Windows 서버를 쓰는 경우:

- 전용 로컬 서비스 계정을 만들고 `Log on as a service`만 부여한다.
- 코드 읽기, 데이터·로그·임시폴더의 필요한 권한만 부여한다.
- NSSM 서비스의 `ObjectName`을 해당 계정으로 지정한다.
- LocalSystem, Administrators 그룹, 사용자 프로필 캐시 공유를 운영 기본값으로 사용하지 않는다.

### S-04. 디렉터리와 파일 권한

운영 경로를 분리한다.

| 영역 | 권한 원칙 | 백업 |
|---|---|---|
| 애플리케이션 | 배포 계정만 쓰기, 서비스 계정 읽기 | 태그·이미지로 재현 |
| 업로드 임시영역 | 서비스 계정만 읽기/쓰기, 자동 만료 | 백업 금지 |
| 보고서·SBOM | 서비스 계정 쓰기, API를 통한 소유권 확인 | 정책에 따라 암호화 백업 |
| 로그 | 서비스 계정 추가, 운영자 읽기 | 중앙 로그 정책 |
| 비밀값 | 서비스 계정만 읽기 | 비밀관리시스템 정책 |
| 인텔 캐시 | 갱신 작업 쓰기, 포털/체커 읽기 | 재반입 가능 |

- 소스 업로드 원본은 점검 완료 또는 실패 후 즉시 삭제한다.
- 임시영역과 보고서 영역에 디스크 quota와 사용률 경보를 둔다.
- 백업 대상에 임시 소스와 세션 토큰을 포함하지 않는다.

### S-05. 런타임·체커·인텔 설치

- 기관 프로파일 기준 Node 20.19+, Python 3.12를 사용한다.
- 잠금파일 기반으로 `npm ci --ignore-scripts` 또는 승인된 빌드 번들을 사용한다.
- 체커 wheel/소스의 커밋·SHA-256·버전을 기록한다.
- `PORTAL_EXPECTED_CHECKER_COMMIT`을 실제 설치 커밋으로 설정한다.
- `gvskb doctor`의 ERROR는 설치 중단, WARN은 사유와 보완계획을 기록한다.
- JavaScript/TypeScript 운영 점검 품질을 위해 Linux Semgrep 사용 여부를 운영 기준으로 확정한다.
- 인터넷 제한·망분리 환경은 `docs/38`의 B/C/D 절차에 따라 인텔 번들을 반입한다.
- 인텔 생성시각, 서명, 해시, stale 상태를 확인한다.

### S-06. 인증·비밀값·관리자 설정

- 운영 인증 제공자를 연결하고 개발 로그인 응답이 비활성인지 확인한다.
- 관리자 초기 비밀번호는 일회성으로 발급하고 첫 로그인 후 교체한다.
- SMTP 비밀번호, Access 설정, DB 비밀번호, 서명키를 Git과 문서에 넣지 않는다.
- 비밀값 파일은 서비스 계정만 읽을 수 있게 하고 로그에 출력하지 않는다.
- 세션 만료, 강제 로그아웃, 관리자 잠금과 감사로그 보존기간을 확정한다.
- 계정 퇴직·부서 이동·권한 회수 절차를 정한다.

### S-07. PostgreSQL과 백업

공식 다중 사용자 운영은 PostgreSQL 16을 기본으로 한다.

- 포털 전용 DB와 최소권한 DB 계정을 생성한다.
- 애플리케이션 계정에는 스키마 소유권이나 관리자 권한을 주지 않는다.
- migration 전 백업, migration 후 스키마 버전 확인, 실패 시 복구 절차를 둔다.
- DB 연결은 TLS 또는 동일 보안영역의 승인된 내부 연결을 사용한다.
- 일일 백업과 보존기간을 정하고 백업을 암호화한다.
- 월 1회 이상 별도 환경에서 복구 시험을 수행한다.
- 보고서 파일과 DB snapshot의 시점을 맞춰 복구 불일치를 점검한다.

### S-08. 운영 설정과 용량

- `PORTAL_ALLOWED_HOSTS`는 실제 서비스 도메인과 내부 health 주소만 둔다.
- 동시 점검 수는 CPU·메모리 실측 후 설정한다. 첫 운영은 낮게 시작한다.
- 사용자당 동시 점검 1건, 전체 queue 상한, quick/standard timeout을 명시한다.
- 업로드 최대 크기, 압축 해제 최대 크기, 보고서 보존기간을 화면 고지와 일치시킨다.
- 디스크 부족 임계값은 최소 한 건의 최대 점검을 완료할 여유보다 크게 둔다.
- 시간대는 `Asia/Seoul`, 서버 시간은 기관 NTP와 동기화한다.

### S-09. 배포·롤백

- CI가 통과한 태그나 서명된 오프라인 번들만 배포한다.
- 배포물의 태그, commit, checker commit, ruleset, 파일 해시를 기록한다.
- 서비스 중지 전에 새 버전의 설정 검사와 전체 guard를 완료한다.
- DB migration과 애플리케이션 배포의 순서 및 호환 범위를 확인한다.
- health만 보지 않고 실제 로그인·업로드·점검·보고서 다운로드를 smoke test한다.
- 이전 이미지/태그와 DB 복구 지점을 준비한다.
- 롤백 후에도 새 버전에서 생성한 데이터가 읽히는지 확인한다.

### S-10. 관측·감사·경보

최소 수집 항목:

- 로그인 성공·실패·잠금, 관리자 작업
- 점검 접수·시작·완료·실패·취소·timeout
- 체커 commit·ruleset·인텔 freshness
- 업로드 거부 사유와 임시파일 정리 결과
- 보고서·SBOM 열람·다운로드·삭제
- 서비스 queue, CPU, 메모리, 디스크, DB 연결 상태

로그에는 원본 소스, 세션 토큰, 비밀번호, 개인 전화번호, 전체 이메일 목록을 남기지 않는다. 경보 기준과 담당 부서의 수신 경로는 서버 운영 문서에서 관리한다.

### S-11. 운영 개시 전 적대적 인수시험

- 무인증·권한 없는 사용자·다른 부서 사용자의 자료 접근 시도
- 개발 로그인 URL 요청과 인증 헤더 위조
- 대용량·느린 업로드, 연결 중단, ZIP 폭탄과 경로 탈출
- XSS 문자열이 포함된 프로젝트명·파일명·체커 보고서
- 체커 commit 불일치, 인텔 stale, 외부망 차단, 체커 timeout
- 동시 점검 상한과 queue 초과
- 서비스 재시작 후 이력·SBOM·감사로그 유지
- 보고서 보존기간 만료와 원본 소스 즉시 삭제
- DB 및 파일 백업 복구
- 이전 태그 롤백

각 시험은 요청시각, 입력 조건, 기대 결과, 실제 결과, 로그 위치를 남긴다. 통과 결과는 운영 승인 증거이지 자동 보안승인은 아니다.

## 7. 실행 순서

1. 로컬에서 L-01~L-07을 수정하고 적대적 테스트를 통과시킨다.
2. SBOM 관리자 기능을 설계하면서 L-08의 서비스·snapshot·inventory 모델을 구현한다.
3. 서버 담당자가 S-01의 운영 조건을 확정한다.
4. 확정된 OS와 인증 방식으로 S-02~S-08을 구축한다.
5. 검증된 태그/번들로 S-09 배포를 수행한다.
6. S-10 관측을 켜고 S-11 인수시험을 통과한 뒤 제한된 시범 사용을 시작한다.
7. 시범 사용 지표와 사고·오탐 기록을 검토한 뒤 정식 운영 범위를 확대한다.

## 8. 지금 적용할 우선순위

현재 로컬 테스트 단계에서는 다음 순서로 수정한다.

1. L-01 운영 인증 fail-closed
2. L-02 업로드 총량·중단·정리
3. L-03 보고서 실행 격리
4. L-04 쿠키·보안 헤더
5. L-05 체커 프로세스 정리와 작업경로 제한
6. L-06 목표 OS 확정 후 ZIP 구현
7. L-07 배포 게이트 강화
8. L-08 DB·SBOM·서비스 영향도 기능

서버 계정, 방화벽, TLS, PostgreSQL, 백업은 지금 개발 PC에 흉내 내어 운영 완료로 처리하지 않는다. 다만 컨테이너·DB·프록시 설정 파일과 자동 검증은 로컬에서 미리 준비할 수 있다.
