# 공공 바이브코딩 보안 게이트 포털 설명영상 시나리오 초안

작성일: 2026-08-29
목적: 첫 테스트 영상 제작용 콘티. 핵심 문제를 1분 안에 각인시키고, 포털의 역할을 짧게 제시한다.

## 1. 영상 핵심 메시지

한 줄 메시지:

> 공무원은 직접 만들 수 있게 되었지만, 보안검토와 운영 이관에서 멈춥니다. 이 포털은 그 병목을 줄이기 위해 점검 근거와 보고서, 패키지 판단 자료를 자동으로 정리해 주는 공공 바이브코딩 관문입니다.

각인시킬 문제:

> 개발은 쉬워졌는데, 검토와 운영은 쉬워지지 않았다.

설명 방향:

- 바이브코딩의 첫 어려움은 개발 자체가 아니라, 만든 뒤의 보안검토·승인·운영 이관이다.
- 현업 공무원은 개발할 수 있지만, 운영 서버로 옮기는 권한과 책임은 정보화부서에 있다.
- 정보화부서는 보안성검토 도구와 인력·지식이 부족하고, 승인 뒤 장애·보안 사고 책임을 져야 해서 쉽게 받아 주기 어렵다.
- 이 서비스는 보안 승인을 자동으로 내리는 도구가 아니다.
- 체커는 관측하고, 하네스는 개발 기준을 지키게 하고, 포털은 결과를 전달하고 축적한다.
- 최종 판정은 보안부서 사람이 한다.
- 원본 소스는 점검 뒤 보관하지 않고, 패키지 메타정보만 화이트리스트 근거로 축적한다.

## 2. 추천 영상 톤

형식: 공공기관 내부 설명용 1분 영상. "문제 각인 → 포털 역할 → 한 문장 결론" 순서로 간결하게.

비주얼 톤:

- 공무원 사무실 실사풍 이미지 중심
- 포털 화면 캡처는 후반 15초에만 압축적으로 사용
- 색상은 포털 UI의 차분한 공공 서비스 톤과, 제목 장면만 어두운 시네마틱 톤

내레이션 톤:

- 정보화부서를 비난하지 않고, "책임은 큰데 근거와 도구가 부족한 구조"로 표현
- "검사합니다"보다 "무엇을 고쳐야 하는지 알게 해줍니다"에 초점
- 공무원과 보안담당자 양쪽의 부담을 줄인다는 메시지

## 3. 최종 1분 제작안 — 5초 단위

기본 단위는 5초다. 긴 실제 대사를 살리기 위해 10컷, 총 60초로 구성한다. 각 컷은 하나의 이미지로 시작하고, 인물의 표정·시선·손동작을 영상 생성 단계에서 움직인다. 02, 04, 05컷은 7초로 잡아 대사가 잘리지 않게 한다.

| 컷 | 시간 | 화면 구성 | 인물의 행동·대화 | 핵심 메시지 |
|---:|---:|---|---|---|
| 01 | 0-5초 | 공무원 사무실. 개발자 책상과 노트북을 클로즈업한다. | 개발자가 AI를 활용해 ‘욕가리게’ 업무 도구를 완성하고, 화면을 보며 자신 있게 고개를 끄덕인다. | 현업도 이제 직접 개발한다 |
| 02 | 5-12초 | 개발자가 노트북과 요청서를 들고 인프라 담당자 자리로 온다. | 개발자: “제가 욕가리게를 개발했어요. 민원 담당자들에게 도움이 될거에요. 이거 정식 서비스 가능할까요?” 인프라 담당자는 문서를 받아 살펴본다. | 개발 뒤에는 정식 서비스 요청이 남는다 |
| 03 | 12-17초 | 인프라 담당자의 모니터와 두 사람의 대화 장면을 같은 프레임에 담는다. | 인프라 담당자: “우선 보안성검토 받아 오세요.” 개발자는 당황한 표정으로 보안담당자 쪽을 돌아본다. | 운영부서는 보안 근거 없이는 이관할 수 없다 |
| 04 | 17-24초 | 보안담당자 책상. 요청서와 체크리스트, 라이브러리 목록이 놓여 있다. | 보안담당자: “이거 직접 개발하신 거예요? 취약점 점검 받아 오시고, SBOM 제출해 주세요.” 개발자는 SBOM이라는 말을 듣고 멈칫한다. | 검토 단계에서 생소한 요구사항이 등장한다 |
| 05 | 24-31초 | 개발자의 얼굴을 중심으로 잡고, 손에 든 문서와 보안담당자를 짧게 교차한다. | 개발자: “네? S 뭐라구요? 취약점 점검은 유료잖아요. 제가 어떻게....” 말끝을 흐리고 문서를 내려다본다. | 현업은 무엇을, 어디서, 어떻게 준비할지 모른다 |
| 06 | 31-37초 | 보안담당자와 개발자를 마주 보게 하고, 인프라 담당자는 옆에서 듣는다. | 보안담당자: “그럼 저희는 어떻게 해요. 받아오세요.” 세 사람 사이에 어색한 침묵이 흐른다. | 누구도 악의적이지 않지만 업무는 멈춘다 |
| 07 | 37-43초 | 회의실 전경. 세 사람은 각자 서류와 모니터를 보고 있고 화면 중앙은 비워 둔다. | 나레이션·속마음: “나는 어떻게 해야 하지? 포기해야 하나?” 이어서 설명 나레이션: “개발은 쉬워졌는데, 검토와 운영은 그대로입니다.” | 개발과 운영 사이의 구조적 병목 |
| 08 | 43-49초 | 포털 메인 화면을 크게 보여준다. 개발자가 `보안 점검`을 클릭하고 세 사람의 시선이 포털 화면에 모인다. | 나레이션: “포털에서 보안 점검을 누릅니다. 복잡한 명령어 없이, 검사 대상과 방식을 고르면 됩니다.” | 클릭 한 번으로 보안 점검 시작 |
| 09 | 49-55초 | 점검 대상 선택 → 표준 점검 선택 → 진행률 → 결과 → HTML·JSON 보고서 저장 화면을 빠르게 연결한다. | 개발자: “점검 결과가 나왔고, 보고서도 저장됐습니다.” 나레이션: “몇 번의 클릭으로 제출할 근거가 정리됩니다.” | 점검하고, 결과를 저장하고 |
| 10 | 55-60초 | 결과 화면의 `보안성검토 요청` 버튼을 클릭한다. 요청 접수 상태와 보고서가 보이고 세 사람이 안도한다. | 보안담당자: “이 자료를 기준으로 검토 요청을 접수하겠습니다.” 나레이션: “모두가 같은 자료로 다음 단계로 움직입니다. 최종 판단은 사람이 합니다.” | 보안성검토 요청까지 한 흐름으로 |

## 4. 자막·음성 트랙 분리

자막 원칙:

- 이미지 생성에는 자막을 넣지 않는다. 자막은 편집 단계에서 별도 삽입한다.
- 등장인물 대사는 인물 가까이에 짧은 대화 자막으로 넣고, 나레이션은 하단 중앙에 고정한다.
- 한 번에 읽을 수 있는 분량만 배치한다. 대사는 최대 2줄, 나레이션은 컷당 1~2문장으로 제한한다.
- SBOM은 첫 등장 때만 “소프트웨어 구성요소 목록(SBOM)”으로 풀어 말하거나 자막에 보조 설명을 붙인다.
- 정보화부서를 무능하거나 악의적인 집단으로 표현하지 않는다. 도구와 근거가 부족하고 책임이 집중된 구조를 보여준다.

| 시간 | 음성 구분 | 화자 | 실제 음성 대본 | 자막 문안 |
|---:|---|---|---|---|
| 0-5초 | 나레이션 | 설명 | AI 덕분에 공무원도 직접 업무 도구를 만들 수 있게 됐습니다. | 개발은 이제 현업도 합니다 |
| 5-12초 | 대화 | 개발자 | 제가 욕가리게를 개발했어요. 민원 담당자들에게 도움이 될거에요. 이거 정식 서비스 가능할까요? | “제가 욕가리게를 개발했어요. 정식 서비스 가능할까요?” |
| 12-17초 | 대화 | 인프라 담당자 | 우선 보안성검토 받아 오세요. | “우선 보안성검토 받아 오세요.” |
| 17-24초 | 대화 | 보안담당자 | 이거 직접 개발하신 거예요? 취약점 점검 받아 오시고, SBOM 제출해 주세요. | “취약점 점검과 SBOM을 제출해 주세요.” |
| 24-31초 | 대화 | 개발자 | 네? S 뭐라구요? 취약점 점검은 유료잖아요. 제가 어떻게.... | “네? S 뭐라구요? 제가 어떻게....” |
| 31-37초 | 대화 | 보안담당자 | 그럼 저희는 어떻게 해요. 받아오세요. | “그럼 저희는 어떻게 해요. 받아오세요.” |
| 37-43초 | 나레이션·속마음 | 개발자 속마음 + 설명 | 나는 어떻게 해야 하지? 포기해야 하나? 개발은 쉬워졌는데, 검토와 운영은 그대로입니다. | 개발은 쉬워졌는데 검토와 운영은 그대로 |
| 43-49초 | 나레이션 | 설명 | 포털에서 보안 점검을 누릅니다. 복잡한 명령어 없이, 검사 대상과 방식을 고르면 됩니다. | 클릭 한 번으로 보안 점검 시작 |
| 49-55초 | 대화·나레이션 | 개발자 + 설명 | 개발자: 점검 결과가 나왔고, 보고서도 저장됐습니다. 나레이션: 몇 번의 클릭으로 제출할 근거가 정리됩니다. | 점검하고, 결과를 저장하고 |
| 55-60초 | 대화·나레이션 | 보안담당자 + 설명 | 보안담당자: 이 자료를 기준으로 검토 요청을 접수하겠습니다. 나레이션: 모두가 같은 자료로 다음 단계로 움직입니다. 최종 판단은 사람이 합니다. | 보안성검토 요청까지 한 흐름으로 |

프롬프트 공통 제작 규칙:

- 16:9 가로형, 이미지-to-영상 변환용 실사풍 스틸 이미지로 생성한다.
- 배경은 한국 공공기관 사무실이며, 세 인물의 외모·복장·역할을 모든 장면에서 유지한다.
- 이미지 안에는 한글·영문 텍스트, 자막, 말풍선, 로고, 개인정보, API 키, 서버 주소, 워터마크를 넣지 않는다.
- 실제 대사는 이미지가 아니라 영상 편집 단계의 음성 및 자막으로 넣는다.
- 프롬프트의 화면 속 UI는 읽을 수 없는 추상 블록으로 만들고, 실제 포털 캡처가 필요한 장면은 별도 캡처로 교체한다.

캐릭터·배경 기준 이미지:

- [`docs/video-references/character-sheet.png`](video-references/character-sheet.png): 김도윤(38세, 현업 개발자), 박서연(43세, 정보보안 담당자), 이준호(39세, 인프라·운영 담당자)의 얼굴·헤어·복장·표정 기준.
- [`docs/video-references/office-reference.png`](video-references/office-reference.png): 개발자 사무실, 서버실, 정보보안 담당자 사무실의 배경과 소품 기준.
- 모든 씬 생성 요청에는 위 두 이미지를 참조 이미지로 함께 전달한다. 장면마다 인물을 새로 해석하지 않고, 얼굴·안경·헤어스타일·복장 색상·명찰 위치를 유지한다.
- 캐릭터 시트에 있는 이름표와 설명 텍스트는 참조용이며, 생성되는 씬 이미지 안에는 복사하지 않는다.

## 6. 이미지-to-영상 움직임 프롬프트

각 이미지를 5~7초 영상으로 만들 때 사용할 프롬프트다. 영상 생성 모델에는 해당 장면 이미지를 함께 넣고, 아래 문장을 추가한다. 장면 02, 04, 05는 실제 대사를 살리기 위해 7초로 생성한다.

| 컷 | 영상 움직임 프롬프트 |
|---:|---|
| 01 | 5-second slow push-in toward the developer’s laptop. The developer finishes typing, looks at the abstract result, and gives a small confident nod. No readable screen text. |
| 02 | 7-second gentle tracking shot. The developer approaches the infrastructure desk, places the request document down, and speaks with hopeful but respectful body language. The infrastructure officer receives it. |
| 03 | 5-second restrained reaction shot. The infrastructure officer raises one hand slightly, points toward the security officer’s desk, and the developer turns with a surprised pause. |
| 04 | 7-second office dialogue shot. The security officer lifts the request document, checks a checklist, gestures toward an abstract package list, and the developer’s expression changes to confusion. No readable text. |
| 05 | 7-second close-medium reaction. The developer looks from the document to the security officer, makes a small “what?” gesture, then lowers the document with embarrassment. Keep emotion realistic, not comic. |
| 06 | 6-second tense two-shot. The security officer returns the document slightly, opens both hands in a practical “we need the materials” gesture, and the developer falls silent. The infrastructure officer looks down. |
| 07 | 6-second slow zoom out from the stalled meeting. Keep all three people nearly still, with the developer looking at the document. Leave the center and lower area clean for narration captions. |
| 08 | 6-second gentle push toward the large portal monitor. The developer moves the mouse and clicks the security-check entry once. The three characters shift their gaze to the same screen. Keep the real portal layout stable. |
| 09 | 6-second controlled UI pan from target selection to standard-check selection, scan progress, results, and HTML/JSON report save controls. Highlight each step once in sequence. |
| 10 | 5-second final side shot. The security officer clicks the security-review request action once, the interface changes subtly to a requested state, the infrastructure officer nods, and the developer looks relieved. Keep human review visible. |

## 9. 참고용 1분 내레이션 통합 대본

> AI 덕분에 공무원도 직접 업무 도구를 만들 수 있게 됐습니다.
> 그런데 실제로 쓰려면 보안검토를 받고, 승인받고, 운영 서버로 옮겨야 합니다.
> 보안담당자는 난감합니다. 유료 도구도 부족하고, AI가 만든 코드에서 무엇을 어떻게 봐야 할지 기준이 약합니다.
> 인프라 담당자도 쉽게 올릴 수 없습니다. 서비스가 멈추거나 사고가 나면 운영 책임이 돌아오기 때문입니다.
> 그래서 현업은 답답하고, 정보화부서는 위험합니다. 좋은 아이디어가 운영까지 가지 못합니다.
> 공공 바이브코딩 보안 게이트 포털은 이 사이에 공통 근거를 만듭니다.
> 코드를 점검하고, 결과와 보고서를 남기고, 자주 쓰는 패키지의 판단 근거를 쌓습니다.
> 체커는 사실을 보고, 포털은 그 결과를 전달하고 축적합니다. 최종 판단은 사람이 합니다.
> 개발은 쉽게, 검토는 근거 있게, 운영은 안전하게.
> 안전한 바이브코딩이 운영까지 이어지게 하는 것이 이 포털의 역할입니다.

## 13. 3분 설명자료 확장판 구성

### 1장. 왜 필요한가 — 개발보다 어려운 것은 운영까지 가는 길

핵심 질문:

- 현업 공무원이 AI로 만든 업무 도구를 실제 서비스로 쓰려면 누가 보안검토하고, 누가 승인하고, 누가 운영 서버로 옮길 것인가?
- 정보화부서는 무엇을 근거로 "받아도 된다" 또는 "아직 위험하다"고 말할 수 있는가?
- 책임은 정보화부서에 있는데, 도구·지식·운영 여력은 부족한 상황을 어떻게 줄일 것인가?

화면:

- 현업 공무원: AI로 업무 자동화 코드를 만드는 장면
- 정보화부서: 보안성검토, 운영 이관, 장애 책임, 서버 반영 요청이 한꺼번에 쌓이는 장면
- 두 사람 사이에 멈춰 있는 "배포 요청" 카드

내레이션:

> 바이브코딩은 공공 업무 자동화를 빠르게 만듭니다. 이제 개발은 현업도 할 수 있습니다. 하지만 실제 운영으로 옮기는 순간 문제가 생깁니다. 보안성검토는 무엇을 봐야 할지 어렵고, 운영 서버 이관은 장애와 보안 사고 책임이 따릅니다. 현업은 답답하고, 정보화부서는 위험합니다. 이 포털은 그 사이에 필요한 점검 근거와 보고서를 만들어 주는 관문입니다.

보여줄 갈등 구조:

| 현업 공무원 | 정보화부서 |
|---|---|
| AI로 업무 도구를 빠르게 만들었다 | 운영 서버에 올리면 책임을 져야 한다 |
| 빨리 써 보고 싶다 | 보안성검토 기준과 도구가 부족하다 |
| "왜 안 해 주지?"라고 느낀다 | "무엇을 근거로 승인하지?"라고 느낀다 |
| 결과적으로 아이디어가 멈춘다 | 결과적으로 요청을 미룰 수밖에 없다 |

3. 간편/표준 점검 선택
4. 대기열/진행률
5. 결과 확인
6. 보고서 다운로드
7. 보안성 검토 요청

내레이션:

> 사용자는 기관 메일로 접속하고, 검사 대상을 고릅니다. 개발 중에는 빠르게 확인하고, 제출 전에는 표준 점검으로 보고서를 남깁니다. 결과 화면에서는 수정할 항목과 검토 요청 버튼을 바로 확인할 수 있습니다.

### 4장. 보안 신뢰 원칙

화면:

- "source_retained: false"
- "보고서 90일 후 자동 삭제"
- "소스/경로/개인정보 미포함"

내레이션:

> 서버 기반 서비스에서 가장 중요한 것은 원본 보관 정책입니다. 업로드된 원본은 점검 뒤 삭제하고, 축적되는 것은 라이브러리 이름, 버전, 취약점 여부 같은 허용된 메타정보뿐입니다.

### 5장. 도구별 역할 경계

화면:

```
하네스 -> 체커 -> 포털 -> 보안부서 -> 화이트리스트 -> 체커 -> 하네스
```

자막:

- 체커: 관측
- 하네스: 집행
- 포털: 전달·축적
- 보안부서: 판정

내레이션:

> 이 구조에서 도구가 사람의 판정을 대신하지 않습니다. 체커는 사실을 말하고, 포털은 그것을 전달하고 축적합니다. 하네스는 정해진 기준을 개발 과정에 적용합니다. 승인과 차단은 보안부서의 몫입니다.

### 6장. 관리자 화면의 의미

화면:

- 화이트리스트 후보
- 문제 패키지
- 패키지 상세
- 검토 요청 대기열

내레이션:

> 관리자 화면은 검사를 많이 돌릴수록 가치가 커집니다. 여러 부서에서 반복적으로 쓰는 안전한 패키지는 후보로 올라오고, 취약하거나 이름 사칭이 의심되는 패키지는 문제 목록으로 모입니다. 보안담당자는 이 근거를 보고 정책을 만들 수 있습니다.

### 7장. 결론

화면:

- 공무원, 체커, 포털, 보안부서가 이어지는 순환 그래픽

마지막 자막:

> 보안 도구가 아니라, 안전한 바이브코딩을 더 많이 쓰게 하는 기반

내레이션:

> 목표는 보안 도구 하나를 더 만드는 것이 아닙니다. 누구나 기준을 따라 만들고, 쉽게 점검하고, 보안부서가 근거로 판단할 수 있게 하는 것입니다. 그렇게 안전한 바이브코딩이 반복 가능한 업무 방식이 됩니다.
