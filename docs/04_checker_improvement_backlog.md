# 보안체커 서비스화 수정 필요사항

## 결론

현재 체커는 CLI와 MCP 기반 점검 도구로는 쓸 수 있지만, 공무원이 신뢰하고 제출 증거물까지 만들 수 있는 “보안 게이트 서비스”가 되려면 제품 레이어와 체커 엔진 양쪽에 보완이 필요하다.

1차 제품은 웹 UI 기반 로컬 웹앱과 Python 기반 체커 엔진으로 한정한다. 필요하면 같은 구조를 데스크톱 앱으로 포장한다. 체커 MCP 기본 등록과 연결 검증은 1차에 포함하고, LLM API, MCP 고급 자동복구, 중앙 기관 웹 포털, 관리자 승인 워크플로는 1차에서 제외한다.

하네스 자동 설치는 1차 선택 기능으로 포함할 수 있다. 단, 검사를 위한 필수조건으로 만들지 않고, 설치·업데이트·프로젝트 적용 단계는 모두 사용자 동의와 검증을 거쳐야 한다.

가장 중요한 방향은 세 가지다.

1. 검사 성공과 검사 미완료를 엄격히 구분한다.
2. 진짜 취약점, 사람 검토 필요, 오탐 후보를 결과 모델에서 분리한다.
3. 업데이트와 룰 변경은 적대적 검증과 최종 재점검을 통과한 안정 채널만 사용자에게 배포한다.

## P0. 반드시 필요한 수정

### P0-1. 제출 전 전체 점검 프리셋

필요 이유:

사용자가 제출하려는 상황에서는 부분 스캔이 아니라 전체 스캔이 기본이어야 한다. 소스만 검사하고 의존성, 설치 패키지, 번들 검사를 빠뜨리면 위험한 항목이 누락될 수 있다.

수정 방향:

- `submit-check` 또는 동등한 하나의 실행 모드를 제공한다.
- 내부적으로 `scan_path`, `scan_dependencies`, `scan_installed_packages`, `scan_vendor_bundles`, `render_report(format="both", save=true)`를 묶는다.
- 실행된 검사와 생략된 검사를 JSON evidence에 기록한다.
- 필수 검사 중 하나라도 실패하면 `검사 미완료`로 판정한다.

### P0-2. 결과 판정 모델 확장

필요 이유:

현재처럼 `block/warn/allow` 중심이면 패턴만 비슷한 코드를 실제 취약점처럼 표시하기 쉽다. 신뢰성 높은 체커는 “확정 차단”과 “검토 필요”를 분리해야 한다.

수정 방향:

- 결과 상태를 최소 다음처럼 분리한다.
  - `confirmed_block`
  - `review_required`
  - `warning`
  - `false_positive_candidate`
  - `not_scanned`
  - `pass`
- `pattern-only` 결과는 기본적으로 `review_required`로 내린다.
- 실제 비밀값, 실제 개인정보, 외부 입력에서 위험 sink로 이어지는 흐름처럼 근거가 충분한 경우만 `confirmed_block`으로 올린다.

### P0-3. 검사 미완료 게이트

필요 이유:

발견 0건은 안전을 뜻하지 않는다. 파일을 못 읽었거나 의존성 검사를 못 했거나 인텔 데이터가 없으면 제출 가능으로 표시하면 안 된다.

수정 방향:

- 다음 조건을 별도 `not_scanned` 또는 `incomplete`로 표시한다.
  - 스캔 파일 0건
  - 의존성 manifest는 있으나 dependency audit 없음
  - lockfile 분석 실패
  - 설치 패키지 또는 vendor bundle 검사 실패
  - 룰셋 로드 실패
  - OSV/KEV/EPSS 등 인텔 조회 실패
  - 적용 요청 profile과 실제 적용 profile 불일치
- UI는 “문제 없음”이 아니라 “검사가 끝나지 않았습니다”로 보여준다.

### P0-4. 재현 가능한 증거 기록

필요 이유:

보안팀이 같은 소스를 다시 검사했을 때 결과를 비교할 수 있어야 한다.

수정 방향:

- 보고서와 JSON evidence에 다음을 기록한다.
  - 체커 버전
  - 엔진 commit
  - 룰셋 commit 또는 hash
  - 인텔 데이터 기준시각
  - 검사 모드
  - 요청 profile과 적용 profile
  - 검사 대상 URL, branch, commit SHA
  - 로컬/압축 소스 hash
  - lockfile hash
  - 검사 제외 파일과 사유

### P0-5. 오탐 억제용 맥락 분석 강화

필요 이유:

완전히 잘못된 코드는 잘 잡지만, 비슷해 보이는 정상 코드까지 자주 잡으면 공무원이 체커를 믿지 못한다.

수정 방향:

- 주민등록번호 탐지는 숫자 조각, timestamp, migration id, 통계값과 구분한다.
- 비밀값 탐지는 placeholder, 환경변수 참조, `.env.example` 예시와 실제 토큰을 구분한다.
- 경로 조작 탐지는 고정 파일명, allowlist, `resolve` 후 base path 검증을 반영한다.
- 명령 실행 탐지는 `shell=True`, 외부 입력 연결, allowlist 기반 실행을 구분한다.
- 빈 `catch` 또는 best-effort cleanup은 치명 취약점이 아니라 검토 또는 품질 경고로 분리한다.
- JSON/YAML/AST 파서를 우선 사용하고 정규식 단독 차단을 줄인다.
- LLM 보안 룰은 실행 코드와 정책·문서·fixture를 구분한다. 2026-08-09 하네스 `core-process-enforcement.yaml`의 완료 보고 안내 문구가 `GOV-LLM-OUTPUT-HANDLING-001` high/block으로 오탐된 사례가 있었다. 실제 sink, 렌더링, eval, shell, SQL 연결이 없는 YAML 정책 문서는 `false_positive_candidate` 또는 `allow`로 분리해야 한다.
- 위 사례는 회귀 fixture로 남긴다. 입력 예시는 `completion_evidence_required`, `scenario_result`, `checker_gate_status` 같은 구조화 정책 필드이며, 기대 결과는 findings 0건 또는 문서 맥락 경고 이하이다.

### P0-6. 업데이트 안정 채널

필요 이유:

로컬 웹앱, 데스크톱 앱 포장, MCP 등록을 제공하면 사용자가 매번 재설치하지 않아야 한다. 동시에 GitHub `main` 변경이 즉시 반영되면 검증되지 않은 룰이 현장에 퍼질 수 있다.

수정 방향:

- 엔진, 룰셋, 인텔 데이터를 분리해 업데이트한다.
- 안정 채널은 서명된 릴리스 또는 승인된 manifest만 받는다.
- 업데이트 전 적대적 테스트 결과를 기록한다.
- 업데이트 후 smoke scan과 대표 fixture 재검사를 수행한다.
- 실패 시 이전 안정 버전으로 rollback한다.

### P0-7. 적대적 검증 체계

필요 이유:

체커 수정으로 새로운 오탐, 과탐, 미탐이 생기면 보안 게이트로 사용할 수 없다.

수정 방향:

- 룰 변경 전후로 공격 샘플과 정상 유사 샘플을 모두 돌린다.
- 회귀 테스트에는 최소 다음을 포함한다.
  - 실제 취약 코드
  - 비슷하지만 안전한 코드
  - 문서/샘플/fixture
  - 의존성 전이 취약점
  - 네트워크 실패
  - 인텔 캐시 만료
  - 검사 대상 0건
- 커밋 전에는 변경 파일 대상 quick 검사, 전체 테스트, 대표 fixture 재스캔을 수행한다.
- 릴리스 전에는 제출 전 전체 점검과 보고서 생성까지 검증한다.

## P1. 제품화를 위해 필요한 수정

### P1-0. 하네스 자동 설치와 검증

- 공식 저장소 `https://github.com/Lex6won/vibe_harness_codex` 또는 검증된 릴리스를 기준으로 설치한다.
- 설치 위치는 앱 관리 폴더 또는 사용자가 지정한 폴더로 제한한다.
- 설치 후 `shared/scripts/gg-validate.ps1` 검증을 실행한다.
- 하네스 버전, commit, 검증 결과를 서비스 화면과 manifest에 기록한다.
- 현재 하네스에는 체커 설치 보조 스크립트는 있지만 하네스 자체 자동 설치 전용 스크립트는 없으므로, `harness-bootstrap` 성격의 설치/검증 흐름을 새로 만들어야 한다.
- 사용자 프로젝트에 `AGENTS.md`, `shared/`, `.mcp.json`, `.codex/` 등을 복사하는 것은 별도 “프로젝트에 하네스 적용” 기능으로 분리한다.
- 프로젝트 적용 전에는 변경 파일 목록, 덮어쓰기 여부, 백업 경로를 보여주고 명시적 동의를 받는다.
- 실패 시 보안검사 자체는 계속 가능해야 하며, 하네스 상태만 `검증 필요` 또는 `미설치`로 표시한다.

### P1-1. 데스크톱 앱 런처 API

- 검사 시작, 진행률, 취소, 결과 조회, 보고서 저장을 안정적인 내부 API로 노출한다.
- CLI 출력 파싱에 의존하지 않는다.
- Windows 경로, 한글 경로, OneDrive 경로를 정식 지원한다.

### P1-2. MCP 기본 등록과 고급 복구

- Codex, Claude Code 등 지원 도구의 설정 위치를 감지한다.
- 기존 설정을 백업한 뒤 MCP 서버를 등록한다.
- 연결 테스트 실패 시 원인과 복구 버튼을 제공한다.
- 체커 업데이트 후 MCP 서버 재시작 또는 경로 재확인을 제공한다.

### P1-3. 연결 진단

- GitHub, OSV, EPSS, PyPI, npm 접근 여부를 검사한다.
- 인터넷망 구역(방화벽 제어하 인터넷 사용 가능)을 위해 필요한 도메인, 포트, 실패 사유를 보여준다. (2026-08-12 정정: 경기도는 논리적 망분리 환경이며, 행정망 구역은 온라인 조회가 불가하므로 오프라인 반입 모드가 별도로 필요하다 — `18_gg_portal_agent_target_architecture.md` §8.1)
- 네트워크 실패 시 “검사 미완료”와 “오프라인 제한 검사”를 구분한다.

### P1-4. 제출 패키지 생성

- 기본 파일: 체커가 저장한 HTML 보고서, 체커가 저장한 JSON evidence, 검사 요약, manifest
- 선택 파일: 체커가 저장한 Markdown 보고서, SARIF, 예외 신청 초안
- 서비스는 체커 원본 리포트를 임의로 다시 저장하지 않고 `saved` 경로를 그대로 참조한다.
- 원본 소스 포함은 기본 꺼짐
- 제출 파일 생성 후 hash를 표시한다.

### P1-5. 사용자 친화적 수정 안내

- 규칙 ID만 보여주지 않고 “왜 위험한지”, “무엇을 바꾸면 되는지”를 업무 언어로 설명한다.
- 수정 예시는 안전한 방향만 제시한다.
- 자동 수정은 별도 단계로 분리하고 기본은 리포팅이다.

## P2. 운영 확장을 위한 수정

### P2-1. 기관 관리자 포털

- 안정 채널 승인
- 기관별 룰 정책
- 예외 승인 이력
- 제출 패키지 접수 현황
- 대표 fixture 회귀 결과 대시보드

### P2-2. 디자인 시스템

- Figma 기준 컴포넌트 라이브러리를 만든다.
- 상태 badge, 위험도 색상, finding table, 검사 progress, report download panel을 공통 컴포넌트로 관리한다.
- 데스크톱 앱과 웹 포털이 같은 언어와 상태 모델을 사용한다.

### P2-3. 보안팀 검토 워크플로

- `review_required` 항목을 보안팀 큐로 넘긴다.
- 검토 결과는 만료일이 있는 예외로만 저장한다.
- 예외가 만료되면 다시 review 또는 block으로 돌아간다.

## 하네스 반영 필요사항

- 제출 전 전체 점검을 하네스 용어로 더 명확히 하기 위해 `submit-check` 프리셋을 문서화할 필요가 있다.
- 경기도형 온라인 환경을 별도 네트워크 프로필로 추가할지 검토한다. 현재 `admin-network`는 외부통신 기본 금지에 가깝고, 경기도는 방화벽 허용 기반 온라인 갱신이 가능하다.
- `checker-integration.md`는 한글 인코딩이 깨져 보이는 환경이 있으므로 UTF-8 표시와 읽기 검증이 필요하다.
- 데스크톱 앱 산출물 기준이 현재 하네스에는 충분히 구체화되어 있지 않다. 설치형 앱, MCP 설정, 업데이트 검증, 제출 패키지 산출물 기준을 별도 참조 문서로 둘 필요가 있다.
