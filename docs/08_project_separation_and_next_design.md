# 프로젝트 분리 기준과 다음 설계

## 분리 원칙

하네스와 포털은 목적이 다르다.

| 프로젝트 | 역할 | 포함할 것 | 포함하지 않을 것 |
|---|---|---|---|
| `vibe_harness_codex` | AI 개발 흐름 표준화 | 정책, 템플릿, 검증 스크립트, 개발 언어 기준, 체커 사용 기준 | 사용자용 웹 화면, 관리자 화면, 검사 이력 DB, 업데이트 버튼 |
| `vibecode-checker` | 보안 점검 엔진 | 룰, 인텔, CLI, MCP 서버, 보고서 생성 | 포털 UI, 하네스 설치 UX, 기관 관리자 대시보드 |
| `vibecode-security-gate-portal` | 사용자가 쉽게 검사하는 서비스 | 화면, 로컬 검사 실행, 진행 상태, 결과 확인, 설치 상태 점검, MCP 등록 | 체커 룰 자체, 하네스 정책 원본 |

포털은 하네스와 체커를 사용할 수 있지만, 두 저장소의 본체 기능을 대신 소유하지 않는다.

## 1차 구현 형태

1차는 `웹 UI 기반 로컬 웹앱`으로 설계한다.

- 사용자는 브라우저 화면에서 사용한다.
- 로컬 백엔드가 사용자 PC에서 실행된다.
- 로컬 백엔드가 폴더 선택, 압축파일 처리, GitHub clone, `gvskb` 실행을 담당한다.
- 필요하면 같은 구조를 나중에 데스크톱 앱으로 포장한다.

순수 중앙 웹만으로는 사용자 PC의 로컬 폴더, Git 설정, MCP 설정, 하네스 설치 상태를 확인할 수 없다. 따라서 설치 상태 점검과 로컬 검사는 로컬 실행 구성으로 제공한다.

## 핵심 사용자 시나리오

### 1. 간편 점검

개발 중 위험 신호를 빠르게 본다.

- 입력: 폴더, 압축파일, GitHub URL
- 실행: 코드 중심 빠른 검사
- 출력: 위험 신호, 사람 검토 후보, 검사 실패 여부
- 제출 패키지: 만들지 않음

### 2. 표준 점검

개발 완료 후 기본 보안 점검과 의존성 점검을 함께 수행한다.

- 입력: 폴더, 압축파일, GitHub URL
- 실행: 코드 검사, 의존성 검사, 체커 HTML/JSON 보고서 생성
- 출력: 제출 가능 여부 초안, 수정 필요 항목, 의존성 위험
- 제출 패키지: 생성하지 않음

### 3. 하네스 설치 및 MCP 등록

개발 중에도 체커를 호출할 수 있도록 개발 도구에 연결한다.

- 하네스 설치 상태 확인
- 하네스 최신 여부 확인
- 체커 설치 상태 확인
- Codex/Claude Code MCP 등록
- 연결 검증

이 기능은 표준 점검을 대체하지 않는다. 개발 중 위험을 줄이는 보조 장치다.

### 4. 총괄 관리자 현황 확인

로그인한 총괄 관리자만 사용한다.

- 익명 검사 건수
- 검사 방식별 사용량
- 제출 가능/수정 필요/사람 검토 필요 통계
- 반복 발생 룰
- 오탐 후보 룰
- 체커 개선 후보

일반 사용자의 담당자명과 부서명은 받지 않는다.

## 상태 점검과 업데이트 UX

상태 점검은 읽기 전용이다.

상태 점검에서 확인할 항목:

- 하네스 설치 여부
- 하네스 공식 저장소 여부
- 하네스 최신 버전 여부
- 로컬 변경 여부
- 체커 CLI 버전
- 체커 MCP 서버 경로
- Codex/Claude Code MCP 등록 여부
- GitHub, OSV, PyPI, npm 연결 가능 여부

업데이트는 별도 버튼으로 분리한다.

업데이트 절차:

1. 현재 상태 확인
2. 업데이트 가능 항목 표시
3. 변경 내용과 출처 표시
4. 사용자 승인
5. 업데이트 실행
6. 하네스 검증과 체커 doctor 재실행
7. 실패 시 복구 안내

## 데이터 저장 기준

저장한다:

- 익명 세션 ID
- 검사 모드
- 대상 유형
- 대상 표시명 또는 해시
- 체커 버전
- 룰셋 버전
- 검사 결과 상태
- 탐지 룰 ID와 심각도
- 보고서 파일명, 해시, 크기

저장하지 않는다:

- 원본 소스코드
- 압축파일 원본
- GitHub 토큰
- 담당자명
- 부서명
- 로컬 전체 경로
- 민원 데이터

## 다음 설계 작업

1. 정적 HTML 시안을 실제 라우트 단위로 정리한다.
2. `src`에 로컬 웹앱 기본 구조를 만든다.
3. `tools/pc-status.ps1` 결과를 API 응답 스키마로 확정한다.
4. 간편 점검과 표준 점검의 체커 호출 옵션을 고정한다.
5. 관리자 화면은 익명 사용량과 체커 개선 후보 중심으로 다시 정리한다.
6. 하네스 README에는 포털 설치 UX가 아니라 하네스 자체 설치와 검증 기준만 남긴다.
