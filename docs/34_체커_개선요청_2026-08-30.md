# 34. 체커(gvskb) 개선 요청 — 포털 자체 점검에서 도출

> 작성: 2026-08-30. 근거: 포털 저장소 전체를 `gvskb scan . --profile public-default-strict --check-deps` 로 점검한 실제 결과.
> 대상: 체커(gvskb / 하네스) 유지보수 담당.
> 목적: "체커가 잡은 것 / 놓친 것"을 실제 사례로 정리해 규칙·엔진 개선에 반영.

---

## 0. 한 줄 요약

이번 점검에서 체커는 **24건을 올렸지만 실제 취약점은 0건**이었고(전부 오탐 또는 자기 시험용 픽스처),
**사람이 직접 찾은 실제 취약점 4건은 체커가 하나도 잡지 못했다.** 아래는 그 격차의 구체적 원인과 개선 방향이다.

체커는 KISA 시큐어코딩 패턴을 정규식(`engine: regex`, `confidence: pattern-only`)으로 검출한다.
따라서 "패턴이 보이는 취약점"에는 강하지만 "흐름·구조·부재(不在)로 생기는 취약점"에는 눈이 없다.
아래 A~C는 **현재 범위 안에서 고쳐야 할 오탐**, D~F는 **가치를 넓히는 신규 역량 제안**이다.

---

## A. [오탐/중요] 시험용 픽스처를 실제 코드처럼 판정한다

체커가 올린 24건 중 **18건이 `fixtures/checker-negative-fixture/` 안의 의도된 취약 샘플**이었다.
이 파일들은 체커(또는 포털)의 검출력을 시험하려고 **일부러 심어 둔 나쁜 코드**인데,
체커는 이를 구분하지 못하고 critical 10건을 포함해 그대로 block 판정했다.

실제 올라온 항목(발췌):
```
fixtures/checker-negative-fixture/app/main.py:24  [block/critical] 하드코드된 DB 비밀번호
fixtures/checker-negative-fixture/app/main.py:96  [block/critical] eval() 코드 삽입
fixtures/checker-negative-fixture/app/main.py:90  [block/critical] subprocess shell=True
fixtures/checker-negative-fixture/app/static/app.js:2  [block/high] innerHTML XSS
... (총 18건)
```

**문제:** 사용자가 자기 프로젝트를 올릴 때도 `tests/`, `fixtures/`, `examples/`, `__tests__/`, `spec/` 아래에
의도적 취약 샘플이나 데모 코드가 흔히 있다. 이걸 실제 취약점과 같은 무게로 block 하면
**신호 대 잡음비가 무너져 사용자가 결과를 신뢰하지 않게 된다.**

**개선 방향:**
1. 관례적 시험 경로(`fixtures/`, `test/`, `tests/`, `spec/`, `__tests__/`, `examples/`, `e2e/`)를 인식해
   해당 경로의 findings 는 **기본적으로 severity 를 한 단계 낮추거나 별도 섹션("시험·예제 코드")으로 분리**.
2. 완전 제외가 아니라 **분리·감등**이 맞다 — 시험 코드에도 진짜 유출이 있을 수 있으니 숨기지는 말 것.
3. 리포트 요약(by_decision)에서 시험 경로 건수를 **본문 판정과 분리 집계**해, "블록 13건"이 실제로는
   "운영코드 0건 + 시험코드 13건"임을 사용자가 바로 알게 할 것.

## B. [오탐/중요] 테스트용 상수를 비밀값으로 판정한다

```
scripts/portal-button-contract-test.mjs:8   [warn/low] "portal-button-contract-token"
scripts/portal-scenario-test.mjs:19          [warn/low] "portal-scenario-local-token"
scripts/portal-scenario-test.mjs:20          [warn/low] "ScenarioAdmin!2026"
```

이 값들은 테스트가 임시 서버에 주입하는 **명백한 가짜 상수**다. 실제 비밀이 아니다.

**개선 방향:**
1. 변수명·주변 문맥에 테스트 신호(`test`, `scenario`, `fixture`, `mock`, `dummy`, `example`, `contract`)가
   있으면 **secret 판정을 warn→info 로 낮추거나 "테스트 상수 추정"으로 표시**.
2. 값 자체의 엔트로피·형식을 함께 볼 것 — `portal-scenario-local-token` 처럼 사람이 읽는 하이픈 라벨은
   실제 API 키(고엔트로피 랜덤)와 형태가 다르다. 지금은 `GOV-SECRET-APIKEY-001` 이 라벨성 문자열도 잡는다.

## C. [정탐이지만 소음] 같은 취약점을 규칙 2개가 중복 보고한다

동일 지점을 KISA 규칙과 GOV 규칙이 각각 올려 건수가 부풀려진다.
```
main.py:96   KISA-PY-INPUT-02 (eval) + GOV-CODE-EXEC-001 (동적 실행)   ← 같은 줄
safe_patterns.py:43  KISA-PY-INPUT-05 + GOV-CMD-INJECTION-001         ← 같은 줄
app.js:6     KISA-JS-API-02 + KISA-JS-INPUT-02                        ← 같은 줄
```
**개선 방향:** 같은 (파일, 줄, 취약 유형)에 복수 규칙이 매칭되면 **하나로 합치고 근거 규칙을 배열로** 표기.
사용자에겐 "1개 문제, 근거 규칙 2개"로 보여야지 "2개 문제"로 보이면 안 된다.

## D. [신규 역량] 흐름 분석 부재 — 이번에 놓친 실제 취약점 4건

체커가 하나도 못 잡았지만 사람이 찾은 실제 취약점. **모두 정규식으로는 안 보이는 흐름·구조 문제**다.

| # | 실제 취약점 | 왜 정규식이 못 보나 |
|---|---|---|
| 1 | **인증 우회**: 개발 모드에서 로그인 링크를 API 응답 본문으로 반환 → 아무나 임의 계정 로그인 | "취약 함수 호출"이 아니라 **응답에 민감정보를 싣는 데이터 흐름** |
| 2 | **경로 경계 우회**: `resolved.startsWith(root)` 가 구분자 없이 접두어만 비교 → 형제 폴더 노출 | 취약한 API 가 아니라 **경계 검사 로직의 미묘한 결함** |
| 3 | **출력 인코딩 누락**: `my-scans.html` 만 `escapeHtml` 없이 사용자 입력을 `innerHTML` 에 | XSS 싱크(`innerHTML`)는 있으나, **소스(사용자 입력)까지 taint 추적**해야 판정 가능 |
| 4 | **보안 헤더 부재**: CSP·X-Frame-Options 없음 → 클릭재킹·토큰 탈취 확대 | **"있어야 할 것이 없는" 부재형 취약점** — 패턴 매칭의 사각지대 |

**개선 방향 (우선순위 순):**
1. **경량 taint 분석**: 최소한 JS 의 `innerHTML`/`outerHTML`/`document.write` 싱크에 대해
   "이 자리에 들어오는 값이 `fetch`/`location`/입력에서 왔는가, 이스케이프를 거쳤는가"를 추적.
   함수 단위 지역 분석만으로도 3번 같은 케이스를 잡을 수 있다. (지금은 `KISA-JS-INPUT-04` 가
   `innerHTML` 존재만 보고 이스케이프 여부는 안 봐서, 안전한 코드도 잡고 위험한 코드도 놓친다.)
2. **경로 경계 안티패턴 규칙**: `startsWith(resolve(DIR))` 뒤에 구분자 검사(`+ sep`)가 없으면 경고.
   이건 흔한 실수라 정규식+간단한 AST 로도 잡을 수 있다.
3. **응답에 실리는 비밀**: `res.json(...)`/`response.end(...)` 인자에 토큰·링크·비밀번호성 필드가
   들어가는지 확인하는 규칙(1번 유형). 흐름 분석이 어려우면 최소한 `dev_login_url`, `token`,
   `password` 같은 키가 응답 객체에 직접 들어갈 때 warn.

## E. [신규 역량] 서버 응답 헤더 점검 (선택)

정적 스캔 범위 밖이지만, 포털처럼 웹 서버 코드를 올리는 경우
`Content-Security-Policy`, `X-Frame-Options`, 쿠키 `Secure`/`HttpOnly`/`SameSite` 설정 여부를
소스에서 추정해 **"보안 헤더 미설정" 정보성 항목**으로 제시하면 가치가 크다.
(4번 취약점이 여기 해당. 지금은 `KISA-PY-SEC-12` 가 파이썬 쿠키만 보고 Node/헤더는 안 본다.)

## F. [잘 된 부분 — 유지]

개선만 적으면 균형이 안 맞으니 명확히 기록한다. 아래는 이번 점검에서 체커가 **정확히 동작**한 부분이다.

- **의존성 점검(`--check-deps`)이 정확했다.** npm 락파일에서 busboy·streamsearch 2개를 정확히 파싱하고
  OSV 조회로 CVE·악성 이력 0건, 설치 스크립트 없음, 쿨다운(버전 나이) 확인까지 리포트에 담았다.
- **외부 통신면(external_surface) 식별이 유용했다.** GitHub 릴리스 다운로드 호출을 "국외/개인정보 인접"
  까지 분류해 보여준 건 공공 도입 검토에 바로 쓸 수 있다.
- **미검사 항목을 정직하게 밝힌다.** `.env`, `package-lock.json` 등을 "검사 안 함"으로 이유와 함께 표기 —
  "판정 불가를 안전으로 속이지 않는다"는 원칙이 잘 지켜졌다.
- **판정 근거·안전한 수정·공공영향·참조(CWE/KISA)** 를 각 finding 에 함께 담아 실무 활용도가 높다.

## 부록: 이번 점검 재현 명령

```bash
# 표준(strict) 프로파일 + 의존성 점검, 판정으로 종료코드 흔들지 않기
gvskb scan . --profile public-default-strict --format json \
  --output <경로>/portal-audit --max-files 20000 --check-deps --fail-on never
```
결과: scanned=112, findings=24 (critical 10 / high 6 / medium 5 / low 3), 전부 픽스처·오탐.
엔진: regex, ruleset digest 는 리포트 `ruleset_version`/`ruleset_digest` 참조.
