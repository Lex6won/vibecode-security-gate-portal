검토 대상:

- `C:\Users\first\Downloads\AI서비스를 서비스답게 만드는UX.pdf`
- 30쪽 PDF

## 핵심 결론

발표자료의 핵심은 “AI가 만든 기능을 사람이 쓸 수 있는 서비스로 바꾸려면 상태, 흐름, 예외, 근거, 피드백을 사람이 설계해야 한다”는 것이다.

현재 공공 바이브코딩 보안 체커 화면은 첫 화면과 기본 동선은 많이 좋아졌지만, 아직 다음 네 가지가 부족하다.

1. 정상 상황 외 상태 설계
2. 검사 결과의 근거 설명
3. 오탐·과탐을 다루는 피드백 루프
4. 제출 가능/불가의 경계와 책임 주체 명시

따라서 이 자료에서 가장 강하게 반영해야 할 것은 색감보다 UX 구조다.

## 발표자료에서 뽑은 적용 원칙

### 1. 첫 화면은 “무엇을 할 수 있는지” 먼저 말해야 한다

발표자료는 첫 화면에서 가능한 일을 명확히 밝히지 않으면 사용자가 기대를 잘못 세우고, 결과가 맞지 않을 때 서비스 신뢰를 잃는다고 설명한다.

현재 반영 상태:

- 첫 화면은 `빠른 점검`, `표준 점검`, `하네스 및 MCP 등록`, `관리자 현황 확인`으로 정리되어 있어 방향은 좋다.

추가 반영 필요:

- 각 선택지에 “무엇을 해주는지”뿐 아니라 “무엇을 하지 않는지”를 짧게 넣어야 한다.
- 예:
  - 빠른 점검: 제출 파일 생성 없음
  - 표준 점검: 보고서 생성, 제출 패키지 없음
  - 제출 점검: ZIP 생성
  - MCP 등록: 개발 중 점검 지원, 최종 제출 점검 대체 아님

### 2. AI 결과는 단정하지 말고 근거와 책임 주체를 보여줘야 한다

발표자료는 AI 추천 결과에서 근거 없이 높은 적합도만 보여주는 방식을 문제로 본다. 보안 체커도 같은 위험이 있다.

적용 방향:

- 결과 카드에 `왜 탐지했는지`, `어떤 파일/줄/패턴 때문인지`, `자동 판정인지 사람 검토 대상인지`를 함께 보여준다.
- `위험 0건`도 “검사한 범위 내에서”라는 범위를 표시한다.
- `사람 검토 필요`은 실패가 아니라 신뢰성을 위한 별도 상태로 표현한다.

필요 UI:

- 결과 상세 패널
  - 탐지 룰
  - 위치
  - 근거
  - 신뢰도
  - 오탐 가능성
  - 권장 조치
  - 재점검 버튼

### 3. 빈 화면은 막다른 골목이 아니라 다음 행동을 제공해야 한다

발표자료는 결과 0건 화면을 중요한 상태로 본다. 보안체커에서는 두 종류의 0건이 있다.

- 정말 발견 항목이 없는 상태
- 검사 대상이 없거나 검사 제외되어 0건인 상태

적용 방향:

- `위험 항목 없음` 상태에는 다음 행동을 제공한다.
  - HTML 보고서 확인
  - JSON 증거 보고서 저장
  - 제출 점검으로 전환
  - 관리자 현황에 기록
- `검사된 파일 0개`는 안전이 아니므로 강한 경고로 분리한다.

필요 UI:

- Empty state 카드
  - 제목: `검사된 위험 항목이 없습니다`
  - 보조: `검사 범위와 제외 파일을 확인하세요`
  - 버튼: `보고서 열기`, `제출 점검으로 전환`, `다시 선택`

### 4. 사용자가 결과를 고칠 수 있는 피드백 루프가 필요하다

발표자료는 추천 결과가 마음에 들지 않을 때 사용자가 즉시 보정할 수 있어야 한다고 말한다. 보안체커에서는 오탐·과탐 피드백이 여기에 해당한다.

적용 방향:

- 각 탐지 항목에 사용자가 선택할 수 있는 피드백을 둔다.
  - `실제 위험`
  - `오탐 의심`
  - `사람 검토 요청`
  - `수정 후 재점검`
- 이 피드백은 관리자 화면에서 반복 오탐 후보와 룰 개선 후보로 집계한다.

필요 UI:

- 탐지 항목 액션
  - 오탐 의심 표시
  - 검토 메모
  - 재점검 예약
  - 룰 개선 요청

### 5. 정상 화면 하나가 아니라 상태 명세서가 필요하다

발표자료의 가장 직접적인 적용 항목이다.

보안체커에 필요한 상태:

1. 정상 대기
2. 대상 선택 완료
3. 검사 중
4. 검사 완료
5. 위험 항목 없음
6. 수정 필요
7. 사람 검토 필요
8. 네트워크 실패
9. GitHub 권한 없음
10. 의존성 점검 실패
11. 검사된 파일 0개
12. 중복 클릭 방지
13. 저장 위치 권한 없음
14. 관리자 권한 없음

현재 부족한 부분:

- 진행 상태는 있으나 실패, 빈 결과, 권한 없음, 중복 클릭 방지 상태가 화면 설계로 충분히 드러나지 않는다.

우선 반영할 상태:

- 검사 중에는 점검 방식 버튼 비활성화
- 중복 클릭 시 `이미 검사 중입니다`
- 네트워크 실패 시 `로컬 코드 검사는 완료, 의존성/OSV 조회 실패`
- GitHub 권한 없음 시 `URL 접근 권한 확인`
- 검사된 파일 0개 시 `안전 판정 불가`

### 6. 서비스 경계와 책임을 명확히 해야 한다

발표자료는 사용자가 오해하지 않도록 “할 수 있는 일”과 “승인/확정이 필요한 일”을 나누라고 한다.

보안체커의 경계:

- 체커는 보안 위험 신호를 찾고 제출 보고서를 만든다.
- 체커 결과는 공식 보안적합성 심사를 대체하지 않는다.
- `사람 검토 필요`는 제출 전 담당자가 판단해야 한다.
- MCP 등록은 개발 중 보안 점검을 돕지만, 최종 제출 전 점검을 대체하지 않는다.

필요 UI:

- 보안 점검 화면 결과 영역에 짧은 게이트 문구
  - `수정 필요 또는 사람 검토 항목이 남으면 제출 가능 상태가 아닙니다.`
- 도움말에 `체커가 하는 일 / 하지 않는 일` 항목 추가

## 현 화면별 적용 제안

### 첫 화면

좋은 점:

- 4개 시나리오가 명확하다.
- 문장 수를 줄여 서비스 화면에 가까워졌다.

보완:

- 카드별 “결과물”을 한 줄 배지로 보여준다.
  - 빠른 점검: `위험 신호`
  - 표준 점검: `HTML·JSON`
  - MCP 등록: `개발 중 점검`
  - 관리자: `기관 이력`
- 하단에 긴 설명 대신 작은 게이트 문구 하나만 둔다.
  - `제출 전에는 표준 또는 제출 점검을 완료하세요.`

### 보안 점검 화면

좋은 점:

- 대상 선택과 점검 방식이 같은 화면에 있다.
- 점검 카드 클릭으로 바로 실행되는 흐름은 발표자료의 “사용자 행동 중심”과 맞다.

보완:

- 검사 중 상태를 더 명확히 해야 한다.
- 결과 없음, 실패, 권한 없음, 검사 파일 0개 상태를 별도 카드로 설계해야 한다.
- 탐지 결과에 근거와 오탐 피드백을 추가해야 한다.

### 하네스 및 MCP 화면

좋은 점:

- 실행 버튼을 상단에 올린 것은 좋다.
- 설치 전 미리보기와 검증 흐름은 발표자료의 CHECK 단계와 맞다.

보완:

- `설치 전`, `설치 중`, `검증 완료`, `실패` 상태를 명확히 보여줘야 한다.
- 설치 대상 파일과 변경 내용 미리보기를 카드로 보여준다.
- MCP 등록은 “개발 중 점검 지원”이라는 경계를 함께 표기한다.

### 관리자 화면

좋은 점:

- 오늘 점검, 제출 가능, 수정 필요, 사람 검토로 요약된다.
- 지표 클릭으로 필터가 바뀌는 구조는 좋다.

보완:

- 반복 오탐 후보, 반복 취약 룰, 검사 실패 사유를 별도 탭 또는 카드로 보여준다.
- `수정 필요`와 `사람 검토`는 관리자가 가장 먼저 봐야 하므로 기본 정렬 우선순위를 높인다.
- 다운로드 이력보다 “제출 차단 사유”가 먼저 보여야 한다.

### 도움말

좋은 점:

- 게시판형 구조는 적합하다.

보완:

- 문서형 설명보다 상황형 질문으로 바꾼다.
  - `검사된 파일이 0개라고 나와요`
  - `GitHub URL 접근이 안 돼요`
  - `오탐 같으면 어떻게 하나요`
  - `MCP 등록 후에도 최종 점검이 필요한가요`

## 발표자료 디자인에서 반영할 만한 것

### 반영 권장

1. 4개 카드 구조
   - 이미 첫 화면에 맞다.
   - 카드 번호, 짧은 제목, 한 줄 설명, 실행 버튼으로 통일한다.

2. 하단 핵심 문장 바
   - 발표자료의 강조 문장 바를 보안 게이트 안내로 활용한다.
   - 예: `검사된 파일 0개는 안전 판정이 아닙니다.`

3. 선택 카드 강조 테두리
   - 노란색 대신 현재 서비스의 `herb` 또는 `harbor`를 사용한다.
   - 선택된 점검 방식, 관리자 필터, MCP 실행 상태에 사용한다.

4. Before / After 비교 구조
   - 도움말 또는 관리자 룰 개선 화면에 적합하다.
   - 예: `오탐 신고 전 / 룰 개선 후`

5. 상태 카드 그리드
   - 보안 점검 상태 명세 페이지 또는 도움말에 적합하다.
   - 정상, 로딩, 결과 없음, 실패, 권한 없음, 중복 클릭 방지를 카드로 설명한다.

### 제한적으로 반영

1. 검은 배경
   - 발표자료에는 강하지만, 공무원 업무 서비스 전체에 쓰면 피로도가 높다.
   - 전체 배경이 아니라 보안 게이트, 경고, 제출 차단 영역에만 사용한다.

2. 노란 강조색
   - 경기도 톤과 현재 `herb` 포인트가 있으므로 노란색을 그대로 쓰지 않는다.
   - 중요한 경고에는 `warn`, 선택 강조에는 `herb`, 링크/포커스에는 `harbor`를 유지한다.

3. 영문 대문자 섹션 라벨
   - 발표용으로는 좋지만 일반 공무원 서비스에서는 장식처럼 보일 수 있다.
   - 필요하면 작은 보조 라벨로만 사용한다.

## 우선순위

### 1순위

- 보안 점검 화면에 상태 명세 반영
- 검사 중/실패/결과 없음/검사 파일 0개/권한 없음/중복 클릭 상태 설계

### 2순위

- 결과 상세에 근거 설명과 오탐 피드백 추가
- 관리자 화면에 반복 오탐 후보와 룰 개선 후보 추가

### 3순위

- 첫 화면 카드에 결과물 배지 추가
- 도움말을 상황형 질문 중심으로 재정리

### 4순위

- 발표자료의 카드 디자인과 하단 핵심 문장 바를 현재 경기도 톤에 맞게 제한 반영

## 바로 적용 가능한 작은 변경

1. 첫 화면 4개 카드에 결과물 배지 추가
2. 보안 점검 결과 영역에 게이트 문구 추가
3. 보안 점검 화면에 숨겨진 상태 카드 샘플 추가
4. 도움말 질문을 상황형 문장으로 수정
5. 관리자 화면에 `반복 오탐 후보` 요약 지표 추가
