# 화면·기능 설계서: 공공 코드 보안검사 게이트

## 사용자 흐름

1. 사용자가 앱을 연다.
2. 첫 화면에서 서비스 목적, 현재 체커 상태, 검사 입력 영역을 확인한다.
3. 로컬 폴더, 압축파일, GitHub URL 중 하나를 선택한다.
4. 앱이 검사 목적을 자동 추천한다.
5. 사용자가 `검사 시작`을 누른다.
6. 앱이 진행 상황과 누락된 조건을 보여준다.
7. 결과 화면에서 제출 가능 여부와 수정 필요 항목을 확인한다.
8. 필요하면 항목별 수정 방향을 확인하고 재검사한다.
9. 표준 점검이 완료되면 HTML, JSON, Markdown 보고서를 확인하고 저장한다.
10. 보안팀 또는 AX 담당자에게 제출한다.

## 1차 화면 범위

1차 화면은 웹 UI 기반 로컬 웹앱 기준으로 설계한다. Python 기반 체커 엔진은 로컬 백엔드가 호출하고, 사용자는 별도 Python 명령어를 몰라도 검사를 실행할 수 있어야 한다. 필요하면 동일 화면을 데스크톱 앱으로 포장한다.

1차 포함 화면:

- 메인 검사 화면
- 하네스 준비 화면
- 진행상황 레이어
- 결과 요약 화면
- 상세 결과 화면
- 의존성 화면
- 오탐 검토 화면
- 연결 진단 및 체커 상태 화면
- 하네스 설치 및 MCP 등록 화면

1차 제외 화면:

- MCP 고급 자동복구 화면
- 중앙 웹 포털 관리자 화면
- 보안팀 검토 큐
- LLM 설명 생성 화면

## 메인 화면 구성

첫 화면은 검사 입력 화면이 아니라 서비스 선택 허브다. 사용자는 여기서 이 서비스가 “공공 업무 도구 개발, 보안점검, 제출 준비를 이어서 돕는 시작센터”라는 점을 바로 이해하고, `업무 도구 만들기`, `만든 소스 보안검사`, `기존 프로젝트 이어가기` 중 하나를 선택한다.

`만든 소스 보안검사`를 누른 뒤에 검사 대상 입력, 검사 시작, 결과 확인, 보고서 다운로드 흐름을 보여준다. 즉 첫 화면은 이해와 선택을 담당하고, 보안검사 화면은 실제 검사 작업을 담당한다.

모든 핵심 화면은 한 화면 안에서 스크롤 없이 사용할 수 있어야 한다. 진행상황, 변경 내용, 승인, 오류, 상세 결과는 본문 아래에 추가하지 않고 레이어 팝업으로 표시한다. 자세한 기준은 `docs/11_single_view_modal_design.md`를 따른다.

상단 영역:

- 서비스명: 공공 코드 보안검사 게이트
- 한 줄 설명: “소스나 GitHub URL을 넣으면 제출 전 보안 점검 보고서를 만듭니다.”
- 체커 상태: 엔진, 룰셋, 인텔 데이터, 네트워크 연결 상태
- 하네스 상태: 미설치, 설치됨, 검증 필요, 업데이트 가능
- 업데이트 상태: 최신, 업데이트 가능, 검증 필요, 오프라인

서비스 안내 영역:

- “무엇을 해주나요?”: 소스코드와 의존성을 검사하고 제출 가능한 보안 점검 보고서를 만든다는 설명
- “무엇을 넣으면 되나요?”: 로컬 폴더, 압축파일, GitHub URL 예시
- “결과는 어떻게 보나요?”: 수정 필요, 사람 검토 필요, 검사 미완료, 제출 가능 상태 설명
- “제출은 무엇을 하나요?”: HTML 보고서와 JSON 증거 보고서 2종을 기본 제출한다는 안내
- “처음이면 이렇게 하세요”: 1. 대상 선택, 2. 검사 시작, 3. 수정/재검사, 4. 보고서 다운로드
- 안내 영역은 접을 수 있어야 하며, 처음 실행하거나 검사 이력이 없을 때는 펼친 상태로 보인다.

하네스 준비 영역:

- 기존 하네스 설치 여부 표시
- `하네스 설치` 버튼
- `하네스 검증` 버튼
- 설치 출처: 공식 GitHub 저장소 또는 검증된 릴리스
- 설치 위치 선택
- 검증 결과: 통과, 실패, 업데이트 필요
- 프로젝트에 하네스 파일을 적용하는 기능은 별도 고급 옵션으로 숨기고, 적용 전 변경 파일 목록을 보여준다.

검사 입력 영역:

- `로컬 폴더 선택`
- `압축파일 선택`
- `GitHub URL 입력`
- 최근 검사 대상 목록
- 비공개 저장소 안내: 토큰 저장 없이 별도 인증 흐름 또는 수동 압축파일 권장

검사 목적 영역:

- `개발 중 빠른 점검`
- `개발 완료 표준 점검`
- 표준 점검 결과 확인
- 기본 추천: 제출 전에는 `표준 점검`

진행 영역:

- 진행상황 레이어로 표시
- 단계별 진행률
- 현재 검사 중인 범위
- 검사 제외 또는 실패 항목 즉시 표시
- 중단, 다시 검사, 로그 보기

결과 요약 영역:

- 상태 배지: 제출 가능, 수정 필요, 사람 검토 필요, 검사 미완료
- 수정 필요 건수
- 사람 검토 필요 건수
- 오탐 후보 건수
- 의존성 위험 건수
- 검사 범위 요약

제출 영역:

- HTML 보고서 다운로드
- JSON 증거 보고서 다운로드
- Markdown 보고서 다운로드
- SARIF 내보내기: CI 또는 GitHub code scanning 연동이 필요한 경우에만 표시

## 구버전 감지와 업데이트 화면

`상태 점검 시작`은 읽기 전용이다. 이 버튼은 설치, 업데이트, MCP 설정 변경을 수행하지 않는다.

과거 버전이 확인되면 같은 화면 아래가 아니라 `업데이트 미리보기` 레이어를 표시한다.

업데이트 미리보기 필수 표시:

- 업데이트 대상: 하네스, 체커, 룰셋, 인텔, MCP 설정
- 현재 버전
- 최신 안정 버전
- 업데이트 출처: 공식 릴리스, 승인된 commit, 검증된 manifest
- 변경 요약
- 룰 변경 영향
- 오탐/과탐 영향 가능성
- 검증 상태: 검증 완료, 검증 대기, 관리자 검증 필요
- 적용 후 재검증 항목: 하네스 검증, `gvskb doctor`, MCP 연결 테스트, 대표 fixture smoke scan

업데이트 적용 절차:

1. 상태 확인
2. 변경 내용 보기
3. 사용자 승인
4. 업데이트 적용
5. 재검증
6. 결과 표시

상태별 CTA:

| 상태 | 화면 문구 | 기본 버튼 |
|---|---|---|
| 최신 | 최신 안정 버전입니다. | 조치 없음 |
| 업데이트 가능 | 최신 안정 버전이 있습니다. 변경 내용을 확인하세요. | 변경 내용 보기 |
| 업데이트 권장 | 최신 룰셋과 취약점 정보를 반영할 수 있습니다. | 업데이트 적용 준비 |
| 검증 필요 | 새 버전이 있지만 아직 검증이 끝나지 않았습니다. | 관리자 검증 보기 |
| MCP 재등록 필요 | 체커 경로가 바뀌어 개발 도구 연결을 다시 확인해야 합니다. | MCP 다시 등록 |
| 네트워크 실패 | 업데이트 정보를 확인하지 못했습니다. 방화벽 또는 프록시를 확인하세요. | 연결 진단 |

업데이트 화면 금지:

- 상태 점검 직후 자동 업데이트
- GitHub `main` 브랜치 실시간 반영
- 사용자 승인 없는 `git pull`
- 사용자 승인 없는 Python 패키지 설치
- 사용자 승인 없는 MCP 설정 변경
- 업데이트 실패를 정상 또는 최신으로 표시

## 주요 상태와 문구

제출 가능:

- “제출 전 전체 점검이 완료됐습니다. HTML 보고서와 JSON 증거 보고서를 제출하세요.”

수정 필요:

- “수정해야 할 보안 항목이 있습니다. 위험도가 높은 항목부터 확인하세요.”

사람 검토 필요:

- “자동으로 확정하기 어려운 항목이 있습니다. 코드 맥락을 확인한 뒤 보안 담당자 검토가 필요합니다.”

검사 미완료:

- “검사가 끝나지 않았습니다. 검사하지 못한 파일이나 의존성이 있어 제출 가능으로 볼 수 없습니다.”

업데이트 검증 필요:

- “새 업데이트가 있지만 아직 안정 채널 검증이 끝나지 않았습니다.”

## 제외 기능

- 검사 결과를 공식 승인으로 표시
- 사용자 동의 없는 소스 업로드
- 비밀값 원문 저장
- `main` 브랜치 실시간 자동 업데이트
- 사용자 동의 없는 하네스 설치 또는 프로젝트 파일 변경
- LLM API 기반 보안 판정 또는 자동 설명 생성
- MCP 고급 자동복구와 기관 일괄 배포
- 검토 없이 오탐 항목을 영구 무시
- 검사 실패를 통과로 처리
- 결과 보고서에 원본 소스를 기본 포함하지 않음

## Figma 화면 설계 방향

Figma로 옮길 때 권장하는 첫 화면은 “단순한 서비스 선택 허브”다.

- 상단: 서비스명, 한 줄 설명, 최소 상태 표시
- 중앙: “오늘 무엇을 하시겠어요?” 질문과 핵심 선택지 3개
- 하단: 처음 사용자용 짧은 안내
- 색상: 공공 업무용 중립 배경, 위험도별 색상만 제한적으로 사용
- 컴포넌트: 큰 선택 버튼, 상태 badge, 단계 흐름 chip, 단일 CTA
- 피해야 할 것: 복잡한 3열 대시보드, 과한 일러스트, 보안 용어가 가득한 첫 화면, 카드 안의 카드
## 보강: 메인 대시보드 UX 원칙

메인 화면은 검사 입력 화면을 넘어 “공공 바이브코딩 시작센터” 역할을 해야 한다. 다만 첫 화면은 여러 패널을 동시에 보여주는 대시보드가 아니라, 사용자가 한 번에 하나의 결정을 내리는 서비스 선택 화면을 기본으로 한다.

첫 화면 필수 구성:

1. 서비스 설명: 설계부터 제출 준비까지 도와주는 하네스 시작점이라는 설명
2. 할 일 선택: 보안검사만 하기, 하네스로 개발 시작, 기존 프로젝트 이어가기
3. 하네스 가능 업무 안내: 설계, 구현, 테스트, 검증, 배포지원
4. 진행 흐름 안내: 설계, 구현, 테스트, 검증, 배포지원
5. 제출 안내: 보안검사 선택 이후 HTML 보고서와 JSON evidence를 내려받을 수 있다는 설명

각 선택지는 “누르면 다음에 무엇이 일어나는지”를 함께 보여준다. 내부 용어는 보조 정보로 낮추고, 공무원에게는 다음 행동 중심으로 보여준다.

보안검사 선택 후 기본 구조:

1. `할 일 선택`
2. `대상 넣기`
3. `결과 받기`

첫 화면에서는 좌우 보조 패널, 최근 작업, 상세 상태 카드, 제출 카드, 결과 설명 카드를 동시에 보여주지 않는다. 해당 정보는 선택 이후 단계별로 노출한다.
