**B2 주의:** GPKI 기관 인증서로는 Windows Authenticode 서명이 불가하다(용도가 다름). 상용 OV 또는 EV 코드서명 인증서가 별도로 필요하며, EV는 하드웨어 토큰 보관 의무가 있어 CI 자동 서명 설계가 달라진다. 1차에 확보가 어렵다면 **기관 자산관리·Intune 중앙배포 + 해시 공지**를 임시 경로로 쓰되, 이는 §4의 신뢰 루트를 "설치 시점 기관 배포 신뢰"로 낮추는 결정이므로 명시적으로 기록한다.

**망 환경 확정 (2026-08-11)**

경기도는 물리적 망분리가 아니라 **논리적 망분리**이며 망연계(망중계) 서버가 있다. **그 방식은 파일전송 스트리밍이다.**

| 확정 사실 | 설계에 미치는 영향 |
|---|---|
| **파일전송 스트리밍 방식** | 파일 단위로 연속 전송된다. 배치 대기가 없어 반입 주기를 일 단위까지 짧게 가져갈 수 있고, 대용량도 나눠 보낼 수 있다 |
| **서비스(프로토콜) 중계는 없다** | `git clone`·미러 push·실시간 API 질의 등 **세션형 통신은 통과하지 않는다** |
| 직접 아웃바운드 금지 | `network-profile.yaml` admin-network: `external_outbound: none` |

따라서 §8.1은 **파일 반입 모드로 확정**한다. 남은 것은 능력이 아니라 **규격 확인**이다 — 허용 확장자(EXE·ZIP 차단 여부), 파일 크기 상한, 압축 중첩 제한, 반복 반입 채널 등록 가능 여부.

**이 확정이 결정하는 것**

- 행정망 사용자 PC의 **GitHub URL 점검은 지원하지 않는다.** 기능 자체가 성립하지 않는다.
- 위협정보·릴리스는 **파일 번들로 반입**한다. 스트리밍이므로 §8.3의 인텔 TTL(14일)을 여유 있게 지킬 수 있다.
- 공공 GitLab·GitHub은 **인터넷망 구간에서만** 접근한다. 행정망 서버가 저장소를 직접 바라보는 구성은 성립하지 않는다(§10.1).
- 사람이 매체로 나르는 전제는 여전히 필요 없다. 반입은 파일전송으로 자동화된다(§8.2).

17번 문서 §7.4의 "필요한 IP·포트를 방화벽에서 허용할 수 있다"는 전제는 폐기한다. 방화벽 예외가 아니라 **파일 반입**이 정규 경로다.

## 3. 목표 아키텍처

### 3.1 전체 구조

```text
[개발·검증 구간 — 인터넷망]
  GitHub 원본 (checker / harness / agent)
    -> PR · 하네스 게이트 · 체커 적대적 검증 · 시나리오 테스트
    -> 사람 승인 -> tag / immutable release
    -> CI: 패키지 빌드 + SBOM + SHA-256 + Authenticode 서명
    -> 오프라인 서명 PC: release manifest에 Ed25519 detached 서명
    -> 반입 매체 또는 승인된 단방향 연계

[경기도 내부 서버 — 행정망]
  gg-security-portal  (Rocky Linux 9 / podman-rootless / nginx / FastAPI / PostgreSQL 16)
    - 승인 번들 레지스트리 (manifest + 패키지 파일 배포)
    - 서비스 안내 · 설치 파일 다운로드
    - 익명 점검 메타데이터 수신
    - 관리자 화면 (OIDC 인증)
    * 사용자 PC의 로컬 API를 절대 호출하지 않는다

[사용자 Windows PC]
  gg-security-agent  (단일 서명 EXE / 사용자 권한 설치)
    - 로컬 UI: 에이전트가 자기 자신이 서빙 (same-origin)
    - 내장 Python 3.12 + gvskb + 룰셋·인텔
    - 내장 하네스 스냅샷
    - 폴더 / ZIP / (인터넷망 한정) GitHub 점검
    - 보고서를 사용자 선택 폴더에 저장
    - 동의 시 익명 메타데이터만 포털로 송신
```

### 3.2 핵심 결정 D1 — 브라우저는 로컬 API를 호출하지 않는다

코덱스 제안의 *"포털이 설치 완료를 자동 확인하고 웹 버튼이 이미 설치된 에이전트와 연결"* 은 **채택하지 않는다.**

원격 origin(경기도 서버 페이지)이 `127.0.0.1`을 호출하는 구조는 DNS rebinding과 임의 사이트의 로컬 제어 시도를 열어 준다. 보안 점검 도구가 그 통로를 만드는 것은 자기모순이다.

대신 다음으로 동일한 사용자 경험을 만든다.

```text
포털의 [보안 에이전트 설치] 버튼
  -> 서명된 설치 파일 다운로드
  -> 사용자가 실행 · Windows 설치 확인
  -> 설치 관리자가 마지막 단계에서 로컬 UI를 자동으로 연다
  -> 이후 사용자는 시작 메뉴 / 트레이 아이콘으로 로컬 UI를 연다
```

- 브라우저가 설치 여부를 탐지할 필요가 **없다.** 설치 관리자가 화면을 넘긴다.
- 로컬 UI 페이지는 **에이전트 자신이 서빙**하므로 same-origin이다. 원격 origin과의 교차 호출이 존재하지 않는다.
- 17번 문서의 `vibecode-gate://` 커스텀 스킴은 **1차 범위에서 제외한다.** 커스텀 스킴은 임의 웹페이지가 트리거할 수 있어 CORS로 막은 위험을 뒷문으로 되돌린다. 향후 도입 시에는 "화면 열기 전용 · 파라미터는 allowlist된 뷰 이름만 · 상태 변경 동작 금지"를 요건화한다.
- 중앙 포털의 "설치 상태" 화면은 **안내와 최신 승인 버전 표시까지만** 한다. 사용자 PC 상태는 로컬 UI에서만 보여준다.

### 3.3 핵심 결정 D2 — 에이전트 구현 언어

`institution-profile.yaml`의 허용 구현 언어는 python / javascript / typescript이며, 그 외는 `needs-review-and-approved-track-rewrite`다. 네이티브 WebView2 호스트(C#/.NET, Rust)는 **예외 신청 대상**이므로 1차에서 제외한다.

1차 에이전트 = **Node.js 20.19+ 단일 실행 파일(SEA) + 내장 Python 3.12**

- 로컬 UI는 사용자의 기본 브라우저에서 `http://127.0.0.1:<port>` 로 연다. 페이지 제공자가 에이전트 자신이므로 D1의 안전성이 유지된다.
- 트레이 상주는 1차에서 하지 않는다(코덱스 1차 범위와 동일). 필요할 때 실행하고, 유휴 30분 후 자동 종료한다.
- 장기적으로 WebView2 네이티브 호스트가 필요하면 그때 예외 신청과 함께 검토한다. **점검 엔진과 화면은 그때도 재작성하지 않는다.**

### 3.4 핵심 결정 D3 — 3단 접근 계층 (설치 없이 되는 것부터)

**전제:** 사용자는 Python이 없을 수 있고, AI 도구가 없을 수도 있으며, 에이전트를 설치하기 전에 웹에서 하네스·체커 설정 파일을 처음 접할 가능성이 높다. 설치를 첫 관문으로 두면 대부분의 사용자가 거기서 멈춘다.

따라서 서비스를 **설치 요구 수준에 따라 3단으로 나눈다. 아래 단계는 위 단계 없이 독립적으로 가치를 낸다.**

| 계층 | 필요한 것 | 할 수 있는 일 | 결과물의 지위 |
|---|---|---|---|
| **T0 — 설치 없음** | 브라우저만 | 하네스 파일 열람·내려받기, 체커 규칙 카탈로그 열람, 샘플 보고서 열람, 브라우저 사전점검 체험 | 참고용. **제출용 보고서 발급 없음** |
| **T1 — 에이전트 설치** | 서명된 에이전트 1회 설치 | 폴더·ZIP 정식 점검, HTML·JSON·MD 보고서 발급, 컴포넌트 설치·업데이트 | 제출 판단용 공식 보고서 |
| **T2 — AI 도구 연동(선택)** | Codex / Claude Code / Claude Desktop 보유 | 개발 중 체커 MCP 호출 | 개발 단계 수정 안내 |

**T0가 T1의 광고가 아니라 독립 기능이다.** 하네스는 파일이므로 T0에서 완결된다. AI 도구가 없는 사용자는 T2 없이도 서비스를 온전히 쓴다.

첫 화면은 `보안 에이전트 설치`가 아니라 **지금 바로 할 수 있는 것**을 먼저 보여준다.

```text
[1] 개발 기준 받기       하네스 ZIP 내려받기 · 웹에서 먼저 읽어보기   (설치 없음)
[2] 내 코드 점검하기     보안 에이전트 설치 → 폴더·ZIP 점검·보고서    (1회 설치)
[3] AI 도구에 연결하기   체커 MCP 등록                               (AI 도구 있는 경우만)
```

`[3]`은 지원 AI 도구가 PC에 없으면 카드 자체를 흐리게 표시하고 "이 기능은 Codex·Claude Code·Claude Desktop을 쓰는 경우에만 필요합니다"로 안내한다. 없는 것을 결핍처럼 보이게 하지 않는다.

#### 3.4.1 T0 — 하네스 열람과 내려받기 (Python·AI 불필요)

하네스는 실행 프로그램이 아니라 **개발 기준 문서와 템플릿, 검증 스크립트의 묶음**이다. 사용자는 프로젝트 폴더에 압축을 푸는 것만으로 적용할 수 있다.

- **웹 뷰어**: 읽기 전용. 파일 20여 개를 그대로 나열하지 않고 역할별 3묶음으로 접어서 보여준다.

  | 묶음 | 내용 | 대상 |
  |---|---|---|
  | 내가 지켜야 할 개발 기준 | 사람이 읽는 한국어 요약 (금지 사항, 커밋 전 확인 목록) | 공무원 본인 |
  | AI 도구가 읽는 파일 | `AGENTS.md`, `.claude/`, 템플릿 원문 | AI 도구 사용자 |
  | 기관이 정한 정책 | `institution-profile.yaml`, 허용 언어·DB·트랙 | 담당·검토자 |

- 모든 파일 상단에 **"이 파일이 하는 일" 한 줄 설명**을 붙인다. 원문만 보여주면 공무원은 첫 화면에서 이탈한다.
- **웹에서 편집·저장 기능은 두지 않는다.** 기관 표준이 사용자별로 갈라지면 하네스의 존재 이유가 없어진다. 필요한 조정은 예외 신청 절차로 간다.
- **`하네스 ZIP 내려받기`**: 서버가 승인 번들의 하네스 스냅샷을 그대로 압축해 제공한다. 파일에 버전 스탬프를 넣어 나중에 체커가 어떤 하네스 버전이 적용됐는지 식별할 수 있게 한다. ZIP의 SHA-256을 화면에 함께 표시해 사용자가 무결성을 확인할 수 있게 한다.
- 사용 안내는 한 문장으로 끝나야 한다: *"프로젝트 폴더에 압축을 풀면 적용됩니다."*

#### 3.4.2 T0 — 체커 규칙 카탈로그와 샘플 보고서

- 체커가 무엇을 어떻게 검사하는지 규칙 단위로 열람한다: 규칙 ID, 한국어 설명, 위험 예시, 안전한 수정 방향.
- 서버는 승인 번들 빌드 시 룰셋에서 **정적 JSON 카탈로그**를 생성해 배포한다. 조회 시 체커를 실행하지 않는다.
- 샘플 보고서(HTML) 전문을 공개한다. 사용자가 설치 전에 "결과물이 어떻게 생겼는지"를 보고 판단할 수 있어야 한다.
- 이 두 가지는 설치 없이도 교육·검토 자료로 독립적인 가치가 있다.

#### 3.4.3 T0 — 브라우저 사전점검 (체험)

설치 전에 위험 신호를 즉시 체감할 수 있는 경량 점검을 제공한다. **소스 미전송 원칙을 깨지 않는다.**

| 항목 | 규칙 |
|---|---|
| 실행 위치 | 브라우저 JavaScript. 파일 내용은 탭 메모리에만 존재 |
| 전송 차단 | 이 페이지는 **`Content-Security-Policy: connect-src 'none'`** 로 제공한다. fetch·XHR·WebSocket·비콘이 기술적으로 불가능하다 |
| 페이지 분리 | 텔레메트리와 API를 쓰는 다른 화면과 **별도 경로**로 분리한다 |
| 검사 범위 | 하드코딩 비밀값·API 키·개인정보 패턴 등 정규식으로 확정 가능한 규칙만 |
| 규모 상한 | 파일 수·총 크기 상한을 두고 초과 시 정식 점검으로 안내 |
| 결과 성격 | **positive-only 신호.** "발견되면 확실히 문제, 발견되지 않아도 안전이 아님" |
| 산출물 | 화면 표시만. **파일 보고서를 발급하지 않는다** |

결과 화면 상단에 고정 배너를 둔다: *"맛보기 점검입니다. 제출·배포 판단에는 쓸 수 없습니다. 발견 사항이 없어도 안전하다는 뜻이 아닙니다."*

`connect-src 'none'`은 말이 아니라 브라우저가 강제하는 보증이다. "우리를 믿어 달라"가 아니라 **"기술적으로 보낼 수 없다"** 를 사용자에게 보여줄 수 있다는 점에서 이 방식을 택한다.

### 3.5 핵심 결정 D4 — AI 비의존 원칙

**포털 서버와 체커 결과 설명은 어떤 단계에서도 LLM을 호출하지 않는다.**

- `network-profile.yaml` admin-network는 `llm_api: "직접 불가"`다. 행정망 서버에서 AI 접근이 막혀도 **기능이 하나도 줄지 않아야 한다.**
- 보고서의 한국어 설명·수정 안내는 체커 룰셋에 내장된 정적 문구를 쓴다. 이미 `vibecode-checker`가 그 방향으로 설계되어 있다.
- 이는 제약이 아니라 이점이다. 같은 코드에 같은 설명이 나오므로 **재현 가능하고 감사 가능하다.** 결재 문서로 쓰이는 산출물에 LLM 생성 문장이 매번 달라지면 안 된다.
- AI 도구 연동(T2)은 **사용자 PC의 AI 도구가 체커를 호출하는 방향**이다. 서버나 체커가 AI를 호출하는 방향이 아니다. 방향을 혼동하지 않는다.

### 3.6 배포본 3종과 설치 부담 완화

| 배포본 | 크기(예상) | 용도 |
|---|---|---|
| **온라인 경량 설치본** | 약 40~60MB | 기본. 에이전트 코어 + UI만. 체커 런타임은 첫 점검 시 포털에서 내려받아 설치 |
| **전체 포함 오프라인 설치본** | 약 180~240MB | 폐쇄망·다운로드 제한 PC. 모든 컴포넌트 포함 |
| **무설치 포터블 ZIP** | 전체 포함본과 동일 | 설치 정책상 EXE 실행이 제한된 PC. 압축 해제 후 실행 |

- 첫 다운로드를 40MB대로 낮추면 행정망에서의 체감 부담이 크게 줄어든다.
- 세 배포본 모두 **같은 서명과 같은 manifest 검증 경로**를 쓴다. 포터블이라고 검증을 건너뛰지 않는다.
- 경량 설치본은 체커 런타임 설치 실패에 대비해 "전체 포함본 받기" 링크를 실패 화면에 노출한다.

**패키지 크기 예상 근거:** Node SEA 약 110MB + Python 3.12 embeddable 약 15MB + gvskb 및 의존성 약 40~80MB + 룰셋·인텔 번들 약 10~30MB. Git 포터블 포함 시 +45MB이며 행정망 빌드는 Git을 제외한다(§8). M3에서 실측하여 갱신한다.

**기존 개발 환경 보호 안내:** 설치 완료 화면에 *"PC에 이미 설치된 Python·Node.js·Git과 환경변수는 변경하지 않았습니다"* 를 명시한다. 개발 경험이 있는 사용자일수록 이 점을 먼저 걱정한다.

### 3.7 핵심 결정 D5 — 진입점 이원화 (GUI / CLI)

에이전트를 GUI 전용으로 만들면 개발 경험이 있는 사용자가 불편해서 우회한다. 그냥 `pip install gvskb` 를 해버리고, 그 순간 기관 승인 버전과 다른 룰셋으로 검사하게 된다. **쓰이지 않거나 다른 기준으로 쓰이는 보안 도구는 효과가 0이다.**

같은 에이전트에 CLI 진입점을 함께 제공한다.

```bash
gg-agent status                      # 설치 상태·버전·번들 ID
gg-agent scan <path> [--quick|--standard] [--out <dir>]
gg-agent scan <path> --ci            # 결과를 종료 코드로 반환 (block=1)
gg-agent update [--check-only]
gg-agent mcp register|unregister|restore --tool <name>
gg-agent bundle info                 # 현재 적용 번들과 승인 정보
```

원칙:

- **GUI와 CLI는 같은 엔진, 같은 승인 번들을 쓴다.** 화면만 다르다. 별도 검사 경로를 만들지 않는다.
- 어느 쪽으로 실행하든 보고서에 **동일한 `bundle_id`** 가 기록된다. 검토자는 실행 방식과 무관하게 같은 기준을 본다.
- CLI도 로컬 API 서버를 거치지 않고 엔진을 직접 호출한다. 토큰·Origin 검증 대상이 아니다.
- `--ci` 는 종료 코드와 SARIF·JSON 산출물만 내고 대화형 프롬프트를 띄우지 않는다.
- 설치 시 사용자 PATH에 shim 추가는 **선택 항목**으로 두고 기본은 끔. 사용자 환경을 기본값으로 바꾸지 않는다(§3.6).
- 인터넷망 개발자에게는 내부 미러 경유 `pipx`/`npx` 경로를 보조로 허용할 수 있으나, **승인 번들과 동일한 고정 버전만** 가리키게 한다. `latest` 해석을 허용하지 않는다.

## 4. 신뢰 체인 설계 (17번 문서 최대 공백 해소)

### 4.1 신뢰 루트

| 계층 | 수단 | 검증 시점 |
|---|---|---|
| 설치 패키지 자체 | Windows Authenticode 서명 | 사용자가 설치 실행할 때 OS가 검증 |
| 릴리스 manifest | **Ed25519 detached 서명** | 에이전트가 업데이트 확인 시마다 검증 |
| 각 컴포넌트 파일 | SHA-256 (manifest에 기재) | staging 검증 시 |
| 전송 구간 | 기관 내부 HTTPS (서버 인증서 pinning 선택) | 매 요청 |

**루트 공개키는 에이전트 설치 패키지 안에 임베드한다.** 설치 패키지는 Authenticode로 서명되어 있으므로 공개키가 변조되면 OS 서명 검증이 깨진다. 즉 신뢰의 시작점은 "기관이 서명한 설치 패키지"이며, 이후 모든 업데이트는 그 안의 공개키가 보증한다. 네트워크나 서버가 침해되어도 개인키 없이는 유효한 manifest를 만들 수 없다.

**서명 키는 두 층으로 나눈다.** 하나의 키가 "만든 사람"과 "배포를 허가한 기관"을 동시에 뜻하면 역할 분리가 불가능하다.

| 키 | 보유자 | 위치 | 의미 | 에이전트가 신뢰하는가 |
|---|---|---|---|---|
| **개발자 릴리스 키** | 개발자 | 개발 PC의 하드웨어 토큰 또는 로컬 키스토어 | "이 산출물은 내가 만든 것이 맞다" (출처 증명) | **아니오.** 내부 서버만 검증 |
| **기관 배포 키** | 정보보안팀 | **행정망 내부**, 승인자 인증 세션에서만 접근 | "경기도가 이 번들의 배포를 허가했다" | **예. 이것이 신뢰 루트** |

이 구조의 효과:

- 개발자 키가 탈취되어도 **보안팀 승인 없이는 배포되지 않는다.** 공격자는 유효한 반입 요청서를 만들 수 있을 뿐이고, 그 다음 관문에서 멈춘다.
- 기관 배포 키는 **행정망 안에만 존재하며 인터넷에 노출되지 않는다.** 인터넷망에 별도 오프라인 서명 PC를 운영할 필요가 없어진다.
- **CI는 어느 키도 갖지 않는다.** CI가 침해되어도 서명이 불가능하다.
- 에이전트가 신뢰하는 공개키는 **기관 배포 키 하나뿐**이므로 검증 로직이 단순하다.

1차 운영에서는 기관 배포 키를 내부 서버의 분리된 시크릿 저장소에 두고 **승인자 인증 세션에서만** 서명이 일어나도록 하며, 모든 서명 행위를 `admin_audit_logs`에 남긴다. 여건이 되면 HSM 또는 USB 토큰으로 옮긴다.

### 4.1.1 GitHub 침해를 전제한 방어 (접근 통제만으로 부족한 이유)

원본 저장소의 접근 통제는 **1층일 뿐**이다. 접근 통제로 막을 수 없는 경로가 실제 공급망 사고의 대부분이다.

| 접근 통제로 막히지 않는 것 | 대응 층 |
|---|---|
| 정당한 관리자 계정의 토큰·세션 탈취(피싱) | 하드웨어 2FA(보안키/passkey) 의무화, 2인 리뷰 필수 |
| 태그 이동 — `v1.2.0`이 어제와 다른 커밋을 가리킴 | immutable release + manifest에 **커밋 SHA·artifact digest 고정** |
| 우리 코드가 아니라 **의존성 하나**가 침해됨 | lockfile + 해시 고정, 릴리스 전 자체 체커 검사, SBOM 대조 |
| CI 워크플로우·서드파티 액션 침해 | 액션을 태그가 아닌 **커밋 SHA로 고정**, 토큰 최소 권한 |
| 권한자의 선의의 실수 | 사람 승인 게이트 2단(외부 릴리스 승인 + 내부 번들 승인) |
| 빌드 산출물이 소스와 다름 | 재현 가능 빌드 지향, SBOM·해시 대조 |

**최종 방어선은 서명 키의 위치다.** 개인키가 GitHub·CI 어디에도 없으면, 저장소가 완전히 장악되어도 공격자는 유효한 manifest를 만들 수 없고 에이전트가 거부한다. 반대로 CI에 서명 키를 두면 위 모든 층이 한 번에 무의미해진다.

**그리고 서버는 GitHub을 직접 바라보지 않는다.** 내부 서버는 `main`을 pull하지 않으며, 반입된 번들도 `draft`로 들어와 **사람이 승인해야** 사용자에게 배포된다(§4.4, §8.2). GitHub → 사용자 PC 사이에 사람 승인이 두 번, 서명 검증이 두 번 있다.

### 4.2 키 승계 (rollover)

manifest에 다음 키를 **현재 키로 서명해** 미리 싣는다. 에이전트는 승계 체인을 로컬에 누적 저장한다.

```json
{
  "manifest_version": 2,
  "keys": {
    "active_key_id": "gg-rel-2026a",
    "next_key_id": "gg-rel-2027a",
    "next_public_key": "base64...",
    "next_key_signature": "base64..."
  }
}
```

- 에이전트는 `next_public_key`를 현재 활성키로 검증한 뒤 신뢰 목록에 추가한다.
- 활성키 교체 시 이미 배포된 모든 에이전트가 재설치 없이 따라온다.
- 키 폐기(revocation)는 `revoked_key_ids` 목록으로 배포하며, 폐기된 키로 서명된 manifest는 즉시 거부한다.

### 4.3 다운그레이드 차단 (anti-downgrade floor)

17번 문서의 롤백 규정은 취약 버전으로의 되돌림을 막지 못한다. 다음을 추가한다.

- manifest에 `min_installable_version` (컴포넌트별)을 둔다. 보안 패치 릴리스는 이 값을 올린다.
- 에이전트는 지금까지 **관측한 최대 floor**를 `data/trust-state.json`에 기록한다.
- 설치·업데이트·롤백 모두 `floor` 미만 버전은 거부한다. 롤백 대상이 floor 미만이면 롤백 대신 "이전 정상 버전 사용 불가 · 재설치 필요" 상태로 사용자에게 알린다.
- `trust-state.json`은 사용자 ACL로 보호하고, 손상 시 floor를 낮추지 않고 `판정 불가`로 처리한다.

### 4.4 승인 번들 구조

번들은 에이전트 · 체커 · 하네스 · 룰셋 · 인텔의 **호환 조합 하나**를 가리킨다.

| 필드 | 설명 |
|---|---|
| `bundle_id`, `channel` | `stable` / `emergency` / `offline_bundle` |
| `components[]` | 이름, 버전, 고정 commit 또는 artifact digest, 파일명, SHA-256, 크기 |
| `min_agent_version` | 이 번들을 적용할 수 있는 최소 에이전트 버전 |
| `min_installable_version` | 컴포넌트별 다운그레이드 하한 (§4.3) |
| `supersedes`, `rollback_target` | 승계·롤백 대상 |
| `sbom_ref` | 컴포넌트별 SBOM 위치 |
| `approved_by`, `approved_at`, `status` | 승인 이력 (`draft`/`approved`/`superseded`/`revoked`) |
| `keys` | §4.2 승계 블록 |

## 5. 로컬 에이전트 설계

### 5.1 설치 위치

```text
%LocalAppData%\Gyeonggi\SecurityAgent\
  app\        에이전트 실행 파일과 UI 정적 자원
  runtime\    내장 Python 3.12 (+ 인터넷망 빌드 한정 Git 포터블)
  checker\    승인된 gvskb, 룰셋, 인텔
  harness\    승인된 하네스 스냅샷
  data\       설정, trust-state.json, runtime.json, 작업 이력
  mcp-backups\ AI 도구 설정 백업
  cache\      ZIP 해제·clone 임시 (작업 종료 시 삭제)
  staging\    업데이트 검증용 임시 영역
  backups\    직전 정상 컴포넌트
```

전역 PATH, 사용자 기존 Python·Node·Git 환경을 변경하지 않는다. 보고서는 이 폴더가 아니라 **사용자가 고른 폴더**에 저장한다.

### 5.2 로컬 API 보안 (17번 §7.1 보강)

기존 프로토타입의 Host·Origin·토큰 검증을 유지하되 다음을 추가한다.

| 항목 | 규칙 |
|---|---|
| 바인딩 | `127.0.0.1` 전용. LAN 인터페이스 금지 |
| 포트 | OS 할당(0번 요청) 후 `data\runtime.json`에 기록. 고정 포트 금지(예측·선점 방지) |
| 토큰 | 기동 시 32바이트 난수. **URL 쿼리스트링으로 전달 금지.** 서버가 HTML `<head>`에 주입하는 현행 방식 유지 |
| 토큰 파일 ACL | `runtime.json`은 현재 사용자 계정만 읽기 가능하도록 ACL 설정. 공용 PC의 타 계정 접근 차단 |
| Origin | `Origin` 헤더가 자기 자신과 정확히 일치할 때만 허용 |
| Sec-Fetch | 상태 변경 요청은 `Sec-Fetch-Site: same-origin` 필수 |
| Host | `127.0.0.1:<port>` / `localhost:<port>` 만 허용 (DNS rebinding 차단) |
| CORS | 어떤 외부 origin에도 열지 않는다 |
| 명령 실행 | shell 없이 인자 배열로 실행. 명령·인자 allowlist |
| 파일 처리 | 경로 탈출, ZIP bomb, 압축 해제 후 총 크기·파일 수·압축률 상한 검증 |
| 감사 로그 | 실행 명령, 변경 버전, 성공·실패 사유를 `data\audit.log`에 append |

**단일 인스턴스·상태 잠금 (17번 미정의 항목):**
- 기동 시 `data\agent.lock`을 배타 획득한다. 이미 실행 중이면 기존 인스턴스의 UI를 열고 종료한다.
- 업데이트 진행 중에는 점검 시작을 거부한다(`409 update_in_progress`). 점검 진행 중에는 업데이트 적용을 거부한다.
- 비정상 종료 시 남은 lock은 PID 생존 확인으로 회수한다.

### 5.3 상태 판정 규칙 (17번 미정의 항목 해소)

17번 수용 기준 2·10이 요구하는 상태들의 **판정 근거**를 확정한다. 각 컴포넌트 설치 시 `<component>\install-receipt.json`(bundle_id, version, 파일별 SHA-256, 설치 시각, manifest 서명)을 남긴다.

| 상태 | 판정 조건 | 활성 버튼 |
|---|---|---|
| `not_installed` | 컴포넌트 루트 부재 또는 receipt 부재 | `설치`만 |
| `official_current` | receipt 유효 + 파일 해시 전부 일치 + version = 채널 최신 | 없음 (상태 표시만) |
| `update_available` | receipt 유효 + 해시 일치 + version < 채널 최신 | `업데이트`만 |
| `unofficial` | receipt 없이 실행 파일 존재 / 에이전트 관리 밖 경로 / editable 설치(`.pth`, `.egg-link`) 탐지 | `공식 설치`만 (기존 폴더 보존) |
| `verification_failed` | 해시 또는 서명 불일치 | `재설치`만 + 경고 |
| `unknown` (판정 불가) | 채널 도달 실패 또는 receipt 손상 | 확인 재시도. **안전으로 표시 금지** |

`unknown`은 안전이 아니다. 화면과 보고서 모두에서 `확인 필요`로 표기한다.

### 5.4 업데이트 절차

```text
1. 채널 manifest 수신 -> Ed25519 서명 검증 -> 폐기키 확인
2. min_agent_version · min_installable_version(floor) 검증
3. 현재 receipt와 비교하여 대상 컴포넌트 산출
4. 변경 요약을 사용자에게 표시 -> 명시적 승인
5. staging\ 에 내려받아 SHA-256 검증
6. data\, mcp 설정, 현재 컴포넌트를 backups\ 로 백업
7. 원자적 교체 (디렉터리 rename 기반)
8. 재검증: gvskb doctor, 하네스 검증, 에이전트 self-check
9. 실패 시 backups\ 로 롤백. 단 floor 미만 롤백은 금지(§4.3)
10. 결과를 audit.log 및 (동의 시) 포털 메타데이터로 기록
```

에이전트 자체 업데이트는 실행 중 파일 잠김을 피하기 위해 **별도 updater 실행 파일**이 에이전트 종료 후 교체하고 재기동한다.

### 5.5 MCP 등록 (17번 지적 ⑥ 해소)

에이전트는 도구별로 **등록 / 해제 / 복원** 세 동작을 모두 제공한다.

- 대상: Codex(ChatGPT Desktop), Claude Code, Claude Desktop. 각각 설정 경로와 형식이 다르므로 **선택한 도구 하나만** 처리한다.
- 변경 전 원본을 `mcp-backups\<tool>\<UTC타임스탬프>.json` 으로 복사하고 원본 해시를 기록한다.
- 등록 항목은 가변 경로가 아니라 고정 진입점을 쓴다: `gg-security-agent.exe mcp serve`. 업데이트로 경로가 바뀌어도 설정을 다시 건드리지 않는다.
- JSON 파싱 실패·스키마 불일치 시 **덮어쓰지 않고 중단**하고 사용자에게 수동 확인을 안내한다.
- `복원`은 백업 목록에서 시점을 골라 되돌린다. `해제`는 우리 항목만 제거하고 나머지 설정은 보존한다.
- Lovable 등 자동 등록 계약이 없는 도구는 `지원하지 않음`으로 명시 표기하고 폴더·ZIP 점검으로 안내한다.

## 6. 점검 실행 설계

| 구분 | 간편 점검 | 표준 점검 |
|---|---|---|
| 프로파일 | `dev-quick` | strict (기관 프로파일 기준) |
| 범위 | 비밀값·인증정보·고위험 규칙 + 의존성 | 전체 코드·의존성·룰셋·벤더 번들 |
| 시점 | 개발 중 수시 | 제출·배포 전 |
| 결과 | 빠른 위험 신호 | 제출 판단용 전체 보고서 |

- 대상: 폴더 / ZIP / (인터넷망 한정) GitHub HTTPS URL.
- **저장 위치를 먼저 고르지 않으면 점검을 시작하지 않는다.** 안내만 표시한다.
- 검사된 파일 0개는 안전이 아니라 `점검 불완전`이다.
- 벤더 번들(`static/*.min.js` 등)이 발견되면 반드시 별도 검사하여 결과를 병합한다.
- 보고서는 HTML·JSON·Markdown을 사용자 선택 폴더에 저장하고, 결과 API는 전체 경로가 아닌 **폴더 라벨만** 반환한다.
- **파일명 충돌 정책(17번 미정의):** `<대상명>_<모드>_<KST YYYYMMDD-HHmmss>` 를 기본으로 하고, 동일 이름 존재 시 `_2`, `_3` 접미사를 붙인다. 덮어쓰지 않는다.
- 진행률은 가중 단계(대상 준비 → 코드·의존성 검사 → 보고서 생성 → 선택 폴더 저장)로 계산한다. 완료 전 100% 표시 금지. 클라이언트 폴링 시간 제한을 두지 않으며 창을 닫아도 점검은 계속된다.

## 8. 망 구간 설계 (논리적 망분리 + 망연계 전제)

### 8.1 동작 모드 (파일 반입 확정)

경기도 망연계는 **파일전송 스트리밍 방식**이다(§1). 서비스 중계가 없으므로 **파일 반입 모드가 기본이자 유일한 운영 모드**다.

| 항목 | **기본 — 행정망 + 파일 반입** | 예외 — 완전 오프라인 |
|---|---|---|
| 사용자 PC → 업데이트 채널 | 경기도 내부 서버 HTTPS | 동일 |
| 내부 서버 → 외부 원본 | **망연계 파일 반입** (§8.2) | 없음. 매체 반입 |
| GitHub / 공공 GitLab 접근 | **인터넷망 구간에서만** | 없음 |
| 인텔 갱신 | 파일 번들 반입 (스트리밍이므로 일 단위 가능) | 반입 시점 |
| GitHub URL 점검 | **미지원 + 사유 표시** | 미지원 |
| Git 런타임 포함 | 제외 (패키지 45MB 감소) | 제외 |
| 의존성 인텔 | 반입된 서명 인텔 번들, `GVSKB_MODE=offline` | 매체 반입 번들 |
| 실시간 외부 질의 | **없음** (설계상 의존하지 않는다) | 없음 |

**보안 불변식**

1. **사용자 PC는 언제나 경기도 내부 서버만 바라본다.** 망연계를 쓰는 주체는 내부 서버 한 곳뿐이다. 그래야 방화벽 정책·검역·감사 지점이 하나로 모인다.
2. **들어온 것은 내부에서 서명을 재검증한다.** 파일전송 통과 자체는 무결성·출처를 보증하지 않는다.
3. **반입은 승인이 아니다.** `draft`로 등록되고 승인을 거쳐야 배포된다.
4. **행정망 어느 구성요소도 외부 저장소를 직접 바라보지 않는다.**

### 8.2 망연계 반입 파이프라인

망연계 덕분에 인텔·릴리스 반입을 사람이 매체로 나를 필요가 없다. 다만 망연계는 검역을 거치는 **배치성 파일 연계**이므로 그 성질에 맞춰 설계한다.

```text
[인터넷망]
  GitHub immutable release + 인텔 소스(OSV 등)
    -> 반입 준비 서버가 수집·정규화
    -> 릴리스 패키지 / 인텔 번들 / 룰셋 번들 생성
    -> 오프라인 서명 PC에서 Ed25519 서명 (§4.1)
    -> 반입 큐에 적재

[망연계 서버]
    -> 검역(백신, 확장자·크기·압축중첩 제한) 및 승인
    -> 단방향 전달

[행정망]
  gg-security-portal 반입 수신 모듈
    -> Ed25519 서명 재검증 (망연계 통과 사실을 신뢰하지 않는다)
    -> SHA-256 대조
    -> 승인 번들 레지스트리에 draft 등록
    -> 사람 승인 -> approved 로 전환
    -> 사용자 에이전트가 내부 서버에서 수신
```

설계 규칙:

- **망연계 통과를 신뢰의 근거로 삼지 않는다.** 검역은 악성코드를 거르는 장치이지 무결성·출처를 보증하지 않는다. 내부 서버는 반입물의 서명을 반드시 재검증한다.
- **반입 자체가 승인이 아니다.** 반입된 번들은 `draft`로 들어오고, 사람이 승인해야 `approved`가 되어 사용자에게 배포된다(§4.4).
- **반입 형식은 검역 규격에 맞춘다.** EXE·ZIP이 차단되면 확장자 변경 또는 분할 전송이 필요하므로 B1에서 확인한다. manifest는 서명 포함 JSON 단일 파일이라 검역 부담이 작다.
- **반입 실패를 감지한다.** 마지막 성공 반입 시각을 관리자 화면에 표시하고, 임계 시간 초과 시 알린다. 조용히 낡아가는 인텔이 가장 위험하다.
- **단방향이면 결과 회신을 설계하지 않는다.** 사용자 메타데이터는 행정망 내부 포털에만 쌓이며 외부로 나가지 않는다. 인터넷망으로의 통계 반출은 1차 범위 밖이다.

### 8.3 인텔 stale 정책

- 인텔 번들에 `generated_at`과 `max_age_days`(기본 14일)를 넣는다.
- TTL 초과 시 간편 점검은 `인텔 오래됨` 배지와 함께 수행하되, **표준 점검은 결과 등급을 `점검 불완전`으로 강등**한다. 제출 판단에 쓰이는 결과이므로 오래된 인텔로 "안전"을 말하지 않는다.
- 화면과 보고서 모두에 인텔 생성일과 경과일을 표기한다.
- 반입 주기(권장 주 1회)가 TTL보다 짧게 유지되도록 관리자 화면에서 감시한다.

### 8.4 인텔 무결성 (코드와 다른 위협 모델)

인텔 캐시는 우리 소스가 아니라 **외부 취약점 데이터(OSV, KEV 등)의 스냅샷**이다. GitHub 접근 통제와 무관한 경로로 오염될 수 있으므로 따로 방어한다.

| 위협 | 방어 |
|---|---|
| 반입 구간 변조 | 인텔 번들도 릴리스와 동일하게 Ed25519 서명. 내부에서 재검증 |
| 상류 데이터 오염·오류 | 소스·수집 시각·레코드 수를 manifest에 기록하고 관리자 화면에 노출 |
| **레코드 누락 (미탐 유발)** | 직전 번들 대비 레코드 수가 임계치(예: 20%) 이상 감소하면 **자동 거부**하고 사람 확인을 요구한다. 있던 취약점이 사라지는 것은 오탐이 아니라 **미탐**이므로 더 위험하다 |
| 파서 공격 | 인텔은 데이터일 뿐 실행하지 않는다. 파싱은 스키마 검증 후 진행하고, 크기·중첩·필드 길이 상한을 둔다 |
| 낡음 | §8.3 TTL |

**설계 원칙 — 인텔은 판정을 강화하는 방향으로만 쓴다.**

- 인텔이 "취약하다"고 말해 경고를 **추가**하는 것은 오염되어도 오탐에 그친다.
- 인텔이 "안전하다 / 이미 수정되었다"고 말해 차단을 **해제**하는 것은 오염 시 곧바로 위험이 통과한다.
- 따라서 `fixed_version` 등을 근거로 차단을 낮출 때는 그 근거(소스, 인텔 생성일, 레코드 ID)를 **보고서에 명시**하고, 오프라인·stale 상태에서는 차단 해제를 적용하지 않는다.

**외부 노출 명시 (17번 수용 기준 3 정정):** 인터넷망 모드에서 의존성 인텔을 조회하면 **대상 프로젝트의 패키지명과 버전이 외부 endpoint로 나간다.** 이는 "사용자 PC 밖으로 아무것도 나가지 않는다"와 충돌하므로, 수용 기준 문구를 "**원본 소스·압축파일·보고서 본문**은 PC 밖으로 나가지 않는다"로 좁히고, 인텔 조회로 나가는 항목을 화면 도움말에 명시한다. 행정망 모드에서는 외부 조회가 없다.

### 9.2 개인정보 관점

- 담당자명·부서는 1차에서 수집하지 않는다.
- 익명 설치 ID는 설치 시 생성한 UUIDv4이며 재설치 시 갱신된다. 사용자·PC를 특정하는 값을 유도해서 만들지 않는다.
- **재식별 방지:** 관리자 통계는 표본 5건 미만 구간을 마스킹한다. 소규모 부서에서 설치 ID + 시각 + 버전 조합으로 개인이 추정되는 것을 막는다.
- 보존 기간 12개월, 이후 일 단위 집계(`daily_usage_stats`)만 남기고 원 레코드 삭제.
- 개인정보 영향평가 대상 여부는 정보보안담당관 판단을 받는다. 익명 처리라도 공공기관 시스템이므로 사전 확인이 필요하다.

### 9.3 DB 스키마

기존 `supabase/schema.sql`의 14개 테이블 설계는 **데이터 최소화 관점에서 잘 되어 있어 대부분 이식한다.** `scan_findings`에 파일 경로·라인·코드 조각이 없는 점이 특히 옳다.

이식 시 변경:
- `admin_profiles.id` → `auth.users(id)` 참조 제거, OIDC `subject` 컬럼으로 대체
- 모든 `row level security` / `create policy` → 애플리케이션 계층 권한 + PostgreSQL 역할 분리로 대체
- `client_type` enum에서 `local_web`, `desktop` → `agent` 단일화 검토
- `release_bundles`에 `min_installable_version`, `keys`, `revoked_key_ids` 필드 추가 (§4)
- 서비스 계정은 텔레메트리 쓰기 전용 / 관리자 조회 읽기 전용으로 분리

### 10.1 공공 GitLab (`gitlab.aigov.go.kr`) 도입 — 권장

행정안전부·NIA가 **「AI 정부 실험실」** 사업으로 구축·운영하는 공공 GitLab이 2026년 7월부터 공무원 누구나 사용 가능하다. **이를 릴리스 관문으로 채택할 것을 권장한다.**

| 확인된 사실 | 근거 |
|---|---|
| 주소 `https://gitlab.aigov.go.kr` — **인터넷망(외부망)** | 이용가이드 p.7, p.9 |
| 운영 주체 = **행정안전부 인공지능정부정책과 + NIA** | p.1, p.21 |
| 2026년 인터넷망 운영 중(VM 200식), **2027년 업무망 구축 예정** | p.3 |
| **GitHub Import 기능 공식 제공** (토큰 → 프로젝트 가져오기) | p.19 |
| CI/CD + **SAST·DAST·오픈소스 취약점·컨테이너 이미지 스캔** 내장 | p.5 |
| **아티팩트 저장소 · 컨테이너 레지스트리** 제공 | p.5 |
| 공개 범위 선택 가능(비공개 / 내부 / 공개) | p.11 |
| 프로젝트 현황이 `axboard.aigov.go.kr` 에 **공개** | p.12, p.17 |

#### 권장 3계층 구조

```text
① GitHub — 개발 원본 (편집 가능, 인터넷망)
     AI 도구로 개발, MIT 공개 저장소 유지
     ↓ GitHub Import / 미러 (태그·커밋 그대로, 강제 push 금지)
② 공공 GitLab (인터넷망, 행안부 운영) — 릴리스 관문 + 공공 확산 창구
     CI 재빌드 · SAST · 의존성 스캔 · SBOM 생성
     산출물을 Release / Package Registry 에 보관
     ↓ 파일전송 스트리밍 (§8.2) — 아티팩트만, 소스 아님
③ 경기도 행정망 내부 서버 — 서명 재검증 · 승인 · 배포
```

**공공 GitLab이 인터넷망에 있다는 점이 오히려 유리하다.** 개발·릴리스 구간이 모두 인터넷망에 모이므로 AI 도구를 계속 쓸 수 있고, 망연계로는 **완성된 아티팩트만** 넘기면 된다.

#### 반드시 지켜야 할 3가지

**① 편집 가능한 원본은 한 곳뿐이다.**

"GitHub에서 개발하고 GitLab에서도 함께 수정한다"는 **가장 위험한 선택**이다. 두 저장소가 갈라지는 순간 어떤 소스가 어떤 산출물이 되었는지 아무도 말할 수 없게 된다. 이는 §14.1에서 행정망 수정을 금지한 것과 같은 이유다.

- GitLab은 **읽기 전용 미러**로 두고 편집 권한을 부여하지 않는다.
- 협업 인원이 늘어 GitLab에서 작업해야 한다면, **GitLab을 원본으로 승격하고 GitHub을 공개 미러로 강등**한다. 방향을 뒤집는 것은 괜찮지만 **양쪽 편집은 안 된다.**
- 미러는 태그·커밋을 그대로 옮기며, 강제 push(`--force`)를 차단한다.

**② 운영 배포에 `git clone` 을 쓰지 않는다.**

소스를 클론해 배포하는 것은 §2-②에서 폐기한 `git pull` 패턴의 재현이다.

| 문제 | 설명 |
|---|---|
| 시점 고정 불가 | 클론은 그 순간의 브랜치 상태다. 사후에 "무엇을 배포했는가"를 정확히 재현할 수 없다 |
| 태그 이동 | `git tag -f` 로 같은 태그가 다른 커밋을 가리킬 수 있다 |
| 서명 검증 지점 없음 | 클론 과정에는 서명을 확인할 자리가 없다 |
| 운영 서버에서 빌드 필요 | 빌드 도구·의존성 설치가 필요해져 운영 서버 공격면이 커진다. 행정망은 패키지 설치 자체가 제약된다 |
| `.git` 잔존 | 운영 서버에 이력·설정이 남고, 나중에 `git pull` 하고 싶은 유혹이 생긴다 |

→ **배포 단위는 소스가 아니라 서명된 아티팩트다.** GitLab Release 또는 Package Registry에 올린 산출물을 받아 SHA-256·서명을 검증한 뒤 설치한다.

**③ GitLab CI에도 서명 키를 두지 않는다.**

GitLab이 기관 내부에 있다는 사실이 신뢰의 근거가 되지 않는다. §4.1.1의 원칙은 그대로다. 기관 배포 키는 **승인 행위와 묶여** 승인자 인증 세션에서만 사용된다.

#### 타 기관이 운영한다는 점의 함의

공공 GitLab은 **경기도가 통제하지 못하는 인프라**다. 브랜치 보호 정책, 접근 권한 관리, 백업, 가용성, 서비스 종료 여부가 모두 행안부·NIA 손에 있다. 따라서:

- **공공 GitLab을 신뢰 루트로 삼지 않는다.** 기관 배포 키는 여전히 경기도 행정망 안에만 있고, GitLab CI는 서명하지 않는다(§4.1). 남의 인프라에 우리 키를 두는 것은 더욱 안 된다.
- **단일 장애점으로 만들지 않는다.** GitHub 원본을 유지해 GitLab이 중단·정책 변경되어도 릴리스가 막히지 않게 한다.
- **공개 범위를 분리한다.** 체커·하네스 소스는 공개해도 되지만(MIT 지향), **경기도 배포 manifest, 기관 프로파일, 승인 정책, 공개키 배포 목록은 공공 GitLab에 두지 않는다.** 프로젝트 설명이 `axboard.aigov.go.kr`에 공개되므로 저장소 설명에도 기관 내부 정보를 적지 않는다.
- **가져오기(Import) 후 자동 동기화 여부를 확인한다.** p.19의 GitHub Import는 일회성 마이그레이션일 수 있다. 지속 미러가 필요하면 GitLab의 저장소 미러링 설정 가능 여부를 확인한다.

#### 얻는 것

- 반입 요청서(§14.5-1단계)를 **GitLab Release 메타데이터로 대체**할 수 있어 개발자 절차가 더 줄어든다.
- **CI 재빌드로 소스와 산출물의 일치를 독립 검증**할 수 있다(공급망 방어 강화).
- 내장 SAST·의존성 스캔을 릴리스 게이트에 **추가 층으로** 붙일 수 있다. 단 우리 체커를 대체하지 않는다 — 관점이 다르다.
- 승인 화면이 GitLab 파이프라인 결과를 직접 인용할 수 있다.
- **공공 확산 창구**가 된다. 타 기관이 `axboard`에서 발견해 가져다 쓸 수 있다.

#### 2027년 업무망 GitLab 대비

행안부는 2027년 업무망 GitLab 구축을 예고했다(p.3). 그때는 §8.2의 파일 반입 파이프라인 상당 부분을 업무망 GitLab으로 대체할 수 있다. **지금 구조를 그에 맞춰 미리 바꾸지는 않되**, 반입 인터페이스를 GitLab Release 규격에 가깝게 만들어 두면 전환 비용이 작다.

| | 행안부 보안게이트 | 경기도 보안 게이트(본 프로젝트) |
|---|---|---|
| **시점** | 2027년 예정 | **지금 필요** (경기도는 이미 AI 코딩이 확산 중) |
| **역할** | 망 경계에서 **반입 여부를 심사**하는 관문 | 개발자 PC에서 **개발 중 상시 점검** + 제출용 보고서 |
| **위치** | 중앙 1지점, 사후 심사 | 분산(각 PC), 사전 예방 |
| **대상** | AI 정부 실험실 산출물의 업무망 반입 | 경기도 공무원의 일상 개발 코드 전반 |

**관계를 한 문장으로:** 우리 도구는 **게이트 앞에서 미리 통과시키는 도구**다. 개발자 PC에서 먼저 잡으면 반입 게이트 통과율이 올라가고 반려가 줄어든다. 게이트가 생겨도 우리 도구의 필요는 사라지지 않는다 — 오히려 게이트가 생기면 사전 점검 수요가 커진다.

#### 지금 해야 할 대비

1. **표준 출력 포맷을 유지한다.** 보고서에 `SARIF` 출력을 계속 지원하고, 규칙 ID·심각도·CWE·파일·라인을 갖춘다. 게이트 사양이 나중에 확정되어도 산출물을 그대로 제출할 수 있어야 한다.
2. **게이트 사양을 미리 문의한다.** 행정안전부 인공지능정부정책과, NIA 공공AI사업지원센터가 공식 문의처다(p.21). 사양·일정·**지자체 참여 가능 여부**를 확인한다. 이르게 접촉할수록 우리 결과물이 사양에 반영될 여지가 크다.
3. **선행 사례로 포지셔닝한다.** 경기도가 먼저 만들어 운영 실적을 쌓으면 **참조 구현 또는 게이트 내부 엔진 후보**가 된다. `vibecode-checker`는 이미 동작하고 검증 이력이 있다.
4. **공공 GitLab에 저장소를 두어 가시성을 확보한다.** `axboard.aigov.go.kr` 프로젝트 현황에 노출되면 타 기관·행안부가 발견할 수 있다.

#### AI 정부 실험실 개발 환경 활용 여부

AI 정부 실험실은 AI 코딩 에이전트와 GPU VM을 제공한다(p.3). 개발 구간을 그리로 옮기는 선택지가 있다.

- **1차에는 옮기지 않는다.** 현재 개발 환경이 이미 검증되어 있고, VM 이전은 그 자체로 비용이다.
- 다만 **산출물을 공공 GitLab에 미러**해 두면 사업 참여 요건은 대체로 충족된다.
- 협업 인원이 늘거나 GPU가 필요해지면 그때 재검토한다.

## 13. 수용 기준

1. Python·Node.js·Git이 없는 초기화된 Windows 11 PC에서 설치 후 폴더·ZIP 간편·표준 점검이 완주한다.
2. §5.3의 6개 상태가 각각 서로 다른 버튼 활성 조합으로 나타나며, 각 상태를 강제로 만들어 재현하는 테스트가 있다.
3. **원본 소스·압축파일·보고서 본문**은 사용자 PC 밖으로 나가지 않는다. 인텔 조회로 나가는 항목은 화면에 고지되어 있다.
4. 서명이 위조되거나 해시가 불일치하는 manifest·패키지는 설치되지 않고 `verification_failed`로 표시된다.
5. `min_installable_version` 미만으로의 설치·롤백이 거부된다.
6. 업데이트 중 강제 종료 후 재기동하면 이전 정상 버전으로 자동 복구되고 점검이 다시 가능하다.
7. MCP 등록 → 복원 왕복 후 원본 설정 파일의 해시가 등록 전과 동일하다.
8. 업데이트 진행 중 점검 시작, 점검 진행 중 업데이트 적용이 각각 거부된다.
9. 중앙 포털은 어떤 경로로도 사용자 PC의 로컬 API를 호출하지 않는다(코드·CSP·테스트로 증명).
10. 관리자 화면은 OIDC 인증 없이 접근 불가하며, 텔레메트리 엔드포인트로는 조회가 불가하다.
11. 인텔 TTL 초과 시 표준 점검 결과가 `점검 불완전`으로 강등된다.
12. 검사 파일 0개, 채널 도달 실패, receipt 손상 중 어떤 경우도 `안전`으로 표시되지 않는다.
13. 관리자 통계에서 표본 5건 미만 구간이 마스킹된다.
14. 릴리스 전 하네스 게이트, 체커 점검, 시나리오 테스트, 로컬 API 적대적 검증을 모두 통과한다.
15. **에이전트를 설치하지 않은 상태에서** 하네스를 내려받아 프로젝트에 적용하고, 규칙 카탈로그와 샘플 보고서를 열람할 수 있다.
16. 브라우저 사전점검 페이지에서 파일을 검사하는 동안 **네트워크 요청이 0건**임이 자동 테스트로 증명된다(CSP 위반 이벤트 수집 포함).
17. 브라우저 사전점검은 파일 보고서를 발급하지 않으며, 결과 화면에 "제출 판단에 쓸 수 없음" 고지가 항상 표시된다.
18. 포털과 에이전트의 어느 실행 경로에서도 LLM API를 호출하지 않는다(의존성·코드 검사로 증명).
19. AI 도구가 하나도 설치되지 않은 PC에서 T0·T1의 모든 기능이 정상 동작하며, MCP 카드가 결핍이 아닌 선택 사항으로 표시된다.
20. 망연계로 반입된 번들은 서명 재검증을 통과해야 등록되며, 반입만으로는 배포되지 않고 사람 승인을 거친다.
21. 망연계 반입이 임계 시간을 초과하면 관리자 화면에 경고가 표시되고, 인텔 TTL 초과 시 표준 점검이 강등된다.
22. GUI와 CLI로 같은 대상을 검사하면 결과와 `bundle_id`가 동일하다.
23. `--ci` 실행이 대화형 프롬프트 없이 종료 코드로 판정을 반환한다.
24. 서명 개인키가 CI·저장소 어디에도 존재하지 않음이 확인된다(비밀 스캔 및 절차 문서로 증명).
25. 직전 대비 레코드 수가 임계치 이상 감소한 인텔 번들이 자동 거부된다.
26. 오프라인 또는 인텔 stale 상태에서는 인텔을 근거로 한 차단 해제가 적용되지 않는다.

## 14. 개발·릴리스·운영 모델

### 14.1 절대 원칙 — 행정망에서 코드를 고치지 않는다

체커·하네스·에이전트의 소스는 **GitHub 한 곳에만** 있다. 행정망 서버에는 저장소가 없고 **서명된 산출물만** 있다.

개발에 AI 도구가 필요한 것은 사실이고, 행정망에서는 AI를 쓸 수 없다. 그래서 **개발을 행정망으로 옮기지 않는다.** 개발은 지금처럼 인터넷망에서 AI와 함께 계속하고, 행정망은 승인·배포·관측만 한다.

행정망에서 급한 수정을 시작하면 소스가 두 갈래로 갈라지고, 그 순간 어떤 버전이 무엇을 검사했는지 아무도 말할 수 없게 된다. 이것이 가장 나쁜 결과다. **급한 수정도 인터넷망에서 하고 `emergency` 채널로 반입한다.**

### 14.2 3구간 분리

| 구간 | 위치 | AI 도구 | 하는 일 | 하지 않는 일 |
|---|---|---|---|---|
| **개발** | 인터넷망 개발 PC | **자유롭게 사용** | 코딩, 실험, 테스트, GitHub push, 룰 작성 | 사용자에게 배포 |
| **릴리스** | 인터넷망 CI + 오프라인 서명 PC | 사용하지 않음 | 태그 빌드, SBOM, 해시, **서명** | 코드 수정 |
| **운영** | 행정망 내부 서버 | 사용 불가(무관) | 반입 수신, 서명 재검증, 승인, 배포, 통계 | **코드 수정·빌드·서명** |

개발 단계는 **현재와 달라지는 것이 없다.** 이 설계가 제약하는 것은 개발이 아니라 "무엇이 사용자 PC에 도달하는가"뿐이다.

### 14.3 컴포넌트별 릴리스 리듬

번들을 컴포넌트 단위로 나눈 이유가 여기 있다. 룰 하나 고쳤다고 200MB 에이전트를 다시 서명하고 전 사용자가 재설치하지 않는다.

| 컴포넌트 | 권장 주기 | 검토 강도 | 사용자 영향 |
|---|---|---|---|
| **인텔 번들** | 주 1회 이상 (자동 수집) | 자동 검증만. 코드 리뷰 없음 | 무중단 갱신 |
| **룰셋** | 월 1회 | `proposed → approved` 사람 검토 | 무중단 갱신 |
| **체커 엔진** | 월~분기 | 전체 게이트 + 적대적 검증 | 컴포넌트 교체 후 self-check |
| **하네스** | 필요 시 | 정책 변경이므로 기관 확인 | 파일 교체 |
| **에이전트 본체** | 분기 1회 | 가장 무거움 (Authenticode 재서명) | 사용자 승인 후 업데이트 |

에이전트 본체 릴리스를 드물게 유지하는 것이 운영 부담을 결정한다. 기능은 가급적 체커·룰셋 쪽에 넣는다.

### 14.4 역할과 보유물

전제: **개발자 = 본인(1인), 승인자 = 정보보안팀.**

| 역할 | 위치 | 보유 | 하는 일 | 하지 않는 일 |
|---|---|---|---|---|
| 개발자 | 인터넷망 개발 PC | GitHub 쓰기 권한, **개발자 릴리스 키** | 코딩, 태그, 반입 요청서 서명, 반입 제출 | 배포 승인, 기관 키 접근 |
| CI (GitHub Actions) | GitHub | **키 없음** | 테스트·게이트·빌드·SBOM·해시 | 서명, 배포 |
| 승인자 (보안팀) | 행정망 | 포털 관리자 계정, **기관 배포 키** | 승인·반려·폐기, 배포 개시 | 코드 작성·수정 |

### 14.5 릴리스·운영 단계별 절차

#### 0단계 — 평소 개발 (개발자 / 인터넷망)

`main`에 계속 push한다. **아무 일도 일어나지 않는다.** 사용자에게 가지 않고, 보안팀도 관여하지 않는다. 지금과 동일하다.

#### 1단계 — 릴리스 (개발자, 명령 하나 + 토큰 터치)

**태그 push·빌드·반입 요청서 작성·서명·제출을 하나로 묶는다.** 개발자가 손으로 하는 일은 명령 하나와 하드웨어 토큰 터치뿐이다.

```bash
gg-release 1.2.0
```

이 명령이 순서대로 수행하는 것:

| # | 자동 수행 | 근거 |
|---|---|---|
| 1 | 버전 상향, CHANGELOG·검증 이력 스텁 생성 | 커밋 이력 |
| 2 | 태그 push → CI 트리거 | — |
| 3 | CI 완료 대기, 게이트 결과 수집 | CI API |
| 4 | `change_summary` 초안 작성 | CHANGELOG·커밋 메시지 |
| 5 | `impact` 자동 판정 | 변경된 파일 경로 → 컴포넌트 매핑 |
| 6 | `dependency_delta` 자동 산출 | lockfile diff |
| 7 | `gate_results` 삽입 | CI 산출물 |
| 8 | floor·rollback_target 계산 | 직전 승인 번들과 비교 |
| 9 | **개발자에게 요청서 초안 표시 → 확인/수정** | ← **사람이 개입하는 유일한 지점** |
| 10 | 개발자 키로 서명 (하드웨어 토큰 터치) | — |
| 11 | 망연계 반입 큐에 제출 | §14.5-2단계 |

**`change_summary` 한 줄만 사람이 확인한다.** 나머지는 기계가 채운다. 자동 생성된 요약이 부정확하면 승인이 지연되므로 이 한 줄만은 눈으로 본다.

**릴리스 시점 판단은 자동화하지 않는다.** `main` push가 곧 배포가 되면 §14.1 원칙이 무너지고, 보안팀에 승인 요청이 push 횟수만큼 쏟아진다. 변경을 모아서 내보내는 것이 보안팀 부담을 줄이는 가장 큰 요인이다.

##### 평소 push 시 CI (릴리스와 별개)

`main` push마다 CI는 게이트를 돌려 **릴리스 후보 상태**만 갱신한다. 태그가 없으므로 배포 경로에는 오르지 않는다. 덕분에 `gg-release` 실행 시점에는 이미 통과 여부를 알고 있어 대기가 짧다.

#### (1단계 내부) CI 자동 검증·빌드

**하나라도 실패하면 릴리스가 중단되고 산출물이 만들어지지 않는다.**

| 검사 | 내용 |
|---|---|
| 전체 테스트 | 단위·통합·시나리오 |
| 하네스 게이트 | 개발 기준 위반 여부 |
| 체커 자기검사 | 체커로 체커 자신을 검사 |
| 적대적 검증 | 수정이 새 오탐·미탐을 만들지 반대 방향 확인 |
| 의존성 검사 | 새 패키지·버전 변경 탐지 |

통과 시 산출물: 패키지 파일, `sbom.json`, `checksums.txt`, `build-manifest.json`(커밋 SHA·아티팩트 digest·게이트 결과 포함), immutable release.

#### (1단계 산출물) 반입 요청서

`gg-release`가 자동 생성하고 개발자 키로 서명하는 문서다.

```json
{
  "version": "1.2.0",
  "components": [{"name": "checker", "commit": "a1b2...", "sha256": "...", "size": 41231234}],
  "min_installable_version": "1.1.3",
  "rollback_target": "1.1.5",
  "change_summary": "SQL 다줄 탐지 오탐 수정, 룰 3건 추가",
  "impact": "체커 엔진만 교체. 에이전트 본체·하네스 변경 없음",
  "dependency_delta": "추가 0건, 버전 변경 1건 (requests 2.32.3 → 2.32.4)",
  "gate_results": {"tests": "1204 passed", "checker_self_scan": "block 0", "adversarial": "pass"}
}
```

`change_summary`, `impact`, `dependency_delta`는 **승인자가 실제로 읽는 항목**이다. `impact`와 `dependency_delta`는 기계가 정확히 채우므로 사람이 손댈 이유가 없다.

#### 2단계 — 망연계 반입 (검역, 반나절~1일)

**핵심: 망연계 반입 승인과 번들 배포 승인을 이중으로 받지 않는다.**

두 통제는 목적이 다르다.

| 통제 | 묻는 것 | 담당 |
|---|---|---|
| 망연계 반입 승인 | "이 파일을 행정망에 들여도 되는가" (검역) | 망연계 운영부서 |
| 번들 배포 승인 | "이 번들을 공무원 PC에 배포해도 되는가" (내용) | 정보보안팀 |

둘 다 매 릴리스마다 사람이 승인하면 부담이 두 배가 되고, 실제로는 같은 사람이 같은 것을 두 번 본다. 다음으로 해소한다.

- **고정 반입 채널(standing channel)을 1회 등록한다.** "보안 게이트 포털 릴리스 파일"을 정기·반복 반입 건으로 최초 1회 신청·승인받고, 이후 개별 신청 없이 정해진 경로·형식으로 반입한다. 대부분의 망연계 시스템이 반복 반입 등록을 지원한다.
- 이후 개별 건은 **검역만 자동 통과**하고 사람 승인이 없다.
- **실질 통제는 내부 서버의 배포 승인 한 곳으로 모은다.** 통제 지점을 하나로 유지해야 각 지점이 형식화되지 않는다.
- 고정 채널 등록이 불가능한 기관이면 반입 승인자를 배포 승인자와 **같은 사람으로 지정**해 한 번에 처리한다.

이 항목은 기관마다 운영이 다르므로 B1에서 확인한다.

#### 3단계 — 내부 수신·자동 검증 (자동, 즉시)

내부 서버가 수행한다. **망연계를 통과했다는 사실을 신뢰하지 않는다.**

1. 개발자 서명 검증 → 실패 시 즉시 거부·기록
2. 파일 SHA-256 대조
3. floor·최소 에이전트 버전 정합성 확인
4. 인텔 번들이면 레코드 급감 검사(§8.4)
5. `draft` 상태로 레지스트리 등록 → 보안팀 대기 목록에 표시

#### 4단계 — 승인 (정책 자동 또는 사람, §14.6)

관리자 화면 한 곳에서 처리한다. **보안팀은 코드를 읽지 않는다.**

화면에 표시되는 것:

| 항목 | 예시 |
|---|---|
| 버전·컴포넌트 | `checker 1.2.0` (에이전트 본체 변경 없음) |
| 변경 요약 | SQL 다줄 탐지 오탐 수정, 룰 3건 추가 |
| **의존성 변경** | 추가 0건, 버전 변경 1건 — **보안팀이 가장 먼저 보는 항목** |
| 게이트 결과 | 테스트 1204 통과 / 체커 자기검사 block 0 / 적대적 검증 통과 |
| 개발자 서명 | ✅ 검증됨 (키 ID, 서명 시각) |
| floor 변경 | 1.1.2 → 1.1.3 (이 미만 버전 설치·롤백 차단됨) |
| 롤백 대상 | 1.1.5 |

동작: `승인` / `보류(질의)` / `반려`.

**`승인`을 누르는 순간 내부 서버가 기관 배포 키로 서명**하고 상태가 `approved`로 바뀐다. 승인자·시각·대상이 `admin_audit_logs`와 `release_bundles`에 남는다.

#### 5단계 — 배포 (자동)

`stable` 채널 manifest가 갱신된다. 사용자 에이전트가 다음 실행 때 감지하고, **사용자 승인을 받아** 교체·검증한다. 실패하면 자동 롤백한다(§5.4).

#### 6단계 — 관측·자동 회수 (대부분 자동)

- 설치 성공·실패 분포, 검증 실패 건수, 버전 분포를 서버가 집계한다.
- **실패율이 임계를 넘으면 사람 없이 자동 `revoke`한다.** 이후 에이전트는 그 번들을 거부하고 이전 승인 버전을 유지한다.
- 회수는 삭제가 아니라 **상태 변경**이다. 이미 설치된 PC는 다음 확인 시 경고를 받는다.
- 자동 회수가 발생하면 그때만 사람에게 알린다.

### 14.6 승인 자동화 설계 (보안팀 부담 최소화)

보안팀은 추가 업무를 부담스러워한다. 이는 저항이 아니라 **현실**이며, 부담이 큰 절차는 반드시 형식화된다. 매번 눌러야 하는 승인 버튼은 결국 읽지 않고 눌리므로, **부담을 줄이는 것이 곧 통제를 유지하는 방법이다.**

원칙은 하나다. **보안팀에게는 "판단"만 남기고 "확인 작업"은 전부 기계에 넘긴다.**

#### 14.6.1 자동 승인 정책 — 강화는 자동, 완화는 사람

핵심 기준은 컴포넌트가 아니라 **변경의 방향**이다.

| 변경의 방향 | 오염·오류 시 결과 | 처리 |
|---|---|---|
| 판정을 **강화**(경고·차단을 추가) | 오탐이 늘어난다 — 불편하지만 안전 | **자동 승인** |
| 판정을 **완화**(차단을 해제·룰 삭제·심각도 하향) | 위험이 그대로 통과한다 — 미탐 | **사람 승인 필수** |

이 기준으로 실제 정책을 만든다.

| 대상 | 기본 | 사람 승인으로 승격되는 조건 |
|---|---|---|
| 인텔 번들 | **자동** | 레코드 급감, 서명 실패, 소스 누락, TTL 초과 |
| 룰셋 — 규칙 추가만 | **자동** | — |
| 룰셋 — 규칙 삭제·심각도 하향·예외 추가 | 사람 | 항상 |
| 체커 패치(x.y.**z**) — 의존성 변경 0건 | **자동** | 의존성 추가·변경, floor 상승, 게이트 경고 |
| 체커 마이너·메이저(x.**y**.z / **x**.y.z) | 사람 | 항상 |
| 하네스 | 사람 | 항상 (기관 정책 변경이므로) |
| 에이전트 본체 | 사람 + 사전 협의 | 항상 (분기 1회) |

#### 14.6.2 사전 승인(standing approval)

보안팀이 **분기 1회 "정책"에 서명**하면, 그 범위 안의 릴리스는 개별 승인이 필요 없다.

```text
승인 대상: 정책 문서 1건 (분기 1회)
  "checker 1.2.x 패치는 의존성 추가 0건 · 게이트 전체 통과 시 자동 승인한다"
  "룰셋은 규칙 추가만인 경우 자동 승인한다"
  "인텔 번들은 레코드 감소율 20% 미만인 경우 자동 승인한다"
```

정책 밖으로 나가는 건만 개별 승인 대기열에 올라온다. **보안팀이 승인하는 것은 개별 릴리스가 아니라 규칙이다.**

#### 14.6.3 알림 정책 — 평소에는 아무것도 보내지 않는다

"승인해 주세요" 알림이 반복되면 무시된다. **이상 신호만** 보낸다.

| 알림을 보내는 경우 | 이유 |
|---|---|
| 의존성이 추가·변경됨 | 공급망 변화 |
| floor가 상승함 | 직전 버전에 취약점이 있었다는 뜻 |
| 게이트 우회 시도 또는 실패한 채 제출됨 | 절차 이탈 |
| 인텔 레코드 급감 | 미탐 위험 |
| 설치 실패율 임계 초과 → 자동 회수 발생 | 사고 |
| 정책 범위를 벗어난 릴리스 도착 | 판단 필요 |

그 외에는 **주간 다이제스트 1건**으로 갈음한다. 읽지 않아도 되지만 기록은 남는다.

#### 14.6.4 자동 승인의 안전장치

자동 승인이 위험하지 않으려면 세 가지가 함께 있어야 한다.

1. **카나리 배포** — 자동 승인된 번들은 먼저 일부(예: 5%) PC에만 배포한다. 정해진 시간 동안 실패율이 정상이면 전체로 확대한다.
2. **자동 회수** — 실패율·검증 실패가 임계를 넘으면 사람 없이 즉시 `revoke`하고 이전 버전을 유지시킨다.
3. **사후 감사 가능성** — 자동 승인 건도 `release_bundles`에 승인 근거(적용된 정책 ID, 판정 값)를 남긴다. 분기 감사에서 정책이 실제로 어떻게 적용됐는지 확인할 수 있어야 한다.

#### 14.6.5 승인 권한 위임

가장 효과가 큰 조치다. **정보보안팀은 정책 소유자로 남고, 일상 승인은 다른 담당이 수행한다.**

| 역할 | 담당 | 빈도 |
|---|---|---|
| 정책 승인·변경 | 정보보안팀 | **분기 1회** |
| 일상 개별 승인 | AI국·정보화 담당(지정 승인자) | 정책 밖 건만 |
| 사후 감사 | 정보보안팀 | 분기 1회 (자동 승인 이력 열람) |
| 사고 대응 | 정보보안팀 | 발생 시 |

이 구조에서 정보보안팀의 실제 작업량은 **분기 1회 정책 검토 + 연 몇 회의 이상 알림 대응**이다. 개발자가 자기 릴리스를 승인하는 경로는 어떤 경우에도 만들지 않는다(§14.7).

### 14.7 예외 경로

**긴급 보안 패치:** `emergency` 채널로 동일 절차를 밟되, 승인 SLA를 별도로 정한다(예: 4시간 내 1인 승인 + 24시간 내 사후 기록). 절차를 건너뛰지 않고 **속도만 올린다.**

**반려 시 회신:** 망연계가 단방향이면 시스템 회신 경로가 없다. 반려 사유는 **전화·메일 등 기존 업무 경로**로 전달한다. 시스템에 양방향 회신을 억지로 만들지 않는다.

**보안팀 부재:** 승인자 대리인을 사전에 지정한다. 지정되지 않은 상태에서 개발자가 자기 릴리스를 승인하는 경로는 **만들지 않는다.** 만들면 2인 원칙이 무너지고, 한 번 열린 우회로는 상시 사용된다.

**CI 실패로 릴리스가 안 될 때:** 게이트를 끄고 내보내지 않는다. 게이트가 잘못됐다면 게이트를 고쳐서 다시 태그한다.

### 14.8 1인 개발 현실 대응

"2인 리뷰"는 개발자가 한 명일 때 성립하지 않는다. 형식만 남기고 실제로는 혼자 승인하게 되면 통제가 아니라 서류가 된다. 다음으로 대체한다.

- **자동 게이트가 코드 리뷰의 자리를 대신한다.** 전체 테스트, 하네스 게이트, 체커 자기검사, 적대적 검증(수정이 새 오탐·미탐을 만들지 반대 방향으로 확인)의 통과 기록을 릴리스 증거로 남긴다.
- **사람 승인은 코드가 아니라 체크리스트를 본다.** 승인자(정보보안담당관 또는 지정 검토자)는 소스를 읽지 않는다. 게이트 통과 여부, 변경 요약, 영향 범위, 롤백 대상만 확인하고 승인한다. 이 역할은 개발을 몰라도 수행 가능하다.
- **개발자와 승인자를 반드시 다른 사람으로 둔다.** 최소 2인 원칙은 여기서만 지킨다. 인원이 늘면 코드 리뷰를 앞단에 추가한다.
- 승인 기록(누가·언제·무엇을)은 `release_bundles`에 남아 감사에 쓰인다.

### 14.9 개발 빌드와 운영 빌드 분리

개발 중에는 승인을 거치지 않은 컴포넌트를 돌려야 한다. 여기서 우회 스위치를 만들면 사용자 PC에서도 켤 수 있게 된다.

- **개발 빌드는 신뢰 루트로 `dev` 공개키를 임베드한 별도 바이너리**다. 운영 빌드는 기관 배포 공개키만 임베드한다. 두 바이너리는 섞이지 않는다.
- `GVSKB_DEV=1` 같은 **환경변수·플래그로 검증을 끄는 경로를 만들지 않는다.** 검증을 끄는 유일한 방법은 애초에 다른 신뢰 루트로 빌드된 다른 실행 파일을 쓰는 것이다.
- 개발 빌드는 UI에 상시 `개발 빌드` 표식을 띄우고, 그 상태로 생성된 보고서에는 `제출용 아님` 워터마크를 넣는다.

정리하면 키는 세 개이며 역할이 겹치지 않는다.

| 키 | 역할 | 어디에 |
|---|---|---|
| `dev` 신뢰 루트 | 개발 빌드 전용 | 개발 PC |
| 개발자 릴리스 키 | 출처 증명(누가 만들었나) | 개발 PC 하드웨어 토큰 |
| 기관 배포 키 | **운영 신뢰 루트**(배포 허가) | 행정망 내부, 보안팀 |

### 14.10 기존 체커 인텔 파이프라인과의 접속

`vibecode-checker`에는 이미 다음이 구현되어 있으므로 **새로 만들지 않고 연결한다.**

| 기존 자산 | 내용 |
|---|---|
| `.github/workflows/update-intel.yml` | 매일 03:00 KST 자동 수집(OSV·KEV·NVD·EPSS) |
| `intel-latest` 롤링 릴리스 | 고정 URL로 번들 + `.sha256` 사이드카 게시 |
| 번들 내부 `manifest.json` | 파일별 SHA-256 |
| `gvskb intel-bundle import` | 망분리 반입 경로 |
| `rules/intel-proposed/` + PR 게이트 | KEV → proposed 룰, 사람 검토, 90일 미승격 시 자동 폐기 |
| `.gvskb/` gitignore | 런타임 캐시가 저장소를 오염시키지 않음 |

반입 파이프라인(§8.2)은 이 `intel-latest` 번들을 받아 **경기도 번들로 다시 포장하고 Ed25519 서명**한 뒤 내부 레지스트리에 등록한다.

**보완이 필요한 2건:**

1. **인텔 번들이 서명되어 있지 않다.** `.sha256` 사이드카는 같은 릴리스에 함께 게시되므로, 릴리스에 쓰기 권한을 얻은 공격자는 zip과 사이드카를 **함께** 바꿀 수 있다. 해시는 전송 오류를 잡지 출처를 증명하지 않는다. → 반입 시점에 오프라인 서명 PC에서 Ed25519 서명을 붙인다(경기도 측 보완으로 가능하며, 체커 저장소 변경 없이 해결된다).
2. **레코드 급감 검사가 없다.** 상류 장애나 수집 실패로 항목이 줄어든 번들이 그대로 통과하면 **미탐**이 된다. 직전 번들 대비 레코드 수 감소율 임계치를 반입 수신 모듈에 넣는다(§8.4).

`intel-latest`는 태그가 이동하는 **가변 릴리스**다(설계상 의도된 것). 따라서 내부 레지스트리는 반입 시점에 **자체 `bundle_id`와 수집 시각을 스탬프**해 고정한다. 그래야 "어떤 인텔로 검사했는가"를 보고서가 말할 수 있다.
