# 서버 기반 포털 재설계 (2026-08-12)

> 이 문서는 사용자(원준석) 지시로 **포털의 범위와 실행 형태를 확정**한다. 이전 문서(01·07·16·18)의 "로컬 웹앱/로컬 에이전트" 전제와 "승격 워크플로 포함" 서술은 이 문서로 대체된다.

---

## 0. 역할 분담 — 이것부터 맞춘다

포털의 범위를 말하기 전에 **누가 무엇을 하는지**가 먼저다. 셋(판정 주체까지 넷)은 겹치지 않게 나뉘어 있고, 하나라도 남의 일을 하기 시작하면 구조가 무너진다.

| 주체 | 성격 | 하는 일 | 하지 않는 일 | **절대 금지** |
|---|---|---|---|---|
| **체커** `gvskb` | **관측** | 코드 룰 검사, 의존성 검사, SBOM 생성, 취약점·악성·라이선스 조회, **보고서 생성**, 관측 번들 생성 | 승인·차단 결정, 설치 차단, 언어 통제, 코드 수정 | **스스로 판정하기.** 체커의 결과는 "이렇더라"이지 "써도 된다"가 아니다 |
| **포털** | **전달·축적** | 공무원이 체커를 쓰게 함, 보고서 **위치 안내**, 하네스·체커 배포와 버전 안내, 관측 축적 → 화이트리스트 근거 | 직접 검사, 판정, PC 조작, 보고서 가공 | **체커 판정을 관대한 쪽으로 바꾸기** |
| **하네스** `vibe_harness` | **집행** | 언어 제한, 패키지 설치 차단·경고·통과, 도구 감지, 설정 파일 백업·수정·복구, MCP 등록, 체커 설치 | 취약점 자체 판단, 보고서 생성 | **체커를 건너뛰고 승인 목록만 보고 통과시키기** |
| **보안부서**(사람) | **판정** | 화이트리스트 확정, 차단 결정, 기본 이미지 빌드 | 코드 열람, 검사 수행 | 근거 없이 판정하기 |

### 고리가 돌아야 제도가 굴러간다

```
체커가 본다 → 포털이 모은다 → 보안부서가 정한다 → 하네스가 막는다
     ↑                                                      │
     └──────── 정해진 것이 체커의 답에 실려 돌아온다 ─────────┘
```

포털의 관리자 기능(화이트리스트 근거 축적)이 중요한 이유가 이것이다. **그 산출물이 최종적으로 하네스의 차단 기준이 된다.** 근거가 쌓이지 않으면 보안부서가 정할 것이 없고, 정해진 것이 없으면 하네스는 계속 "모른다"만 답한다.

### 체커는 두 곳에서 돈다 — 같은 체커, 같은 규칙

| 경로 | 흐름 | 포털의 관여 |
|---|---|---|
| **① 만드는 중** (공무원 PC) | 하네스가 AI 도구에 체커를 붙여 두고(MCP), 패키지 설치 시도 시 **하네스가 체커에게 묻고** 그 답으로 차단·경고·통과 | **없음** — PC 안에서 끝난다 |
| **② 다 만든 뒤** (포털 서버) | 공무원이 업로드 → **포털이 서버의 체커를 실행** → 체커가 검사하고 보고서 생성 | 실행시키고 결과 위치를 안내 |

두 경로가 **같은 체커·같은 규칙**을 쓰므로 "만들 때는 괜찮다더니 올리니까 걸린다"가 생기지 않는다. 체커 버전이 벌어지면 그 약속이 깨지므로, 포털은 최신 버전을 게시하고 관리자 화면에 **서버 체커 버전**을 표시한다.

### 구현 시 어기기 쉬운 경계 다섯

1. **포털이 판정을 관대한 쪽으로 바꾸는 것** — 포털은 체커 판정을 **더 안전한 쪽으로만** 덮어쓸 수 있다. 검사가 잘렸을 때 `allow`를 `incomplete`로 낮추는 것은 되지만, 체커가 `needs_review`라 한 것을 `allow`로 올리는 것은 **절대 안 된다**. 강화는 자동, 완화는 사람이다.
2. **하네스가 체커를 건너뛰는 것** — 승인 목록만 보고 통과시키면 로컬 악성 탐지와 긴급 취약점 대조가 빠진다. 반드시 체커를 경유한다.
3. **"확인 못 함"을 "안전"으로 바꾸는 것** — 조회 실패·검사 미완·대조 불가는 전부 "모른다"다. 특히 **기관 승인 패키지라도 로컬 악성 신호가 뜨면 그것을 가리지 않는다.**
4. **포털이 보고서를 다시 만드는 것** — 체커가 만든 파일 그대로 전달한다. 다시 그리면 결재 문서와 검사 증거가 갈라진다.
5. **감지·설정 변경 로직을 두 곳에 두는 것** — 하네스에만 둔다. 도구 관리자에 중복 구현하면 규칙이 갈라진다.

## 1. 범위 확정 — 포털이 하는 일은 이것뿐이다

### 하는 것

| # | 기능 | 설명 |
|---|---|---|
| 1 | **보안점검** | 체커를 호출해 공무원이 만든 소스를 점검한다 |
| 2 | **간편점검 / 표준점검** | 두 갈래로 나눠 목적에 맞게 고르게 돕는다 |
| 3 | **보고서 안내** | 체커가 만든 리포트의 **위치를 알려 준다**(포털이 다시 만들지 않는다) |
| 4 | **체커·하네스 버전 지원** | 최신 버전 여부를 확인해 주고 설치를 돕는다 |
| 5 | **관리자 — 패키지 근거 축적** | 체커의 SBOM·의존성 검사 결과에서 차단/승인 여부를 확인하고, 안전한 패키지와 문제 있는 패키지를 구분한다. 공무원이 많이 쓰는 라이브러리를 축적해 **보안부서가 화이트리스트를 만들 근거**를 제공한다 |

### 하지 않는 것 — 명시적 범위 밖

- **승격 워크플로**(등급 판정, 승격 신청, 게이트 통과 처리) — 이는 **거버넌스**이며 별도 서버에서 구현한다. 포털은 관여하지 않는다.
- **판정(승인/차단) 권한** — 판정은 보안부서(gg-trusted-registry)가 한다. 포털은 근거를 모아 보여 줄 뿐, 스스로 승인하지 않는다. 3자 구조의 권한 경계를 그대로 지킨다.
- **LLM 호출** — 포털도 체커도 어느 단계에서도 LLM을 부르지 않는다(결재 문서의 재현성).

> **이 범위 확정으로 폐기되는 이전 설계**: 발표자료(v2.1)의 등급 5문항·승격 신청 화면을 포털에 넣자는 제안, `20_설계검증보고` §2-1의 "승격 워크플로 부재" 지적. 부재가 아니라 **범위 밖**이 정답이다.

## 2. 실행 형태 전환 — 로컬 단독 → 서버 기반 다중 사용자

### 확정 사항

포털은 **서버에서 동작**하며 **여러 공무원이 동시에 이용**한다. 개인 PC에 설치해 혼자 쓰는 로컬 웹앱이 아니다.

이것이 낳는 변화는 단순한 배포 위치 변경이 아니다. 다음 네 가지가 근본적으로 달라진다.

| 축 | 로컬 단독(현재) | 서버 기반(목표) |
|---|---|---|
| 검사 대상 전달 | 사용자 PC의 경로를 직접 읽음 | **업로드**로 받음 |
| 동시성 | 한 번에 한 명 | 동시 다수 → **큐·상한 필수** |
| 결과 접근 | 전부 내 것 | **소유자 검증 필수** |
| 신원 | 관리자 1명 자체 계정 | **기관 통합인증**(차단조건 B3가 실질 조건이 됨) |

### 이 전환이 원래 설계와 오히려 정합하다

발표자료(v2.1)의 구역 설계에는 이미 **DEV-PORTAL**("포털·인증·조달 프록시 — 공무원이 처음 만나는 화면")과 **DEV-RUN**("체커 실행")이 있다. 서버 기반 포털은 바로 이 두 서버에 해당한다. **로컬 웹앱이 오히려 임시 형태였고**, 서버로 가는 것이 본래 구성으로 돌아가는 것이다.

또한 목표설계(docs/18)의 원칙 D1 "브라우저는 로컬 API를 절대 호출하지 않는다"는 서버 기반에서 **자동으로 충족**된다. 브라우저는 서버 API만 부른다. `20_설계검증보고` §4에서 "구조적 블로커"로 지적한 D1 상충은 이 전환으로 해소된다.

## 3. 망 배치 — 논리적 망분리 + 망중계서버

### 사실 정정

경기도는 **물리적 망분리가 아니라 논리적 망분리**다. **망중계서버가 있어 내외부망 연계가 가능**하다. (이전 문서들이 "행정망은 온라인 조회 불가"만 강조해 연계 가능성을 과소평가했다 — 이 문서로 정정한다.)

### 배치 결정

**포털 서버는 인터넷망에 둔다.** 근거:

1. 바이브코딩 자체가 인터넷망에서 이뤄진다(외부 AI API 필요).
2. 체커가 취약점 DB·패키지 레지스트리(OSV, npm, PyPI)를 조회하려면 인터넷이 필요하다.
3. 논리적 망분리이므로 **직원 PC 한 대에서 인터넷망 서비스에 URL로 접근**할 수 있다. 행정망 전용 포털을 따로 둘 이유가 없다.

```
[직원 PC] ──(논리적 망분리, URL 접근)──> [인터넷망: 포털 서버 + 체커]
                                              │
                                              │ 화이트리스트·판정 데이터
                                              ↓
                                        [망중계서버]
                                              ↓
                                    [행정망: 보안부서 시스템 / 운영 환경]
```

### 망중계서버를 쓰는 지점

포털의 일상 동작에는 망중계가 필요 없다(전부 인터넷망 안에서 끝난다). 망중계는 **결과물을 행정망으로 넘길 때만** 쓴다.

- 축적된 패키지 화이트리스트 후보 → 행정망 보안부서로 전달
- 보안부서 판정 결과 → 포털로 반입(선택)

전달 방식은 망중계서버의 허용 규격을 따른다. **규격 확인이 필요한 항목**(§9-1)으로 남긴다.

## 4. 핵심 설계 결정

### 4-1. 소스 보관 정책 — 가장 중요

**서버 기반으로 가면 여러 부서의 소스가 한 서버에 모인다.** 이는 기존 제품 원칙("소스를 서버에 보내지 않는다")을 뒤집는 변경이며, **서버 자체가 고가치 표적**이 된다는 뜻이다.

이 위험은 가정이 아니라 실증됐다 — 2026-08-10 시흥시 TLS 개인키 사고(`21_보안사고_시흥시TLS개인키.md`)가 정확히 "검사용으로 올라온 타 기관 소스에 개인키가 들어 있었고, 그것이 삭제되지 않고 쌓였다"는 사건이다. 로컬에서도 그랬는데 서버에 모이면 규모가 커진다.

**따라서 다음을 절대 원칙으로 건다.**

| 원칙 | 구현 |
|---|---|
| 원본 미보관 | 검사 종료 즉시 업로드본 삭제. 성공·실패·타임아웃·서버 재기동 **어느 경우에도** 삭제 보장 |
| 작업별 격리 | 업로드는 작업 UUID 디렉터리에만. 작업 간 교차 접근 불가 |
| 기동 시 소거 | 서버가 뜰 때 검사 작업 영역 전체를 비운다(현재 구현됨) |
| 결과만 저장 | DB에는 메타데이터·판정·패키지 관측만. **소스 조각·전체 경로·개인식별자 저장 금지** |
| 보고서 보존 기한 | 다운로드 후 N일 경과 시 자동 삭제(기본 7일). 기한은 운영 정책으로 확정 |
| 저장소 위치 | 업로드·작업 영역은 **동기화·백업 대상 밖**에 둔다(OneDrive류 금지 — 시흥시 사고의 직접 원인) |

### 4-2. 동시성

현재 코드는 요청이 오는 대로 체커를 무제한 spawn한다. 다중 사용자 서버에서는 그대로 두면 서버가 죽는다.

| 항목 | 기준 |
|---|---|
| 동시 실행 상한 | `min(4, CPU코어-2)` 기본. 환경변수로 조정 |
| 대기열 | 상한 초과 시 큐 적재. 사용자에게 **대기 순번** 표시 |
| 작업 타임아웃 | 간편 5분 / 표준 20분. 초과 시 중단하고 정리 |
| 업로드 상한 | 요청당 500MB·파일 1만 개(현행 유지), **사용자당 동시 작업 1건** |
| 디스크 워터마크 | 작업 영역 사용률 임계 초과 시 신규 접수 중단 + 관리자 경보 |

### 4-3. 접근 통제

현재는 `scan_id`만 알면 누구나 결과를 조회할 수 있다(단일 사용자 전제). 서버에서는 정보 유출이다.

- 모든 검사 작업에 **소유자(사용자 ID)** 를 바인딩한다.
- 진행률·결과·보고서 다운로드 전부 소유자 검증을 거친다.
- 관리자는 **집계와 메타데이터**를 보되, 타인의 보고서 본문은 기본 비열람(필요 시 별도 권한·감사 기록).
- `scan_id`는 추측 불가한 UUID를 유지하되, **UUID를 접근 통제 수단으로 쓰지 않는다.**

### 4-4. 인증

서버 기반 + 소유자 검증 + 관리자 기능이므로 인증이 필수가 된다. **차단조건 B3(기관 통합인증 연계)가 이제 실질적 선행조건**이다.

- 방식: 기관 통합인증(Keycloak OIDC / 기관 SSO / GPKI). **자체 ID·비밀번호 구현 금지**(정책).
- 구조: **인증 어댑터 인터페이스**를 두고 구현체를 갈아끼운다. 개발·시범 단계에서는 임시 구현체를 쓰되 "중앙 전환 시 폐기" 표시를 화면과 코드에 남긴다.
- 저장: 사용자 식별자는 **해시**로, 부서는 **부서코드**만 저장한다. 이름·연락처는 저장하지 않는다.
- 부서코드가 필요한 이유: 화이트리스트 근거의 핵심 지표가 "**어느 부서에서 얼마나 쓰는가**"이기 때문이다. 익명만으로는 "많이 쓰는 라이브러리"의 설득력이 약해진다.

## 5. 관리자 기능 — 패키지 화이트리스트 근거 축적 (핵심 신규)

### 5-1. 입력 — 체커가 이미 다 만들어 준다

검사 1회당 체커가 산출하는 `*.registry-bundle.json`(스키마 `gvskb-registry-bundle/1`)에 필요한 데이터가 전부 들어 있다. 실측(포털 자체 검사 1회):

- 패키지 **188건** — `manifest` 20 / `lockfile` 148 / `installed` 20
- 생태계 — npm 152 / PyPI 36
- 판정 — `checked_clean` 180 / `vulnerable` 7 / `not_found` 1

항목별 필드: 이름·버전·생태계·`verdict`·취약점 수·`max_cve`·`in_kev`/`kev_checked`·라이선스·`install_scripts`·배포 경과일·`deprecated`·타이포스쿼팅 휴리스틱·`registry_status`/`registry_decision`·`source_scope`.

> **포털은 이 데이터를 새로 만들지 않는다. 모아서 보여 줄 뿐이다.**

### 5-2. 축적 규칙 (연동합의 준수)

| 규칙 | 내용 |
|---|---|
| 관측은 전부 저장 | `manifest`·`lockfile`·`installed` 모두 축적한다. **실제 위험은 대부분 전이 의존성(lockfile)에서 나온다** — 실측상 148/188이 lockfile이다 |
| 심사 큐는 좁게 | 사람이 볼 대기열에는 **`single`·`manifest`만** 올린다. lockfile·installed까지 올리면 담당자 일이 폭증해 제도가 무너진다 |
| 되돌림 방지 | 버전 미확정, `unknown`/`error` 항목은 판정 근거로 쓰지 않는다 |
| 침묵 금지 | `checked=false`, `registry_status≠ok`는 **안전이 아니라 "확인 못 함"** 으로 표시한다. `in_kev=false`는 `kev_checked=true`일 때만 의미가 있다 |
| 판정 우선순위 | 로컬 악성 탐지가 기관 승인보다 우선한다. 승인된 패키지라도 악성 신호가 뜨면 그것을 가리지 않는다 |

### 5-3. 관리자 화면 (4개)

**① 화이트리스트 후보** — 이 기능의 목적 그 자체
```
정렬: 사용 부서 수 ↓, 사용 프로젝트 수 ↓
필터: 판정 없음(미심사) + verdict=checked_clean + 취약점 0
표시: 패키지 / 생태계 / 버전 분포 / 사용 부서 수 / 사용 프로젝트 수 /
      최초·최근 관측일 / 라이선스 / install_scripts 유무
동작: [선택 → 화이트리스트 후보 내보내기] — 승인 버튼은 두지 않는다
```
가장 많이 쓰이면서 아직 화이트리스트에 없는 패키지가 맨 위에 온다. **보안담당자는 위에서부터 처리하면 커버리지가 가장 빨리 올라간다.**

**② 문제 패키지** — `vulnerable`·`malicious`·`not_found`·`deprecated`·`install_scripts` 있음·타이포스쿼팅 의심. 각 항목에 **영향받는 프로젝트 수**를 함께 보여 조치 우선순위를 잡게 한다.

**③ 패키지 상세** — 버전별 관측 이력, 사용 부서 분포, 취약점 이력, 판정 이력(누가 언제 왜), `source_scope` 분포.

**④ 판정 현황** — 화이트리스트 등재 건수, 차단 건수, 판정 신선도(승인 1시간·차단 7일 비대칭 규칙), 대기 건수, 커버리지("관측 패키지 중 화이트리스트에 들어간 비율").

### 5-4. 출력 — **1차 범위는 "지원까지"로 확정** (2026-08-13)

**포털에 승인·차단 버튼을 만들지 않는다.** 1차 목표는 보안담당자가 **화이트리스트를 만들고 그것으로 기본 이미지를 굽도록 지원하는 데까지**다. 결재 절차를 포털에 붙이는 것은 화이트리스트가 실제로 운용되기 시작한 뒤에 판단해도 늦지 않다.

이유는 둘이다. ① 판정은 보안부서 소관이고, 포털이 승인까지 하면 **검사한 쪽이 스스로를 승인**하는 구조가 된다. ② 지금 필요한 것은 근거를 모아 주는 일이지 결재 시스템이 아니다.

**내보내기 형식** — 검토용 목록에 그치지 않고 **이미지 빌드에 바로 투입할 수 있는 형태**로 낸다.

| 형식 | 용도 |
|---|---|
| `requirements.txt` (버전 고정) | PyPI — 기본 이미지 빌드에 직접 투입 |
| `package.json` dependencies (버전 고정) | npm — 동일 |
| 저장소 프록시 허용목록 | Nexus 등 사내 저장소의 허용 규칙 |
| CSV / JSON | 사람이 검토하고 결재에 붙이는 용도 |

모든 내보내기는 **소스·파일 경로·개인식별자를 포함하지 않는다**(허용목록 스키마). 망중계로 행정망 전달이 가능한 형태로 만든다.

**판정 반입**은 유지한다 — 보안부서가 확정한 화이트리스트·차단 목록을 파일로 반입해 포털이 **표시**한다. 반입분은 **서명 검증 후에만** 적용하고, 검증 실패 시 전량 거부한다(부분 적용 금지).

> DB의 `package_decisions` 테이블은 스키마에 남겨 둔다. 1차에서는 **반입 경로로만 쓰기**가 일어나고, 포털 화면에서의 직접 판정은 만들지 않는다.

## 6. 현재 코드 재평가 — 재사용 / 수정 / 폐기

전체적으로 **핵심 파이프라인은 그대로 살고, 로컬 전용 껍데기만 걷어내면 된다.** 브라우저 업로드 경로가 이미 구현되어 있어 전환 비용이 낮다.

### 그대로 재사용

| 대상 | 위치 |
|---|---|
| 체커 호출·프로파일 분기·판정 해석 | `runScanJob` (`src/server.js`) |
| 브라우저 업로드 수신 | `receiveBrowserTarget` — **이것이 유일한 입력 경로로 승격** |
| ZIP 사전검사(폭탄·경로탈출) | `assertSafeArchive` — 서버에서 더 중요해짐 |
| 보고서 생성·한글 파일명 | `reportStemForJob`, `serveReport` |
| 진행률 추정 | `progressForJob` |
| 작업 영역 정리 | `cleanupJobTargets`, `purgeOrphanScanTargets` |

### 수정

| 대상 | 변경 |
|---|---|
| 바인딩 | `127.0.0.1` → 리버스 프록시 뒤 서비스 바인딩 + TLS 종단 |
| 요청 경계 | 로컬 토큰(`X-VibeCode-Local-Token`)·Host 정확일치 → **세션 기반 CSRF 토큰 + 표준 Origin 검증** |
| 인증 | 자체 scrypt 관리자 계정 → **기관 통합인증 어댑터** |
| 저장 | `.local/scan-history.jsonl` → **PostgreSQL** |
| 결과 조회 | 무제한 → **소유자 검증** |
| 실행 | 무제한 spawn → **큐 + 동시 실행 상한** |
| 관리자 | 단순 현황 → **패키지 축적·화이트리스트 후보**(§5) |

### 폐기 — 서버에서 동작해선 안 되는 것

| 대상 | 이유 |
|---|---|
| **PowerShell 파일 선택창** (`pickLocalPath`, `folderPickerScript`) | 서버에서 실행하면 **서버 콘솔에 대화상자가 뜬다.** 다중 사용자 환경에서 명백한 결함 |
| `target_type: "folder"`·`"archive"` (로컬 절대경로) | 서버에는 사용자의 로컬 경로가 존재하지 않는다 |
| 사용자 PC 설치·MCP 등록 (`installComponent`, `registerMcp`) | 서버가 사용자 PC를 조작할 수 없다. **폐기가 아니라 도구 관리자로 이관**한다(§7) — 로직은 그대로 살린다 |
| 결과 저장 폴더 선택 (`save_dir`) | 서버 파일시스템을 사용자가 고를 수 없다 → **다운로드**로 대체 |

> ZIP 사전검사가 PowerShell에 의존하므로, 서버 OS가 Linux면 **Node 순수 구현 또는 `unzip` 기반으로 대체**해야 한다(§9-2).

## 7. 체커·하네스 설치 지원 — **도구 관리자 방식으로 확정** (2026-08-13)

### 먼저 확인해야 할 기술적 사실

**웹페이지는 사용자 PC에 무엇이 설치돼 있는지 볼 수 없다.** 이는 구현 난이도의 문제가 아니라 브라우저가 의도적으로 막아 둔 경계다. 웹페이지가 `gvskb version`을 실행하거나 PATH·설치 경로를 읽을 방법은 없다(있다면 임의의 웹사이트가 방문자 PC를 조사할 수 있다는 뜻이다).

따라서 "현재 버전 확인 → 최신과 비교 → 업데이트 버튼"이라는 흐름은 **웹 화면에서는 성립하지 않는다.** 그 화면은 **PC에서 실행되는 프로그램**이 띄워야 한다.

### 확정: 책임을 세 층으로 나눈다 (하네스팀 협의 반영, 2026-08-13)

| 층 | 담당 | 하는 일 |
|---|---|---|
| **웹 포털** (서버) | 포털팀 | 설치·연결 **안내**, 설치 파일 배포, 도구별 **지원 범위** 표시, 최신 버전 게시, 설치기가 보고한 **상태 표시**, 관리자 조회 |
| **설치기 겸 도구 관리자** (PC) | 포털팀 | 실행 UI. 처음 실행하면 설치기, 이후 실행하면 관리자 화면(버전 비교·업데이트). 하네스 스크립트를 호출하고 결과를 서버에 **최소 정보만** 보고 |
| **하네스** (PC) | 하네스팀 | 실제 PC 조작 — **도구 감지**, 설정 파일 **백업·수정·복구**, MCP 등록, 체커 설치, 보고서 PC 저장 |

**웹 브라우저는 어느 층에서도 PC 설정 파일을 직접 만지지 않는다.** 브라우저가 Codex·Claude 설정을 바꿀 수 있게 되면 임의의 웹사이트에도 같은 통로가 열린다.

### 사용자가 겪는 흐름

1. 포털 `/tools`에서 **내가 쓰는 AI 도구가 지원되는지** 확인한다(Codex CLI·VS Code / Claude Code / ChatGPT·Codex 데스크톱 / Claude Desktop).
2. 설치 파일을 내려받는다. 이때 포털이 **일회용 등록 토큰**을 함께 넣어 준다.
3. 설치 파일을 실행한다.
4. 설치기가 **PC에 실제로 깔려 있는 도구를 감지**한다(포털에서 고른 것이 아니라 감지 결과가 기준이다).
5. **감지된 도구에만** 하네스 지침과 MCP 설정을 적용한다. 없는 도구는 건드리지 않는다.
6. 완료 화면에 **적용된 도구 · 체커 버전 · 다음에 할 일**을 보여 준다.
7. 설치기가 최소 상태 정보를 서버에 보고한다 → 이후 포털 `/tools`에서도 **내 PC 상태**가 보인다.

> 포털에서의 "도구 선택"은 **지원 범위 안내**를 위한 것이지 적용 대상 지정이 아니다. 사용자가 자기 PC에 무엇이 깔렸는지 정확히 모를 수 있으므로 **적용 기준은 항상 설치기의 감지 결과**다.

### 상태 보고 — 방향이 반대라 안전하다

브라우저가 로컬을 호출하는 것은 위험하지만, **로컬 프로그램이 서버를 호출하는 것(아웃바운드)** 은 일반적인 클라이언트 동작이며 안전하다. 이 방향이면 D1 원칙에도 저촉되지 않는다.

- 최초 1회: 설치기가 **일회용 등록 토큰**으로 자신을 등록한다. 토큰은 포털 로그인 상태에서 발급되므로 어느 사용자·부서인지 서버가 안다.
- 이후: 버전·MCP 연결 상태만 갱신 보고한다.
- **보고 항목은 최소로 고정한다** — 익명 클라이언트 ID, OS 종류, 도구 관리자 버전, 체커 버전, 하네스 커밋, 도구별 연결 여부. 그 이상은 받지 않는다. DB의 `client_installations` 테이블이 정확히 이 형태다.
- 보고하지 않는다: 파일 경로, 프로젝트 이름, 소스, 사용자 이름·PC 이름.

이 보고가 있어야 포털이 **"설치 버전 vs 최신 버전"** 을 화면에 띄울 수 있다. 보고가 없으면 포털은 최신 버전만 알 뿐 사용자 PC 상태를 모른다.

### 도구 관리자는 새로 만드는 것이 아니다

현재 로컬 포털이 이미 이 일을 하고 있다. **폐기가 아니라 이관이다.**

| 기존 코드 | 도구 관리자에서의 역할 | 실제 PC 조작 주체 |
|---|---|---|
| `simpleVersionStatus` | 설치 버전 vs 최신 비교, `current`/`update_available`/`reinstall_required` 판정 | 도구 관리자 |
| `installComponent` | 임시 위치에 받기 → 검증 → 기존 백업 → 교체 → 재검증 | 하네스 `checker-bootstrap.mjs`·`gg-validate.ps1` 호출 |
| `applyUpdates` | `--ff-only` 갱신 후 재검증 | 하네스 검증 스크립트 호출 |
| `registerMcp` | 도구 감지 결과에 따라 MCP 등록(설정 백업 후) | **하네스가 감지·수정·복구** |
| `mcpSummary` | 도구별 연결 상태 확인 | 하네스 감지 결과 사용 |
| `design/html-prototype/skill-harness.html` | 도구 관리자 화면의 원형 | — |

업데이트 시 **고쳐 쓴 흔적이 있으면 덮어쓰지 않고 재설치를 유도**하는 현재 동작도 그대로 유지한다. 사용자가 "지우고 새로 설치"를 고르면 그 경로도 지원한다.

> **분계선**: 도구 관리자는 *언제 무엇을 할지* 정하고 결과를 보여 주는 층이고, *실제로 PC를 바꾸는* 것은 하네스 스크립트다. 감지·백업·복구 로직을 도구 관리자에 중복 구현하지 않는다 — 하네스팀 소관이며, 두 곳에 두면 규칙이 갈라진다.

### 웹 화면 안에서 로컬 프로그램을 부르지 않는 이유

브라우저가 `http://127.0.0.1`의 로컬 프로그램을 호출하게 만들면, **임의의 웹사이트도 같은 방법을 쓸 수 있는 통로**가 열린다(CSRF·DNS 리바인딩). 목표설계 원칙 D1("브라우저는 로컬 API를 호출하지 않는다")이 이를 금지한 이유다. 창을 분리하면 그 통로 자체가 생기지 않는다. HTTPS 페이지에서 HTTP 로컬호스트로의 혼합 콘텐츠 차단 문제도 함께 사라진다.

### 남은 선행조건

도구 관리자는 배포 파일이므로 **코드서명(B2)** 이 필요하다. 확보 전까지는 설치 파일의 **SHA-256 확인값을 웹에 함께 게시**하고, 신뢰 근거가 서명이 아닌 해시 공지임을 명시적으로 기록한다.

관리자 화면에는 별도로 **서버 자체의 체커 버전**을 표시한다(서버 체커가 낡으면 모든 사용자의 점검 품질이 함께 낡는다).

## 8. 구현 착수 순서

각 단계는 앞 단계 없이도 의미가 있고, 순서대로 위험이 줄어든다.

| 단계 | 내용 | 선행조건 |
|---|---|---|
| **S1** | 로컬 전용 요소 제거(§6 폐기 목록) + 업로드를 유일 입력으로 정리 | 없음 |
| **S2** | 큐·동시 실행 상한·타임아웃·디스크 워터마크 | 없음 |
| **S3** | PostgreSQL 연결 + 이력·관측 저장(`db/schema.postgresql.sql`) | DB 인스턴스 |
| **S4** | 인증 어댑터 + 소유자 검증 + 보고서 접근 통제 | 임시 구현체로 착수 가능, **확정은 B3** |
| **S5** | 관리자 패키지 축적·화이트리스트 후보 화면(§5) | S3 |
| **S6** | 내보내기(이미지 빌드용 형식 포함)·반입 | **망중계 규격 확인** |
| **S7** | 서버 배포(리버스 프록시·TLS·로그·백업) | 서버 자원 배정 |
| **S8** | **도구 관리자 분리**(§7) — 기존 설치·업데이트·MCP 코드를 떼어 별도 프로그램으로 | 배포 시 **B2 코드서명**(미확보 시 해시 공지로 임시 운영) |

S1·S2는 지금 바로 착수할 수 있다. S8은 기존 코드를 옮기는 작업이라 신규 개발 부담이 작고, 웹 포털 작업과 **병행 가능**하다.

## 9. 남은 결정 — 확인이 필요한 항목

1. **망중계서버 전달 규격** — 허용 확장자·크기 상한·주기·신청 절차. 화이트리스트 내보내기(S6) 설계에 필요.
2. **서버 OS** — Linux면 ZIP 사전검사의 PowerShell 의존을 걷어내야 한다(Windows면 현행 유지 가능).
3. ~~설치 지원 방식~~ → **확정(2026-08-13): 도구 관리자 방식**(§7). 웹은 최신 버전 안내·설치 파일 제공까지, 버전 비교와 업데이트는 PC의 도구 관리자가 한다. 기존 로컬 포털 코드를 이관해 재활용한다.
4. **서버 자원** — vCPU·메모리·디스크. 동시 실행 상한과 업로드 보존 기한이 여기서 나온다.
5. **보고서 보존 기한** — 기본 7일 제안. 기관 기록물 기준과 대조 필요.
6. **부서코드 확보 경로** — 통합인증이 부서 정보를 주는지, 아니면 사용자가 선택하는지.
7. **일반 사용자 인증 범위** — 전원 로그인인지, 열람은 익명이고 검사만 로그인인지.
