# 보안사고 대응 기록 — 타 기관(시흥시) TLS 개인키 노출

작성 2026-08-12 · 발견 2026-08-10 · 상태 **진행 중**(기관 통보·키 폐기 미완)

---

## 1. 사고 개요

경기도 바이브코딩 보안점검 포털의 **검사 대상 임시 폴더**(`tmp/scan-targets/`)에, 검사를 위해 업로드된 타 기관 프로젝트(「응소ON」/`disaster-response`)의 사본이 삭제되지 않고 남아 있었다. 그 안에 **시흥시 와일드카드 TLS 인증서의 개인키**와 Flask 애플리케이션 비밀키가 포함되어 있었다.

포털은 검사 후 임시 폴더를 정리하도록 설계돼 있으나(`cleanupJobTargets`), 과거 실행분이 정리되지 않은 채 누적됐고, 해당 폴더가 **OneDrive 동기화 경로 안**에 있었던 탓에 로컬 삭제만으로는 노출이 끝나지 않는 상태였다.

## 3. 위험 평가

**현재 위험도: 중(中)** — 낮아졌으나 해소된 것은 아니다.

- **완화 요인**: 해당 인증서는 2026-07-18에 만료되었다. 만료 인증서로는 브라우저가 TLS 연결을 거부하므로, **이 인증서 자체를 이용한 사이트 위장은 불가능**하다.
- **잔존 위험(핵심)**: 인증서 갱신 시 **동일한 개인키를 재사용**하는 관행이 널리 퍼져 있다. 시흥시가 2026년 7월 갱신 때 같은 키로 CSR을 만들었다면, **현재 유효한 신규 인증서가 이미 노출된 개인키와 짝을 이루고 있어 위험은 그대로 살아 있다.**
- **부수 위험**: 과거 트래픽을 기록해 둔 공격자가 있다면 RSA 키 교환 구간에 한해 소급 복호화가 가능하다(ECDHE 사용 시에는 해당 없음). Flask `.secret_key`는 세션 위조에 직접 쓰이므로 해당 시스템이 운영 중이면 즉시 교체 대상이다.

**따라서 시흥시가 확인해야 할 단 하나의 질문**은 이것이다 — *"2026년 7월 갱신한 `*.siheung.go.kr` 인증서의 공개키가 이전 인증서와 동일한가?"* 동일하다면 **즉시 재발급(키 신규 생성) + 기존 인증서 폐기(revoke)** 가 필요하다.

## 5. 시흥시 통보 문안 (초안)

> 전달 경로: 시흥시 정보통신과(정보보안 담당) 유선 연락 후 공문 또는 메일. **개인키 파일 자체를 첨부하지 말 것.** 인증서 지문으로 특정하면 충분하다.

---

**제목: 「응소ON」 프로젝트 소스 내 TLS 개인키 포함 사실 통보 및 확인 요청**

1. 귀 시의 정보보안 업무에 노고가 많으십니다.

2. 경기도 AI산업육성과는 공공 바이브코딩 산출물의 보안점검 도구를 개발·시험하는 과정에서, 시험 대상으로 제공받은 「응소ON」(disaster-response) 프로젝트 소스에 **귀 시의 TLS 인증서 개인키 파일이 포함되어 있음**을 확인하였습니다.

3. 확인된 내용은 다음과 같습니다.
   - 파일: `ssl/STAR.siheung.go.kr_key.pem` (RSA 개인키)
   - 해당 인증서: `CN=*.siheung.go.kr`, 발급자 DigiCert/Thawte TLS RSA CA G1
   - 유효기간: 2025-06-17 ~ 2026-07-18 (**현재 만료**)
   - SHA-256 지문: `8C:7E:78:6A:A0:4A:D3:C4:7B:B0:D5:AD:A6:CA:64:58:D1:E3:49:0C:E4:5E:C9:7E:38:47:E1:4F:CC:30:B1:B7`
   - 동일 경로에 애플리케이션 비밀키(`.secret_key`) 파일도 포함

4. 본 건은 외부에 공개되지 않았으며, 경기도 내부 비공개 저장소에서만 확인되었습니다. 형상관리(Git) 이력에는 포함되지 않았음을 확인하였고, **관련 파일 일체를 2026년 8월 12일 삭제 완료**하였습니다. 클라우드 동기화 이력도 함께 정리하였습니다.

5. 다만 다음 사항의 확인을 요청드립니다.
   - **2026년 7월 인증서 갱신 시 기존 개인키를 재사용하셨는지** 확인 부탁드립니다. 재사용하셨다면 현재 유효한 인증서도 노출된 키와 연결되므로, **새 키를 생성하여 재발급하고 기존 인증서를 폐기(revoke)** 하실 것을 권고드립니다.
   - 「응소ON」 애플리케이션이 운영 중이라면 `.secret_key` 값 교체를 권고드립니다.
   - 소스 저장소에 인증서·개인키를 함께 보관하지 않도록 분리하실 것을 권고드립니다.

## 6. OneDrive 휴지통·버전 기록 정리 절차

로컬 삭제만으로는 끝나지 않는다. OneDrive는 삭제 파일을 휴지통에 보관하고, 파일별 버전 기록도 별도로 유지한다.

1. **Windows 휴지통 비우기** — 탐색기 → 휴지통 → 비우기 (동기화 폴더에서 지운 파일이 여기 들어감)
2. **OneDrive 웹 휴지통** — <https://onedrive.live.com> 로그인 → 좌측 **휴지통** → 시흥시/응소ON 관련 항목 선택 → **삭제**(영구 삭제)
3. **2단계 휴지통** — 휴지통 화면 하단의 「두 번째 단계 휴지통」(비즈니스 계정은 *Second-stage recycle bin*) → 같은 항목을 다시 영구 삭제. **이 단계를 빠뜨리면 최대 93일간 복원 가능한 상태로 남는다.**
4. **버전 기록 확인** — 파일 자체를 영구 삭제하면 버전 기록도 함께 사라진다. 다만 **삭제하지 않고 덮어쓴 파일**이 있다면 해당 파일 우클릭 → 「버전 기록」에서 이전 버전을 개별 삭제해야 한다.
5. **정리 후 확인** — OneDrive 웹 검색창에 `siheung`, `.pem`, `secret_key`를 각각 검색해 결과가 0건인지 확인한다.

> 참고: 기관 계정(Microsoft 365) OneDrive라면 관리자 보존 정책에 따라 사용자 삭제 후에도 보존 저장소에 남을 수 있다. 그 경우 정보보안 담당에게 보존 정책 적용 여부를 확인해야 완결된다.

## 7. 남은 원본 파일 — 결정 필요

다음 위치에 **개인키 원본이 그대로 남아 있다.** 이 파일은 도구가 만든 파생 사본이 아니라 최초 내려받은 원본이므로, 임의 삭제하지 않고 판단을 남겨 둔다.

```
C:\Users\first\Downloads\응소ON\ssl\STAR.siheung.go.kr_key.pem
C:\Users\first\Downloads\응소ON\disaster-response\ssl\STAR.siheung.go.kr_key.pem
```

- 인증서 지문은 §2에 채증해 두었으므로 **삭제해도 통보·소명 근거는 남는다.**
- 권고: 시흥시 통보(§5-A)를 마친 뒤 삭제한다. 통보 전에 삭제하면 담당자가 "어떤 파일이냐"고 물었을 때 대조가 어려울 수 있다.
- 삭제 명령(통보 후 실행):
  ```powershell
  Remove-Item -Recurse -Force "$env:USERPROFILE\Downloads\응소ON"
  ```
  삭제 후 Windows 휴지통도 비울 것.

## 8. 재발 방지 — 이번 사고가 드러낸 구조적 결함

1. **검사 임시 폴더가 정리되지 않고 누적됐다.** 포털은 작업 종료 시 `cleanupJobTargets`로 정리하지만, 실패·중단된 작업의 잔존물이 남았다. → **2026-08-12 조치 완료**: `src/server.js`에 `purgeOrphanScanTargets()`를 추가해 **기동 시마다 `tmp/scan-targets` 전체를 비운다.** 기동 시점에는 실행 중인 작업이 있을 수 없으므로 모든 항목이 고아다. 검증: 시험용 폴더 2개를 만들고 기동 → 자동 정리 확인, `npm run guard` 전체 통과.
2. **검사 작업 폴더가 OneDrive 동기화 경로 안에 있었다.** 타 기관 소스가 클라우드로 자동 업로드되는 구조 자체가 위험하다. → 검사 임시 폴더는 **동기화 대상 밖**(예: `%LOCALAPPDATA%`)으로 옮겨야 한다. 저장소 정본을 OneDrive 밖으로 옮기자는 `20_설계검증보고` §0-2 제안과 같은 뿌리의 문제다.
3. **삭제 조치가 한쪽 저장소에만 적용됐다.** 저장소가 두 벌로 나뉘어 있어 08-10 조치가 절반만 이뤄졌고, 그 사실이 08-12 재점검 전까지 드러나지 않았다. → 저장소 이원화 해소가 보안 사안이기도 하다는 근거.
4. **역설적으로, 이 개인키를 찾아낸 것은 체커였다.** 국정원 안내서식으로 "키 파일을 사전 제외"했다면 발견되지 않았을 파일이다(`가이드대조_국정원AI보안점검안내서` G4 실증 사례). **전체 탐지 먼저 → 정제본 산출** 순서 원칙을 유지해야 한다.
