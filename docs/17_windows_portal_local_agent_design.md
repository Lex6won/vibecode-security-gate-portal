# Windows 웹 포털·로컬 보안 에이전트 권장 설계

## 1. 결론

경기도 환경의 1차 권장안은 **경기도 기관 내부 서버의 중앙 웹 포털**과 **Windows 로컬 보안 에이전트**를 분리하는 구조다. 외부 배포 서버는 재난 복구 또는 향후 대외 서비스가 필요할 때만 검토하며, 1차 운영의 기준 경로는 기관 내부 서버다.

- 웹 포털은 서비스 안내, 승인된 설치 패키지 배포, 업데이트 공지, 설치 번들 목록, 익명 사용 현황, 총괄 관리자 통계를 제공한다.
- 로컬 보안 에이전트는 사용자의 PC에서만 하네스·체커·MCP·원본 소스를 다룬다.
- 원본 소스, 압축파일, 토큰, 전체 로컬 경로, 보고서 본문은 중앙 서버에 보내지 않는다.
- 현재 `vibecode-security-gate-portal`의 Node.js 로컬 서버와 화면은 에이전트 기능의 검증 가능한 프로토타입으로 활용한다. 중앙 포털은 이 프로토타입과 별도 배포·인증·메타데이터 수집 계층으로 구현한다.

브라우저만으로는 파일 시스템, MCP 설정, Python 실행 환경을 안전하게 제어할 수 없다. 따라서 외부 또는 기관 내부에 웹 포털을 배포하더라도 사용자의 실제 점검은 반드시 설치된 로컬 에이전트가 수행한다.

## 2. 해결하려는 문제

공무원이 별도로 Python, Node.js, Git, PowerShell 명령을 설치하거나 이해하지 않아도 다음을 할 수 있어야 한다.

1. 하네스와 체커가 설치되어 있는지, 공식 최신 릴리스인지 확인한다.
2. 폴더, ZIP, GitHub URL의 개발 소스를 PC에서 빠르게 또는 표준 점검한다.
3. HTML, JSON, Markdown 보고서를 사용자가 선택한 PC 폴더에 저장한다.
4. Codex, Claude Code, Claude Desktop 등 사용하는 AI 도구별 MCP 등록 상태를 확인하고 명시적 승인 후 등록한다.
5. 총괄 관리자는 원본 없이 기관의 사용량·결과 요약·반복 취약 유형·체커 개선 후보를 확인한다.

## 3. 권장 아키텍처

```text
공식 GitHub 원본
  -> PR 리뷰·하네스 게이트·체커 적대적 검증
  -> 승인된 tag / release manifest / 서명된 설치 패키지
  -> 기관 내부 승인 번들 레지스트리·배포 서버
  -> 경기도 기관 내부 중앙 웹 포털
       -> 설치 파일 다운로드·업데이트 채널 안내
       -> 승인 번들 목록·익명 메타데이터 수신·총괄 관리자 화면

사용자 Windows PC
  -> 로컬 보안 에이전트
       -> 개인 Python 런타임·체커·룰셋·인텔
       -> 하네스·MCP 설정·GitHub 소스 임시 복제
       -> 로컬 파일 선택·ZIP 해제·점검·보고서 저장
       -> 선택 동의 시 메타데이터만 중앙 포털에 전송
```

### 3.1 기관 내부 중앙 웹 포털

중앙 포털은 경기도 기관 내부 운영 서버에 배포한다. 포털은 설치·업데이트의 안내와 승인 번들의 배포, 관리자 현황 조회를 담당하지만, 로컬 파일 점검 기능을 서버에서 대신 실행하지 않는다.

| 기능 | 중앙 포털 책임 | 원본 소스 취급 |
|---|---|---|
| 서비스 안내·도움말 | 설치 목적, 점검 차이, 보고서 활용 안내 | 없음 |
| 설치·업데이트 배포 | 서명된 설치 파일과 승인된 manifest 제공 | 없음 |
| 운영 정책 | 안정 채널, 최소 엔진 버전, 룰셋·인텔 적용 기준 공지 | 없음 |
| 관리자 현황 | 동의된 사용량·결과 요약·오탐 피드백 조회 | 메타데이터만 |
| 통계·개선 | 반복 규칙, 실패 원인, 버전 분포 분석 | 코드·경로·보고서 본문 금지 |

웹 포털은 `localhost` 에이전트 API를 CORS로 직접 호출하지 않는다. 원격 페이지가 로컬 PC 제어 API를 호출하게 하면 브라우저 보안 모델과 DNS rebinding 위험이 커진다. 설치된 에이전트가 로컬 화면을 열거나, `vibecode-gate://` 같은 등록된 사용자 승인 URI로 자신의 화면을 열도록 한다.

### 3.2 승인 번들 레지스트리와 배포 서버

기관 내부 서버는 GitHub의 `main` 브랜치를 사용자 PC에 직접 전달하지 않는다. 검증·승인된 릴리스만 **승인 번들**로 등록하고, 포털과 에이전트는 이 목록만 신뢰한다.

```text
GitHub 변경 -> PR 검토·자동 게이트 -> 사람 승인 -> tag/release
  -> 서명된 설치 패키지·SBOM·manifest 생성
  -> 기관 내부 승인 번들 레지스트리에 등록
  -> 포털이 현재 승인 버전으로 안내
  -> 에이전트가 레지스트리와 로컬 설치본을 비교
  -> 사용자 승인 후 설치 또는 업데이트
```

승인 번들은 에이전트, 체커, 하네스, 룰셋·인텔을 하나의 호환 조합으로 관리한다. 각 번들에는 버전, 고정 commit 또는 artifact digest, SHA-256, 코드서명, SBOM, 승인자, 승인 시각, 최소 에이전트 버전, 롤백 대상 버전을 기록한다. 긴급 보안 업데이트도 새 승인 번들로 등록하며, 승인 전 GitHub 변경은 사용자 PC의 설치·업데이트 후보가 될 수 없다.

### 3.3 Windows 로컬 보안 에이전트

### 3.2 Windows 로컬 보안 에이전트

에이전트는 사용자별로 설치되는 Windows 프로그램이다. 기본 설치는 관리자 권한 없이 가능하게 설계하고, 기관 정책상 필요한 경우에만 별도 관리자 배포(MSI/MSIX)를 제공한다.

| 구성요소 | 역할 |
|---|---|
| 로컬 UI | 현재 포털 화면을 WebView2 또는 localhost 화면으로 제공 |
| 로컬 API | 파일 선택, 상태 확인, 점검 실행, 보고서 저장, MCP 등록 |
| 체커 런타임 | 사설 Python 런타임과 `gvskb`, 승인된 룰셋·인텔 실행 |
| 하네스 런타임 | 승인된 하네스 버전, 템플릿, 검증 게이트 제공 |
| Git 런타임 | GitHub URL의 shallow clone을 위해 에이전트에 포함 또는 검증된 내장 구성 사용 |
| 업데이트 관리자 | manifest 검증, staging, 백업, 교체, 재검증, 롤백 |

사용자 PC에 Python, Node.js, Git이 없어도 동작해야 한다. 설치 패키지는 필요한 런타임을 에이전트 전용 폴더에 함께 배치한다. 시스템 전역 PATH나 사용자의 기존 개발 도구를 변경하지 않는다.

권장 저장 위치:

```text
%LocalAppData%\Gyeonggi\VibeCodeSecurityAgent\
  app\                 에이전트 실행 파일과 UI
  runtime\             개인 Python·Git 등 사설 런타임
  checker\             승인된 체커, 룰셋, 인텔 manifest
  harness\             승인된 하네스 스냅샷
  data\                설정, 상태, 작업 로그
  cache\               GitHub clone·ZIP 해제 임시 파일
  backups\             업데이트 전 설정·컴포넌트 백업
```

보고서는 이 폴더가 아니라 사용자가 고른 폴더에 저장한다. 임시 대상은 점검 종료 또는 실패 후 정리한다.

## 4. 하네스·체커·MCP의 관계

### 4.1 하네스

하네스는 도구별로 다른 제품이 아니다. 프로젝트에 적용되는 공통 개발 기준이다.

- 허용 개발 언어와 실행 환경을 정한다.
- 기획, 설계, 구현, 테스트, 적대적 검증, 커밋 전 게이트를 강제한다.
- 체커 사용과 안전한 패키지 검증을 개발 흐름에 포함한다.
- Codex와 Claude Code 등 AI 도구가 읽을 수 있는 프로젝트 지침·검증 파일을 제공한다.

따라서 하네스 화면의 공통 버튼은 `설치 버전 확인`, `설치`, `업데이트` 세 개로 유지한다. 설치 후에는 새 프로젝트에 하네스를 적용하는 방법을 안내한다.

### 4.2 체커와 MCP

간편·표준 점검은 **개발이 끝난 소스**를 로컬 에이전트가 검사하는 기능이다. MCP는 **개발 중인 AI 도구**에서 체커를 호출하도록 연결하는 기능이다.

| 구분 | 간편 점검 | 표준 점검 | 체커 MCP |
|---|---|---|---|
| 시점 | 개발 중 수시 확인 | 제출 전·배포 전 | 개발 중 AI 도구 사용 시 |
| 범위 | 비밀값, 인증정보, 고위험 규칙, 의존성 우선 | 전체 코드·의존성·룰셋 | 요청한 코드 조각 또는 프로젝트 |
| 결과 | 빠른 위험 신호 | 제출 판단용 전체 보고서 | 개발 단계의 수정 안내 |
| 비용 | 낮음 | 시간 소요 가능 | 구현 시간 약 1.2~1.5배, AI 토큰 추가 소요 가능 |

MCP 설정은 AI 도구별로 분리한다. Codex/ChatGPT Desktop, Claude Code, Claude Desktop의 설정 위치와 형식이 다르므로, 에이전트는 선택한 도구 하나만 확인·등록한다. Lovable처럼 자동 MCP 등록 계약이 없는 도구는 지원하지 않는다고 명확히 표시하고, 포털의 간편·표준 점검으로 안내한다.

체커 화면도 하네스와 같이 `설치 버전 확인`, `설치`, `업데이트` 세 버튼만 제공한다. MCP 등록은 체커가 설치·검증된 뒤 선택한 도구 카드에서 별도 승인으로 실행한다.

## 5. 사용자 흐름

### 5.1 최초 사용자

```text
중앙 포털 접속
  -> Windows 보안 에이전트 설치 다운로드
  -> Windows 설치 확인
  -> 에이전트가 개인 런타임·체커·하네스를 설치
  -> 설치 결과와 버전 표시
  -> 로컬 포털 열기
  -> 저장 위치 선택 -> 검사 대상 선택 -> 간편 또는 표준 점검
```

브라우저의 설치 버튼은 설치 파일 다운로드까지만 할 수 있다. 브라우저가 사용자의 동의 없이 EXE/MSI를 실행하거나 Python을 설치할 수는 없다. 다운로드 후 Windows 설치 확인 창에서 사용자가 승인하는 것이 정상적인 보안 흐름이다.

### 5.2 이미 설치한 사용자

```text
로컬 포털 또는 에이전트 열기
  -> 설치 버전 확인
  -> 최신: 상태 표시, 확인 버튼 비활성화
  -> 미설치: 설치 버튼만 활성화
  -> 구버전: 업데이트 버튼만 활성화
  -> 비공식·개발 설치: 공식 설치 버튼만 활성화, 기존 개발 폴더는 보존
```

설치·업데이트·MCP 등록·점검은 모두 진행 레이어를 사용한다. 실행 중에는 전체 진행률, 현재 단계, 다음 단계, 경과 시간을 보여준다. 완료되면 성공 내역과 `확인` 또는 `닫기`를, 실패·취소 시에는 이유와 `다시 시도`를 보여준다.

### 5.3 점검 사용자

```text
1. 결과 저장 위치 선택
2. 폴더 / ZIP / GitHub URL 선택
3. 간편 점검 또는 표준 점검 선택
4. 로컬 에이전트가 대상 준비 -> 체커 실행 -> 보고서 생성 -> PC 저장
5. HTML, JSON, Markdown 보고서 확인
6. 선택 동의 시 결과 요약만 중앙 통계에 전송
```

저장 위치를 고르지 않은 상태에서 점검을 시작하면 먼저 저장 위치가 필요하다는 안내만 보이고, 바로 점검을 시작하지 않는다.

## 6. 설치·업데이트 설계

### 6.1 배포 원칙

`main` 브랜치의 변경이 사용자 PC에 즉시 반영되면 안 된다. 다음 승격 절차를 거친다.

```text
변경 PR
  -> 하네스 게이트·체커 적대적 검증·사용자 시나리오 테스트
  -> 사람 승인
  -> tag / release 생성
  -> 설치 패키지 빌드
  -> SHA-256·코드서명·SBOM·release manifest 생성
  -> 기관 내부 승인 번들 레지스트리 등록
  -> 안정 채널 배포
```

release manifest에는 최소한 다음을 포함한다.

- 에이전트, 체커, 하네스, 룰셋, 인텔의 버전과 고정 commit 또는 artifact digest
- 파일 SHA-256, 코드서명 정보, 최소 호환 에이전트 버전
- 릴리스 날짜, 승인자, 변경 요약, 롤백 대상 버전

### 6.2 사용자 업데이트

1. 에이전트가 기관 내부 승인 채널의 manifest와 번들 목록을 읽는다.
2. 현재 설치본과 manifest의 버전·서명·해시를 비교한다.
3. 업데이트 필요 시 변경 요약과 영향을 보여주고 사용자가 승인한다.
4. 새 파일을 staging에 내려받아 서명·SHA-256·호환성을 검증한다.
5. 설정과 기존 버전을 백업하고 원자적으로 교체한다.
6. `gvskb doctor`, 하네스 검증, 에이전트 health check를 실행한다.
7. 실패하면 이전 정상 버전과 설정으로 롤백한다.

룰셋·인텔은 엔진과 독립적으로 갱신할 수 있지만, 검증된 manifest에 명시된 조합만 적용한다. GitHub의 `main`을 직접 `git pull`하여 운영 컴포넌트를 바꾸지 않는다. 로컬 설치본이 비공식·개발용 경로로 판정되면 자동 덮어쓰기를 하지 않고, 공식 번들을 별도 위치에 설치한 뒤 설정과 결과를 검증하여 전환한다.

## 7. 보안 설계

### 7.1 로컬 에이전트 API

- `127.0.0.1`에만 바인딩하고 LAN 인터페이스에는 열지 않는다.
- 허용 Host는 `127.0.0.1:포트`, `localhost:포트`로 제한한다.
- 상태 변경 API는 동일 Origin과 서버 기동 시 생성한 랜덤 요청 토큰을 요구한다.
- 관리자 인증과 로컬 제어 인증을 분리한다.
- 외부 웹페이지가 `localhost` API를 호출하도록 CORS를 열지 않는다.
- 명령 실행은 shell 없이 allowlist 인자만 사용한다.
- 파일명·압축 해제·업로드 경로는 경로 탈출, ZIP bomb, 파일 수·크기 제한을 검증한다.

현재 포털에 반영된 Host·Origin·요청 토큰 검증과 한글 보고서 다운로드 검증은 에이전트 API의 최소 보안 기준으로 유지한다.

### 7.2 데이터 최소화

| 데이터 | 로컬 에이전트 | 중앙 포털 |
|---|---|---|
| 원본 소스·ZIP | 검사 중 임시 보관 후 정리 | 전송·저장 금지 |
| GitHub URL·토큰 | 점검에 필요한 범위만 로컬 처리 | 토큰 전송 금지 |
| 전체 경로 | 로컬 UI에만 최소 표시 | 전송·저장 금지 |
| HTML·JSON·Markdown 보고서 | 사용자 선택 폴더에 저장 | 기본 전송 금지 |
| 검사 요약 | 로컬 이력 | 사용자 동의 시 익명 메타데이터만 |

중앙 DB에는 익명 설치 ID, 에이전트·체커·하네스 버전, 점검 모드, 결과 건수, 완료·실패 사유, 규칙 ID 집계만 저장한다. 담당자·부서 입력은 로그인 없는 1차 서비스에서 받지 않는다.

### 7.3 중앙 메타데이터와 관리자 목록

서버에는 보고서 파일이나 원본 소스가 아니라, 승인 번들의 배포·설치 현황과 점검 집계만 저장한다. 총괄 관리자만 기관 인증 후 이 목록을 조회·내보낼 수 있다. 일반 사용자는 자신의 PC에서만 보고서를 열고 저장한다.

| 관리 객체 | 필수 항목 | 금지 항목 |
|---|---|---|
| `release_bundles` | 번들 ID, 구성요소별 버전, 해시·서명·SBOM, 승인자·시각, 상태, 롤백 대상 | 원본 소스, 개인 토큰 |
| `agent_installations` | 익명 에이전트 ID, OS·에이전트 버전, 마지막 확인 시각, 설치 상태 | 사용자명, 부서명, 전체 PC 경로 |
| `agent_bundle_inventory` | 익명 에이전트 ID, 번들 ID·버전, 설치·검증·업데이트 상태, 실패 코드, 시각 | 보고서 본문, 소스 경로 |
| `scan_metadata` | 점검 모드, 결과 건수, 사용 번들 ID, 완료·실패 상태, 시각, 선택 동의 여부 | 소스·ZIP·GitHub 토큰·보고서 파일 |
| `admin_audit_logs` | 관리자 ID, 조회·내보내기·정책 변경 행위, 시각, 대상 범위 | 관리자 비밀번호, 원본 보고서 |

`release_bundles`와 `agent_bundle_inventory`의 조합이 향후 경기도 서버에 설치·승인할 패키지 목록의 기준이다. 관리자 화면은 최신 승인 번들, PC별 적용 번들 분포, 업데이트 대기·실패 수, 체커·하네스 버전 분포를 우선 보여준다.

### 7.4 네트워크

경기도 환경은 완전 망분리가 아니라 필요한 IP·포트를 방화벽에서 허용할 수 있다는 전제를 사용한다.

- 기본 온라인 모드: 기관 내부 포털, 기관 내부 승인 패키지 저장소, 승인된 인텔 미러 또는 OSV 등 필요한 체커 인텔 endpoint만 허용한다.
- 권장 운영: GitHub 원본은 개발·검증에 사용하고, 사용자 배포·업데이트는 기관 내부 승인 번들만 사용한다.
- 연결 실패: 최신 여부·의존성 인텔 확인이 불완전하면 안전으로 표시하지 않고 `확인 필요` 또는 `점검 불완전`으로 표시한다.
- 오프라인 전환: 별도 서명된 룰셋·인텔 bundle을 가져오는 절차를 제공한다.

## 8. 현재 구현에서의 전환 계획

| 단계 | 목표 | 기존 자산 활용 | 완료 기준 |
|---|---|---|---|
| 0 | 로컬 포털 보안 고정 | 현재 Node.js 서버, 화면, 시나리오 테스트 | Host·Origin·토큰, 보고서, 관리자 경계 테스트 |
| 1 | Windows 에이전트 패키지 | 현재 API·점검 작업·진행 레이어 | Python/Node/Git 사전 설치 없이 폴더·ZIP·GitHub 점검 |
| 2 | 서명된 안정 배포 | 하네스 게이트, 체커 검사, GitHub 저장소 | manifest, code signing, staging·rollback 업데이트 |
| 3 | 기관 내부 중앙 웹 포털 | 현재 화면 설계, Supabase 설계 | 승인 번들 레지스트리, 설치 메타데이터, 총괄 관리자 통계 |
| 4 | 운영 고도화 | 오탐 피드백·검사 기록 | 보존 정책, 릴리스 승인, 장애 대응, 개선 주기 |

### 8.1 기술 선택 원칙

현재 Node.js 구현을 즉시 폐기하지 않는다. 1차 에이전트는 Node 런타임과 Python 런타임을 설치 패키지 안에 포함해 현재 검증된 점검 로직을 재사용할 수 있다. 장기적으로는 Windows 서명·자동 업데이트·설치 관리에 적합한 네이티브 shell 또는 .NET 기반 host를 검토하되, 점검 엔진과 화면을 동시에 재작성하지 않는다.

패키지 형식은 기관 배포 정책에 따라 다음 우선순위로 검토한다.

1. 코드서명된 MSIX 또는 MSI: 중앙 관리·배포·업데이트에 적합하다.
2. 코드서명된 per-user EXE installer: 관리자 권한 없이 빠른 초기 배포에 적합하다.
3. 압축파일·PowerShell 설치 스크립트: 개발·검증용으로만 사용하며 일반 사용자 기본 경로로 쓰지 않는다.

## 9. 수용 기준

1. Python, Node.js, Git이 없는 깨끗한 Windows PC에서 설치와 간편·표준 점검이 가능하다.
2. 설치되지 않음, 최신, 업데이트 필요, 비공식 설치, 판정 불가 상태가 서로 다른 버튼 상태로 명확히 보인다.
3. 점검 대상과 보고서는 사용자 PC 밖으로 전송되지 않는다.
4. 업데이트는 서명·해시·manifest 검증과 백업·재검증·롤백 없이 적용되지 않는다.
5. MCP 등록은 AI 도구별로 분리되고, 선택한 도구의 설정만 사용자 승인 후 변경한다.
6. 간편 점검과 표준 점검의 범위·시점·결과 차이가 화면과 보고서에서 일관되게 설명된다.
7. 모든 설치, 업데이트, MCP 등록, 점검 진행 레이어는 성공·실패·취소의 최종 상태와 다음 행동을 보여준다.
8. 릴리스 전에는 하네스 게이트, 체커 점검, 사용자 시나리오, 로컬 API 적대적 검증을 모두 통과한다.
9. 기관 서버에는 승인된 번들만 등록되고, 관리자만 번들 목록·설치 현황·점검 메타데이터를 조회할 수 있다.
10. 에이전트는 설치된 번들과 기관 승인 번들을 비교하여 미설치·최신·업데이트 필요·판정 불가 상태를 구분하며, 사용자의 승인 없이 업데이트하지 않는다.

## 10. 설계 결정이 필요한 항목

- 기관 내부 배포 서버의 운영 주체, 승인자, 장애·재난 복구 절차
- 코드서명 인증서와 MSIX/MSI/EXE 배포 정책
- 체커 인텔 endpoint, GitHub release 또는 기관 mirror의 방화벽 allowlist
- 온라인 업데이트 주기와 긴급 보안 업데이트 절차
- 익명 메타데이터 전송 동의 문구, 보존 기간, Supabase 또는 기관 DB 선택 및 기관 인증 연계 방식
- 보고서 충돌 시 파일명 정책과 로컬 보존·삭제 정책
